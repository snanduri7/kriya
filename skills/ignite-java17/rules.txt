# Strict Rules for Apache Ignite on Java 17
Use Apache Ignite version 2.18.0.
Always include both ignite-core and ignite-spring Maven dependencies when setting up Ignite with Spring XML.
Always add the mandatory --add-opens flags for java.base (lang, reflect, io, util, concurrent, nio, net, concurrent.locks) to JVM execution configuration.
Enable peer class loading in Spring XML configuration if dynamic tasks/classes are run.
Use Java 17 source and target compatibility in the Maven Compiler Plugin.
Cache operations like getOrCreateCache must be called on an Ignite instance (returned by Ignition.start), never on the Ignition utility class.
Do not pass a Spring ApplicationContext object to Ignition.start().
The cache name argument to ignite.getOrCreateCache(...) or ignite.cache(...) must be a String literal (e.g. "my-cache") - never an Ignite instance, IgniteConfiguration, or ApplicationContext object. Passing the wrong type here ("incompatible types: Ignite cannot be converted to String") has caused repeated compile failures - double check the cache name argument's type before returning generated code.
IgniteCache is in the top-level org.apache.ignite package - import org.apache.ignite.IgniteCache;, NOT org.apache.ignite.cache.IgniteCache. Confirmed directly against the real ignite-core-2.18.0.jar contents: org.apache.ignite.cache holds configuration/enum types (CacheMode, CacheAtomicityMode, CacheConfiguration) but not IgniteCache itself, which is a plausible but wrong place to guess it lives. The wrong import compiles-fails with "cannot find symbol: class IgniteCache, location: package org.apache.ignite.cache" and was observed to repeat unchanged across every retry attempt in a real run - this is a fact to know outright, not something to work out from the compiler error.
Give every variable holding the started Ignite instance (from Ignition.start(...) or context.getBean(Ignite.class)) a name and keep it consistently in scope for the rest of the method - a variable referenced before or without being assigned (e.g. "cannot find symbol: variable igniteInstance") is a common self-inflicted regression when fixing an unrelated compile error.
To start Ignite using Spring XML, either use:
1) Direct Ignition: Ignite ignite = Ignition.start("ignite-config.xml");
2) Spring Bean: Define org.apache.ignite.IgniteSpringBean in the XML and fetch it from ApplicationContext using: Ignite ignite = context.getBean(Ignite.class);

When running Ignite with Java 11 or later, pass the following JVM flags: --add-exports=java.base/jdk.internal.misc=ALL-UNNAMED --add-exports=java.base/sun.nio.ch=ALL-UNNAMED --add-exports=java.management/com.sun.jmx.mbeanserver=ALL-UNNAMED --add-exports=jdk.internal.jvmstat/sun.jvmstat.monitor=ALL-UNNAMED --add-exports=java.base/sun.reflect.generics.reflectiveObjects=ALL-UNNAMED --add-opens=jdk.management/com.sun.management.internal=ALL-UNNAMED --add-opens=java.base/java.nio=ALL-UNNAMED --illegal-access=permit --add-opens=java.base/jdk.internal.access=ALL-UNNAMED --add-opens=java.base/jdk.internal.misc=ALL-UNNAMED --add-opens=java.base/sun.nio.ch=ALL-UNNAMED --add-opens=java.base/sun.util.calendar=ALL-UNNAMED --add-opens=java.management/com.sun.jmx.mbeanserver=ALL-UNNAMED --add-opens=jdk.internal.jvmstat/sun.jvmstat.monitor=ALL-UNNAMED --add-opens=java.base/sun.reflect.generics.reflectiveObjects=ALL-UNNAMED --add-opens=jdk.management/com.sun.management.internal=ALL-UNNAMED --add-opens=java.base/java.io=ALL-UNNAMED --add-opens=java.base/java.nio=ALL-UNNAMED --add-opens=java.base/java.net=ALL-UNNAMED --add-opens=java.base/java.util=ALL-UNNAMED --add-opens=java.base/java.util.concurrent=ALL-UNNAMED --add-opens=java.base/java.util.concurrent.locks=ALL-UNNAMED --add-opens=java.base/java.util.concurrent.atomic=ALL-UNNAMED --add-opens=java.base/java.lang=ALL-UNNAMED --add-opens=java.base/java.lang.invoke=ALL-UNNAMED --add-opens=java.base/java.math=ALL-UNNAMED --add-opens=java.sql/java.sql=ALL-UNNAMED --add-opens=java.base/java.lang.reflect=ALL-UNNAMED --add-opens=java.base/java.time=ALL-UNNAMED --add-opens=java.base/java.text=ALL-UNNAMED --add-opens=java.management/sun.management=ALL-UNNAMED --add-opens=java.desktop/java.awt.font=ALL-UNNAMED
Use Maven dependency <groupId>org.apache.ignite</groupId> <artifactId>ignite-core</artifactId> <version>2.18.0</version>
Use Maven dependency <groupId>org.apache.ignite</groupId> <artifactId>ignite-spring</artifactId> <version>2.18.0</version>
Set the JAVA_HOME environment variable to point to the Java installation directory when running Ignite with Java 11 or later
Set the IGNITE_HOME environment variable to point to the installation folder and ensure there is no trailing / in the path when using binary distribution
Any output a goal explicitly requires to be observable (e.g. a "[RESULT] ..." marker string proving the app worked) MUST use System.out.println(...), never an SLF4J/logger call - confirmed live for a different exec:java-based skill: Maven's `-q` flag silently suppresses SLF4J logger output entirely when the app class runs inside Maven's own JVM (the exec:java goal, not a separate spawned process), even though the exact same logger call prints fine without `-q`. System.out.println is unaffected by `-q` either way and is the only reliable choice here.
Apache Ignite needs its --add-opens flags applied at JVM STARTUP, which the exec:java goal cannot do (it runs inside Maven's own already-started JVM, and exec-maven-plugin's "java" goal has no "jvmArguments" parameter at all - confirmed by reading the actual mojo descriptor). Use exec:exec instead: <executable>java</executable> with every --add-opens flag as its own <argument>, then <argument>-classpath</argument> and the bare <classpath/> element, then the main class as the final argument - never <mainClass>+<jvmArguments>. Run via `mvn -q compile exec:exec -Dexec.mainClass=com.example.App`, not exec:java. See examples/pom.xml for the complete, verified-working shape.
The final <argument> in exec:exec's <arguments> list (the main class to run) must be ${exec.mainClass}, not a hardcoded literal class name - confirmed live: a literal value ignores `-Dexec.mainClass=...` on the command line and always runs that class regardless. Set a sensible default via an <exec.mainClass> property, so `mvn exec:exec` with no override still works, while every class in a multi-entrypoint project stays independently runnable via its own -Dexec.mainClass override.
