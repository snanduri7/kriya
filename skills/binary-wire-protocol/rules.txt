When a binary wire-format field's declared byte width is NARROWER than Java's native primitive width for that value's type (e.g. a 3-byte field holding a value you'd naturally store as an int, which occupies 4 bytes; a 1-byte field holding an int/short; a 6-byte field holding a long), do NOT use ByteBuffer.putInt()/putShort()/putLong() or DataOutputStream.writeInt()/writeShort()/writeLong() for that field - these always write the FULL native width regardless of the wire format's actual declared width. Confirmed live (2026-08-12, repeated across multiple sessions): a wire format specifying a 3-byte, big-endian `dataLength` field written via `buffer.putInt(dataLength)` throws `java.nio.BufferOverflowException` the moment the destination buffer/array is sized to the wire format's real total length (e.g. a 9-byte header), not Java's 4-byte int width - and the model's own fix-analysis correctly diagnoses this exact root cause on almost every retry, but has never once successfully re-implemented it correctly via a small edit; only a full rewrite or model escalation has fixed it live.
Instead, manually extract and write each byte individually via bit-shifting and masking. For a 3-byte big-endian field at offset `o` in a byte array `header`: `header[o] = (byte) ((value >> 16) & 0xFF); header[o+1] = (byte) ((value >> 8) & 0xFF); header[o+2] = (byte) (value & 0xFF);`. The mirror-image decode (reconstructing an int from 3 big-endian bytes, each masked with `& 0xFF` first since Java bytes are signed): `int value = ((data[o] & 0xFF) << 16) | ((data[o+1] & 0xFF) << 8) | (data[o+2] & 0xFF);`. Generalizes directly to any other narrower-than-native width (1 byte: just `(byte) (value & 0xFF)` / `data[o] & 0xFF`; 6-byte long: 6 shift/mask pairs instead of 3) and to little-endian (reverse which byte gets which shift amount).
Only use ByteBuffer.putInt()/getInt(), putShort()/getShort(), putLong()/getLong(), etc. directly when the wire field's declared width EXACTLY matches that primitive's native Java width (4 bytes for int, 2 for short, 8 for long) - narrower-than-native is the only case requiring manual byte-by-byte packing above.
Size the destination byte array/ByteBuffer to the wire format's EXACT total declared byte length - the sum of every field's own declared width (e.g. a 9-byte header really means 9, even though a naive `sizeof`-style calculation using each field's native Java type would total more) - never derive buffer size from native primitive widths.
When hand-rolling a binary wire-format encode() method that writes fields SEQUENTIALLY (a header followed immediately by more fields, written top-to-bottom in one pass), use ONLY relative (cursor-based) ByteBuffer writes - `put(byte)`, `putShort(value)`, `putInt(value)`, `putLong(value)` with NO index argument - never the absolute-indexed overloads (`putInt(index, value)`, `putLong(index, value)`, `putShort(index, value)`, or `position(n)` followed by more writes). Confirmed live twice (2026-08-14, isolated reproduction independent of any specific goal): a model asked to encode a header containing a non-standard-width field wrote `buffer.putInt(0, bodyLength)` (once followed by `buffer.position(4); buffer.putInt(...)` for the next field) - an absolute write at a HARD-CODED, assumed-fixed offset that silently overwrote already-correctly-written EARLIER fields (e.g. protocolVersion/softwareVersion at offsets 0-1) and misaligned every field written after it. This produces NO compile error and no BufferOverflowException either (the buffer is sized correctly, so nothing throws) - the corruption is only ever caught, if at all, by an unrelated-looking downstream validation error (e.g. "Data length mismatch" inside decode()), which makes it easy to misdiagnose as a completely different bug.
Absolute-indexed ByteBuffer writes ARE legitimate for exactly one recognizable shape: writing a placeholder value first, sequentially, for a field whose real value (a total length, a checksum) is only known AFTER writing everything that follows it, then going back with exactly one absolute-indexed write to patch just that field once the rest is written - that "backpatch" write happens LAST in the method, after the sequential writes it corrects. An absolute-indexed write appearing BEFORE or INTERLEAVED WITH the sequential writes for other fields, as in both confirmed incidents above, is not a backpatch - it is the model confusing "resume writing here" with "always write starting from this fixed spot," and should be treated as the anti-pattern above, not a legitimate use of the API.
When a wire-format field is declared as a NARROWER-than-native TRUNCATION of a wider Java type you're asked to store it as (e.g. a `long time` field the spec says to "treat as a 32-bit value" - the field is a `long` in your code, but only its low 4 bytes are ever written to/read from the wire), any SAMPLE or test value you manufacture for that field yourself MUST already fit within the declared narrower width - do not populate it with whatever the language's standard "get the current value" idiom happens to return if that idiom's natural range exceeds the wire width. Confirmed live (2026-08-14, spikes/eval_harness/runs/a-6): asked to build a 32-bit big-endian `time` field from a `long`, the model wrote correct byte-shifting encode()/decode() logic (matching this skill's own rules above) but populated the sample `Protocol` object's `time` field with `System.currentTimeMillis()` - which returns MILLISECONDS since epoch (currently ~1.75 trillion, needing ~41 bits), not seconds (~1.7 billion, well inside 32 bits). Encoding then decoding that value through a 4-byte field silently truncates it to a completely different number every time - a deterministic, 100%-reproducible round-trip failure with no exception and no malformed-input error, since the encode/decode arithmetic itself is correct; only the chosen sample value is wrong. This is easy to misdiagnose as an encode/decode bug (the visible symptom - "values don't match after round-trip" - looks identical to a real arithmetic error) when the actual fix is one line at the call site that constructs the sample value, e.g. `System.currentTimeMillis() / 1000` or `Instant.now().getEpochSecond()` for a "seconds since epoch" field. When a field's own spec names a unit (seconds vs. milliseconds) or an explicit bit width narrower than the variable's declared type, treat that as a hard constraint on any value the code itself generates for that field, not just on the encode/decode byte-packing logic.
