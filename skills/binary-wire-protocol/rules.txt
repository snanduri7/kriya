When a binary wire-format field's declared byte width is NARROWER than Java's native primitive width for that value's type (e.g. a 3-byte field holding a value you'd naturally store as an int, which occupies 4 bytes; a 1-byte field holding an int/short; a 6-byte field holding a long), do NOT use ByteBuffer.putInt()/putShort()/putLong() or DataOutputStream.writeInt()/writeShort()/writeLong() for that field - these always write the FULL native width regardless of the wire format's actual declared width. Confirmed live (2026-08-12, repeated across multiple sessions): a wire format specifying a 3-byte, big-endian `dataLength` field written via `buffer.putInt(dataLength)` throws `java.nio.BufferOverflowException` the moment the destination buffer/array is sized to the wire format's real total length (e.g. a 9-byte header), not Java's 4-byte int width - and the model's own fix-analysis correctly diagnoses this exact root cause on almost every retry, but has never once successfully re-implemented it correctly via a small edit; only a full rewrite or model escalation has fixed it live.
Instead, manually extract and write each byte individually via bit-shifting and masking. For a 3-byte big-endian field at offset `o` in a byte array `header`: `header[o] = (byte) ((value >> 16) & 0xFF); header[o+1] = (byte) ((value >> 8) & 0xFF); header[o+2] = (byte) (value & 0xFF);`. The mirror-image decode (reconstructing an int from 3 big-endian bytes, each masked with `& 0xFF` first since Java bytes are signed): `int value = ((data[o] & 0xFF) << 16) | ((data[o+1] & 0xFF) << 8) | (data[o+2] & 0xFF);`. Generalizes directly to any other narrower-than-native width (1 byte: just `(byte) (value & 0xFF)` / `data[o] & 0xFF`; 6-byte long: 6 shift/mask pairs instead of 3) and to little-endian (reverse which byte gets which shift amount).
Only use ByteBuffer.putInt()/getInt(), putShort()/getShort(), putLong()/getLong(), etc. directly when the wire field's declared width EXACTLY matches that primitive's native Java width (4 bytes for int, 2 for short, 8 for long) - narrower-than-native is the only case requiring manual byte-by-byte packing above.
Size the destination byte array/ByteBuffer to the wire format's EXACT total declared byte length - the sum of every field's own declared width (e.g. a 9-byte header really means 9, even though a naive `sizeof`-style calculation using each field's native Java type would total more) - never derive buffer size from native primitive widths.
