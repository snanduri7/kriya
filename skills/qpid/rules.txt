"Red Hat Qpid MRG" and "Red Hat AMQ" (classic messaging line) both refer to Apache Qpid - use genuine Apache Qpid Broker-J and qpid-jms, not ActiveMQ Artemis, even though both speak AMQP.
Use org.apache.qpid:qpid-broker-core, org.apache.qpid:qpid-broker-plugins-amqp-1-0-protocol, and org.apache.qpid:qpid-broker-plugins-memory-store (version 9.2.1) for an embedded Qpid Broker-J server. All qpid-broker-* modules release in lockstep - use the same version number for all of them.
Do not guess a Qpid Broker-J version number - 7.0.0 and 1.4.0 do not resolve on Maven Central. Use 9.2.1; if that fails to resolve, verify the current version at https://central.sonatype.com/artifact/org.apache.qpid/qpid-broker-core before retrying.
Embed the broker via org.apache.qpid.server.SystemLauncher: call startup(Map<String,Object>) with a config map containing "type": "Memory", "initialConfigurationLocation" (a URL to a JSON config resource), and "startupLoggedToSystemOut": true; call shutdown() to stop it.
"initialConfigurationLocation" must be a real java.net.URL string, obtained via YourClass.class.getClassLoader().getResource("qpid-initial-config.json").toExternalForm() (resolves to a file:/jar: URL the JDK understands). Do NOT build it as "classpath:qpid-initial-config.json" or new URL("classpath:...") - "classpath:" is a Spring-only convention that plain java.net.URL does not recognize.
The attributes map passed to SystemLauncher.startup() MUST also include "initialSystemPropertiesLocation", even when the app sets no custom system properties: getClass().getClassLoader().getResource("system.properties").toExternalForm() against an empty src/main/resources/system.properties file (see examples/system.properties) is enough. If this key is omitted, SystemLauncher itself defaults to loading "classpath:system.properties" via its own hardcoded, uncaught java.net.URL("classpath:...") call - this only resolves when Qpid's own "classpath" protocol handler (org.apache.qpid.server.util.urlstreamhandler.classpath.Handler) is visible to java.net.URL's handler lookup, which uses the JVM's system classloader and is NOT visible when exec-maven-plugin's exec:java goal loads the app through its own isolated project classloader. This is the real, root cause of "PrivilegedActionException...unknown protocol: classpath" at broker startup, confirmed via bytecode inspection of qpid-broker-core 9.2.1's SystemLauncher.class - it fires even when the generated code itself never constructs a "classpath:" URL anywhere. See examples/BrokerServer.java for the exact, verified-working pattern.
The initial configuration JSON (loaded from src/main/resources) must define the broker name, a port for AMQP 1.0 (default 5672), and at least one virtual host node with a queue auto-creation policy - see examples/qpid-initial-config.json for the exact, verified-working structure.
The AMQP port in the initial configuration JSON must declare "virtualhostaliases" including a {"type": "defaultAlias"} entry. Without it, the client's AMQP Open-frame hostname (defaulting to whatever host is in the connection URI, e.g. "localhost") can never resolve to any virtualhost regardless of what that virtualhost is named - fails with "JmsResourceNotFoundException: Unknown hostname in connection open" even though the broker itself started and the port opened without error.
session.createQueue(name) in JMS is purely a client-side reference and does NOT create anything on the broker. The virtualhost's virtualHostInitialConfiguration must include a nodeAutoCreationPolicies entry (pattern ".*", createdOnPublish/createdOnConsume "true", nodeType "queue" - see examples/qpid-initial-config.json for exact syntax), or sending to a not-yet-existing queue fails with "InvalidDestinationException: Could not find destination for target".
A Memory (non-durable) broker store cannot accept the JMS default PERSISTENT delivery mode - call producer.setDeliveryMode(DeliveryMode.NON_PERSISTENT) before sending, matching the official qpid-jms Sender.java example, or sends fail with "Non-durable message store cannot accept durable message."
The initial configuration JSON's "modelVersion" field is the broker's internal domain-model schema version, NOT the qpid-broker-core artifact/release version - do not set it to match the broker-core version (e.g. "9.2" for broker-core 9.2.1). Use "8.0", which is what qpid-broker-core itself ships as its own default initial-config.json across its 8.x/9.x/10.x releases. A mismatched modelVersion fails with "IllegalConfigurationException: No phase upgrader for version X" during SystemLauncher.startup() - this does NOT throw from startup() itself, so the broker silently never binds its AMQP port and any client connection attempt fails with a plain connection-refused error that gives no hint the root cause was the config file.
Use org.apache.qpid:qpid-jms-client for the JMS client - version 1.16.0 for javax.jms (JMS 2.0), or 2.10.0 for jakarta.jms (Jakarta Messaging 3.1). Match whichever javax/jakarta convention the rest of the Spring project uses; do not mix the two.
The client connection factory class is org.apache.qpid.jms.JmsConnectionFactory. It has a no-arg constructor and a setRemoteURI(String) setter, so it is directly usable as a Spring XML bean via <property name="remoteURI" value="amqp://localhost:5672"/>.
Connection URIs use the amqp:// scheme (amqps:// for TLS), e.g. amqp://localhost:5672 - this is different from ActiveMQ Artemis's acceptor URL syntax (tcp://localhost:5672?protocols=AMQP), do not mix the two conventions.
Use standard javax.jms / jakarta.jms API calls (ConnectionFactory, Connection, Session, MessageProducer, MessageConsumer) against the JmsConnectionFactory - qpid-jms is a JMS provider, not a separate client API to learn.
If a goal requires an embedded broker AND a client to communicate within the SAME application (not connecting to an already-running external broker), start the broker via SystemLauncher.startup(...) BEFORE building the Spring ApplicationContext or creating any JMS connection, in the same main()/bootstrap method - see examples/CombinedBrokerClientApp.java. A client-only class that wires JmsConnectionFactory without ever starting the broker compiles fine but fails at runtime with connection-refused.
For internal logging output, SLF4J (org.slf4j:slf4j-api and org.slf4j:slf4j-simple, version 1.7.36, via LoggerFactory.getLogger(YourClass.class); slf4j-simple requires no extra config file) is fine. But any output a goal explicitly requires to be observable (e.g. a specific "[RESULT] ..." marker string that proves the app worked) MUST use System.out.println(...), never an SLF4J/logger call - confirmed via a real `mvn -q compile exec:java` run: when the app class runs inside Maven's own JVM (the exec:java goal, not a separate process), Maven's `-q` flag suppresses SLF4J logger output entirely (0 bytes reach stdout/stderr) even though the exact same logger.info(...) call prints fine without `-q` - System.out.println output is unaffected by `-q` either way and is the only reliable choice for a required verification marker.
To run the app via `mvn exec:java`, the exec-maven-plugin configuration must use ONLY <mainClass> and a single <jvmArguments> string for any JVM flags (e.g. Java 17's --add-opens) - never an <arguments> element, which belongs to the different exec:exec goal and fails with "Unable to parse configuration of mojo ...:java for parameter arguments" if used with exec:java. See examples/pom.xml for a complete, verified-working reference.

Use modelVersion "8.0" in the initial configuration JSON, not the qpid-broker-core artifact version (e.g., do not use "9.2" for broker-core 9.2.1).
The AMQP port definition in the initial configuration JSON MUST include a virtualhostaliases entry with a defaultAlias, or client connections will fail to resolve the virtualhost.
Any virtualhost in the initial configuration that should accept publishes to not-yet-existing queues MUST have a nodeAutoCreationPolicies entry with pattern ".*", createdOnPublish/createdOnConsume "true", and nodeType "queue".
When using a Memory store broker, JMS senders must explicitly call setDeliveryMode(DeliveryMode.NON_PERSISTENT) before sending messages, as the Memory store cannot accept the default PERSISTENT delivery mode.
The qpid-jms client library version to use is 1.16.0 for javax.jms (JMS 2.0) or 2.10.0 for jakarta.jms (Jakarta Messaging 3.1).
The JMS ConnectionFactory class is org.apache.qpid.jms.JmsConnectionFactory, which supports a no-arg constructor and setRemoteURI(String) setter.
Connection URIs for the JMS client must use the amqp:// scheme (e.g., amqp://localhost:5672), not ActiveMQ Artemis's tcp:// syntax.
The initial configuration JSON file must be loaded via a java.net.URL obtained using YourClass.class.getClassLoader().getResource("qpid-initial-config.json").toExternalForm().
When running via mvn exec:java, use only <jvmArguments> and avoid adding an <arguments> element to the exec-maven-plugin configuration.
The broker's startupLoggedToSystemOut flag in the config map passed to SystemLauncher.startup() should be set to true for debugging purposes.
