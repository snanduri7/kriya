## Current backlog

Confirmed still open, checked against actual code as of tag `0.10`:

- **Stage 2B's human-ask fallback asymmetry** - only falls back to asking a human when live-lookup returns *some* result but nothing usable; if it returns literally nothing, the fallback doesn't fire (unlike Stage 1.2's more robust pattern). Pre-existing, narrow, not yet fixed.
- **"Enabling reasoning" / retry-prompt de-noising** - HIGH PRIORITY, narrowed further. Several cheap instances closed (redundant-dependency checklist; `retry_temperature` opt-in + javac `-Xlint:rawtypes,unchecked` diagnostics; LSP grounding for import/symbol mistakes). Injected into future milestones the way `_java_toolchain_fact()` already injects a fact. Different retry attempts papered over this differently: one attempt referenced the original object from a method scope where it didn't exist (a real, LSP-catchable "cannot find symbol" compile error), another attempt's cache lookup simply returned nothing at runtime (a real, RUN VERIFICATION-catchable failure) - but neither compile checks, LSP grounding, nor lint flags can ever catch "you skipped an explicitly-requested step but produced plausible-looking code around its absence," because the code that exists is syntactically/type-correct. This is a different failure class from every other one logged so far (missing instruction, wrong/ignored fact, lost self-diagnosis) - a genuinely missing implementation step masked by a workaround. Not fully fixed (see the retry-loop fix below, which addresses WHY the model got zero course-correction across 3 identical attempts, not the underlying model behavior itself) - would still benefit from a goal-completion-specific reviewer check distinct from the general code-quality Reviewer pass.
- **LSP grounding still gave zero log trace on a real, live-reproducible catch - fixed (2026-08-03)** - the very next cold-start run after the debug→warning visibility fix had a real "cannot find symbol: class Logger" (missing imports) compile error, exactly the shape LSP grounding is built for - and again, zero "jdtls"/"LSP" trace anywhere in the log. Re-ran the real production functions directly against the actual broken file: jdtls started in 1.6s and correctly caught every missing-import diagnostic. So the WARNING-level fix wasn't enough - a successful check that finds zero diagnostics produces zero log output BY DESIGN (not a failure), which meant "never engaged this run" and "engaged, found nothing" were still indistinguishable. Fixed: `_get_or_start_jdtls_client()` now logs a one-time INFO note on both the not-found path (previously fully silent) and the successful-start path (previously silent on success) - a run's log can now affirmatively confirm LSP grounding was active. Still open: whether jdtls was actually invoked during that specific cold-start run remains unconfirmed - this closes the observability gap for the NEXT run, not a retroactive diagnosis of this one.
- **Same symptom, different root cause across two different cold-start runs (2026-08-03)** - "No Person found in cache" recurred in a second cold-start run, but the actual generated code was completely different this time: a real `MessageConsumer.receive()` call WAS present and correctly threaded into the cache write (unlike the earlier run's missing-receive bug) - the actual bug was `storeInIgniteCache()` and `readAndLogFromCache()` each independently calling `Ignition.start()` inside their own try-with-resources block, so the write's node auto-closed before the read's brand-new node ever existed - two separate, non-communicating Ignite instances. Unlike the missing-receive() case, this IS the kind of fact a skill rule can catch (a concrete "don't do X" pattern, not "did you skip an entire step") - added to `skills/ignite-java17/rules.txt`. Reinforces the existing "not every wrong case needs the same fix" lesson: two failures with an identical user-visible symptom had entirely different root causes and entirely different appropriate fixes.
- **Anchored-edit parsing swallowed a redundant trailing FILE CONTENT: block into the applied patch - fixed (2026-08-04)** - M1 (previously 100% reliable across every prior run) failed for the first time in a manual overnight re-run. Root-caused: attempt 1 hit the classic `org.apache.ignite.cache.IgniteCache` wrong-import bug; attempt 2's retry (with LSP grounding active, confirmed via the INFO trace) correctly self-diagnosed AND correctly fixed it via a clean 3-line SEARCH/REPLACE - but ALSO appended a redundant, unasked-for FILE CONTENT: block after it. `_split_fix_analysis_edit()`'s `replace_block = text[replace_match.end():].strip()` had no bound at a subsequent "file content:" marker, so the entire redundant full-file text (plus the literal "FILE CONTENT:" string) got swallowed into the applied patch, duplicating the package/import/class declaration mid-file and producing "class, interface, enum, or record expected". That corruption then cascaded: every remaining attempt (3-6) failed with "Anchor matching failed... matched 0 times" against the now-unexpectedly-shaped file, burning the entire retry budget on a self-inflicted parsing bug rather than a real model or environment issue. Genuinely reassuring finding buried in a bad outcome: the model's own SEARCH/REPLACE diagnosis was entirely correct - LSP grounding and the Ignite skill rule both did their job; Kriya's own parsing corrupted a good answer. Fixed: truncate `replace_block` at any trailing "file content:" marker. Confirmed failing pre-fix (reproduced the exact real response shape), passing post-fix.
- **Anchored-edit SEARCH/REPLACE blocks sometimes contained Kriya's own copied error-source gutter formatting - fixed (2026-08-04)** - found live in the very next validation run after the FILE CONTENT truncation fix above (same failure class, different mechanism). `_build_error_source_context()` shows the model real source lines prefixed with `>> N: ` (the reported error line) or `  N: ` (surrounding context), so the model can see exactly what's broken - but a real response copied that display formatting directly into its SEARCH block (`>> import org.apache.ignite.cache.IgniteCache;`, keeping the `>>` marker, dropping the line number). That text can never match the real file's plain `import ...;` line, guaranteeing "Anchor matching failed... matched 0 times" regardless of whether the model's intended fix was otherwise correct - a self-inflicted retry-budget waste, not a model reasoning failure. Fixed: `_split_fix_analysis_edit()` now strips both `>>`/line-number gutter prefixes and wrapping ```lang fences from SEARCH/REPLACE blocks before they're used, matching the exact format `_build_error_source_context()` itself emits (safe against false positives - no real source line legitimately starts with `>>`, and the non-highlighted gutter form is only stripped when followed by a colon-terminated line number, never just an ordinary 2-space indent). A subtle ordering bug surfaced while testing this: the pre-existing `.strip()` on the raw extracted block ran before gutter-stripping and silently ate a "  N: " gutter's leading spaces on whichever line landed first - fixed by deferring all stripping until after gutter-removal. 3 new regression tests (real gutter shape, line-numbered gutter shape, confirms ordinary indented code is untouched), all confirmed failing pre-fix, passing post-fix.
- **Root-caused the "silent exit code 1 right after Qpid Broker Ready" mystery (2026-08-04)** - reproduced the exact failing attempt in a real standalone Maven project (not mocked) to get the real, unfiltered stderr Kriya's own captured output was missing. Real cause: the model's hand-rolled JSON serialization (`"{\"name\":\"" + name + "\",\"age\":" + age + "}"`) parsed back via unbounded `substring(indexOf(...) + N)` calls - the age field's substring has no upper bound, so it always includes the trailing `}`, and `Integer.parseInt("1}")` throws `NumberFormatException` on literally the first message every time (not an edge case - the last field is always followed by the closing brace). Confirmed this is a genuine model-generated code bug, not a Kriya bug - added a concrete rule to `skills/qpid/rules.txt` recommending Jackson's `ObjectMapper` (or explicit substring bounds) instead of unbounded ad-hoc string parsing. Separately confirmed Kriya's own output-capture mechanism (including yesterday's process-group fix) correctly captures this exact exception when re-tested directly - the original run's missing exception text looks like an intermittent capture race, not a deterministic bug; not chased further given no reliable repro.
- **Root-caused the "app finishes all work, prints the correct result, then times out anyway" mystery (2026-08-04)** - the model's own fix-analysis blamed a slow Qpid broker shutdown; verified this directly instead of trusting it. Reproduced with a minimal, isolated test: a bare `SystemLauncher.startup()`/`.shutdown()` with no Ignite involved exits cleanly in ~1s. Adding an `Ignite ignite = Ignition.start()` that's never explicitly closed reproduced the exact hang - the process printed everything expected (including the shutdown-returned marker) and then hung indefinitely, confirmed by letting it run past a 30s timeout with nothing further happening. Real cause: yesterday's node-lifecycle fix (share ONE Ignite instance across methods instead of starting a new one per operation) correctly fixed the "separate nodes, read returns null" bug, but left the natural follow-on question - "closed how, and when?" - unaddressed, and the generated code that surfaced this never explicitly closed the shared instance. Not a Kriya bug; a real, reproducible Ignite lifecycle gotcha (background threads keep the JVM alive) that the retry loop was burning budget on for the wrong diagnosis (the model kept trying to add Maven exec-plugin timeout settings, which can't fix a genuine application hang). Updated the same skill rule from yesterday to cover both halves: start once, AND close exactly once (try-with-resources wrapping the whole main() body, or an explicit `ignite.close()` alongside the Qpid shutdown call).
- **Timed-out commands leaked child processes across entirely separate, later runs - fixed (2026-08-03)** - a "port in use" Runtime Verification failure in one validation folder was traced to a stray `java` process from a DIFFERENT, already-finished validation folder, still alive and holding the port over an hour later. Root cause: `_run_cmd_with_timeout()` used `subprocess.run(..., timeout=...)`, whose built-in timeout handling only kills the DIRECT child process. `mvn exec:exec` forks its own separate `java` process to actually run the app (the entire point of exec:exec over exec:java) - killing `mvn` on timeout left that `java` child (and the embedded Qpid broker it started) running indefinitely, orphaned, in the background. Fixed: the subprocess is now started with `start_new_session=True` (POSIX `setsid`, putting it in its own process group) and a timeout now kills the WHOLE process group (`os.killpg(..., SIGKILL)`), not just the direct child. New regression test spawns a real child process from within the timed-out command and confirms it actually stops (a heartbeat file stops updating) rather than surviving orphaned - confirmed failing pre-fix (child kept running for the full duration) and passing post-fix.
- **Runtime Verification failures got weaker retry-loop treatment than compile failures - fixed (2026-08-03)** - root-caused why the same model, same goal, same prompt failed 3 consecutive attempts with zero self-correction: `extract_implicated_files()` scopes a retry by finding a known file's basename literally inside the failure text. A compile error always contains that (`file:[line,col]`). A Runtime Verification failure's text is an LLM judge's prose plus captured stdout (broker banners, SLF4J lines with no `.java` suffix) - confirmed by inspecting the actual captured output from the real failing run, no filename ever appears. So `last_implicated_files` came back empty for every runtime failure, which silently disabled the FIX ANALYSIS forcing instruction, the anchored-edit preference, and file-scoped LSP grounding - for this entire failure class, on every project, regardless of any skill (this is the general, cold-start-friendly fix, as opposed to a narrow per-domain skill rule). Fixed: `RunVerifierAgent.grade()` now also receives `files_written` and returns a `likely_files` field (validated against the real file list - same trust-boundary pattern as the skill-conflict-checker's index validation), which gets folded into the raised failure text ("Likely responsible file(s): ...") - the existing basename-matching mechanism picks it up with no other plumbing needed, so the file-scoped retry, FIX ANALYSIS, and LSP grounding all now apply to runtime-verification failures the same way they already did for compile failures.
- **Breadth beyond Java/Maven** - real compile/test/LSP support only exists for Java (Maven/Gradle + jdtls), Ruby, and Python; anything else (most obviously Node/TypeScript, given prevalence) gets `"unknown"`-stack handling (honest "not validated" skip, see the false-positive fix above) rather than an actual quality gate. Closing this for one more stack means three separate pieces of work: real compile/test invocation (`PolymorphicValidator`), an LSP client for that stack's language server (mirroring `kriya/tools/lsp.py`'s jdtls client, e.g. `typescript-language-server`), and dependency-checklist/regression logic for that stack's manifest (mirroring `get_pom_dependencies()` for `package.json`). Not started - scope as its own increment, not a quick fix.
- **Rule-level verification granularity** - a passing Runtime Verification run marks *every* rule in the active-context snapshot verified, not just the ones the generated code actually exercised. Known limitation of the Gap 6 skill-trust design, not fixed.

## Durable lessons learned (pattern-level, not session narrative)

- **Passive reference material is never enough - the model needs explicit checklists/instructions.** Confirmed repeatedly: showing the model its own prior file content, or existing dependencies, as passive context did NOT stop dependency drops, missing files, or redundant/wrong additions. An explicit "you must preserve/must not add X" instruction did. This generalizes: never assume a model will infer a constraint from context alone if the constraint is important.
- **A retry loop needs a forcing function, not just "here's the error, try again."** Single-shot, non-reasoning completion will regenerate byte-for-byte identical broken code across many retries even with the exact error present in every prompt, because nothing requires it to engage with that error before writing code. Structured "explain the fix, then write the code" instructions work as a prompting-level substitute for genuine reasoning.
- **Scope error-specific instructions to the file(s) actually implicated, always - even in a "regenerate everything" retry.** Broadcasting an error-specific instruction to every file in a batch produces confused/wrong output for unrelated files and dilutes the one response that mattered. Whatever mechanism identifies "which file is broken" should gate every downstream per-file signal, not just decide targeted-vs-full-set routing.
- **A model that already knows the right answer in a clean prompt can still get it wrong in the real noisy retry loop.** Don't assume a wrong answer means a knowledge gap - test the same question in isolation before concluding the model needs more capability (reasoning, a bigger model, live lookup). Often the fix is making the prompt say the right thing more clearly, not giving the model more power.
- **Test capability claims at realistic scale, not on a toy task.** Tool-calling reliability that looked solid (3/3) on a tiny Stack-class task collapsed completely on a realistically-sized file. Any "is X reliable" check needs to match the real workload's shape (size, complexity), or the result doesn't transfer.
- **Verify a regression test actually fails pre-fix, every time - a passing-for-the-wrong-reason test is a real, recurring risk.** Caught more than once: a test that looked like it validated a fix instead passed on both old and new code because of an unrelated mocking gap. `git stash` + confirm the failure mode matches the bug, every time, no exceptions.
- **Environment/toolchain mismatches are easy to re-discover from scratch - check memory before re-diagnosing.** JAVA_HOME/JDK version drift has bitten multiple times; the fix each time was already recorded from a prior session.
- **Real, live validation surfaces bugs that a fully-mocked test suite structurally cannot.** Nearly every significant bug found this whole effort came from an actual end-to-end run against real local models and real tools, not from the (extensive, always-green) mocked test suite. Mocked tests verify the code does what it's supposed to do; live runs verify the code's assumptions about the outside world are correct.
- **A "durable fact injected into the prompt" is a proven, reusable pattern** (skills, toolchain facts, dependency checklists) - reach for this shape again before inventing something new when the problem is "the model doesn't reliably know/apply X."
- **Structural/deterministic grounding beats more or better prompting for some error classes.** Real research found production coding agents increasingly favor deterministic tools - LSPs, linters, the compiler's own lint flags - over bigger models or cleverer prompts for catching import-path and type mistakes specifically. Matches this session's own evidence: a reasoning model gave zero benefit over prompting for a fact-recall error, and a prose skill rule stated verbatim in every prompt still didn't stop a recurring wrong-import mistake. When a mistake is the kind a compiler/tool could verify with certainty, reach for that before reaching for a smarter/slower model.
- **Lower temperature, not higher, for a stuck retry.** Counter to intuition, cited research found code-gen success rate drops as temperature rises even within a low range - "add randomness to shake it loose" is not supported by evidence.
- **A correct self-diagnosis can still fail to become a correct edit - and full-file regeneration is where it gets lost.** Found live: a model's own FIX ANALYSIS text named the exact right fix, then the regenerated file didn't contain it. Not a knowledge or grounding problem (LSP wouldn't help this one) - a small, anchored patch instead of a full rewrite has no unrelated content for a stated intention to get lost inside. When a precise fix location is known, prefer patching over regenerating.
- **An optional feature's failure path must never log below the default level - or its failures are undebuggable from the field.** Found live: LSP grounding's own start()/check failure paths logged at `debug`, so when jdtls silently failed to catch a real compile error it should have caught, the log gave zero clue why - "not installed" and "installed but broken" looked identical from the outside. Any optional/best-effort capability (a local tool, an LSP client, a linter) needs its degrade-to-off path logged at a level that actually survives to the operator, matching the precedent already set by `toolchain_warning`/`unresolved_skill_gaps` - both a debug log line AND a persisted result field, not one or the other.
- **A general retry-loop mechanism can silently only work for the failure class it was first built against - check it against every failure class, not just that one.** `extract_implicated_files()`'s basename-in-text matching was built and validated against compile errors (which always name a file), then reused as the single gate for FIX ANALYSIS/anchored-edit/LSP scoping generally - but a Runtime Verification failure's text structurally never names a file, so the same mechanism silently never engaged for that whole class, on every project, regardless of skills. This is also the right lever for a cold-start user with zero pre-existing skills: a domain-specific skill rule only ever fixes the one pattern it was written for and does nothing for the next novel goal, but a structural retry-loop fix like this one helps every goal in that failure class immediately, skill or no skill.
- **Any display formatting Kriya adds when SHOWING the model something (line-number gutters, `>>` highlight markers, etc.) is at risk of being echoed back verbatim into a field that needs the raw, unmarked original.** Found twice now in the same mechanism: a model asked to produce an exact-match SEARCH block copied the visual formatting Kriya itself added for readability, not just the underlying content. Any prompt section that displays code/text with added-for-humans decoration, when the model is later asked to reproduce a piece of it exactly, needs either an explicit "these markers are not part of the file" instruction, defensive stripping on the way back in, or both.
- **Parse defensively for a model that over-delivers, not just one that complies exactly.** The anchored-edit prompt asks for SEARCH/REPLACE OR FILE CONTENT, not both - but a real response included both anyway (a redundant, unasked-for full-file regeneration appended after a perfectly correct small patch). The parsing code assumed "replace_block runs to the end of the model's response" was a safe bound; it wasn't, the moment a model does more than exactly what was asked. Every marker-based parser in this codebase should assume a well-intentioned model may add extra structure beyond what's requested, not just omit what's asked for.
- **Separate validation folders aren't actually isolated from each other at the OS level - a leaked process from one can silently corrupt a completely different run, an hour later.** Found live: a "port in use" failure in one validation folder was actually caused by a stray process from a DIFFERENT, already-finished folder that Kriya's own timeout handling failed to fully kill. Each folder has its own git worktree/filesystem sandbox, but they all share the same machine's process table and network ports - a resource leak in one run's execution is a real, cross-contaminating risk to every other run sharing the machine, not a contained failure.
- **Not every "the model got it wrong" case needs the same fix.** This session found several different root causes behind superficially similar retry failures - a missing instruction (redundant dependency), a missing/ignored fact the model won't override on its own (wrong import), and a correct fact that didn't survive a full rewrite (missing Serializable). Diagnose which one before reaching for a fix - they don't share a solution.
