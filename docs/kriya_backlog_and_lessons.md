## Current backlog

Confirmed still open, checked against actual code as of tag `0.10`:

- **`check_skill_conflicts()` O(skills²) waste** - near-100% hallucination rate observed live (38 discarded "conflicts" across 3 skill pairs, ~93s/~4700 tokens burned, zero real conflicts) - the verbatim-match safety filter works correctly, but the underlying LLM call is producing near-pure noise. Not yet investigated for a prompt-level fix.
- **`extract_target_test()` substring-vs-basename matching** - does substring matching against the full filepath, not basename, for "is this a test file" detection. Minor, low blast-radius, still present.
- **Stage 2B's human-ask fallback asymmetry** - only falls back to asking a human when live-lookup returns *some* result but nothing usable; if it returns literally nothing, the fallback doesn't fire (unlike Stage 1.2's more robust pattern). Pre-existing, narrow, not yet fixed.
- **"Enabling reasoning" / retry-prompt de-noising** - HIGH PRIORITY, narrowed further. Two cheap instances closed (redundant-dependency checklist; `retry_temperature` opt-in + javac `-Xlint:rawtypes,unchecked` diagnostics). Reasoning-model routing specifically is now de-prioritized - a direct A/B test showed zero correctness benefit for a fact-recall-class error (13x slower for the same answer), and cited research (LLMs have "a very strong bias to generate code based on their priors," struggle to override it via in-context info "especially for smaller, openly-accessible models") suggests prompting alone - reasoning or not - may not be the right lever for the remaining hard case (`IgniteCache` wrong-import, persists even with the correct fact stated verbatim). See the new LSP item below, which targets that case directly and differently.
- **LSP integration (e.g. `jdtls` for Java) as a pre-flight/grounding check**, researched 2026-08-03, not yet scoped. Well-corroborated as now-mainstream practice among real coding agents. Directly targets the one bug this whole effort never closed: a language server holds the project's REAL resolved type graph and reports an unresolvable import deterministically in milliseconds, rather than relying on the model's own knowledge or a prose skill rule it may still ignore. Bigger scope than a config/flag change - needs its own pass (how to invoke/manage a language server process per-language, parse diagnostics, decide gate-vs-inform).
- **Durable "verified project facts" ledger** - not yet scoped. Idea: capture project-specific facts learned the hard way (e.g. "X resolves transitively, don't add it explicitly") after a successful run, the same way skill rules get extracted/verified today, but scoped per-project not per-library. Injected into future milestones the way `_java_toolchain_fact()` already injects a fact. Open questions: what counts as a fact worth capturing, how to extract it automatically, how to invalidate it if the project changes.
- **Extending `extract_error_search_terms()` to more compiler error shapes** - only 2 shapes handled (coordinate, wrong-import). Partially superseded by the newer, more general file:line:col source-context mechanism, but not fully closed - explicitly requested to stay logged as backlog.
- **Model-mixing within the Developer pipeline** - json_mode for large/full-file content (proven reliable across every model tested), native tool-calling specifically for small anchored-edit-sized targeted fixes (reliable for 2/3 models even on large-argument tests). Real, evidence-backed, not implemented.
- **Standalone `kriya skills audit` command** - explicitly deferred multiple times.
- **Full containerized (Docker) isolation** for quality-gate execution - explicitly out of scope; process-level sandboxing (env allowlist + resource limits) is what exists today.
- **mypy/type-checking** - deferred pending a concrete pain point.
- **Rule-level verification granularity** - a passing Runtime Verification run marks *every* rule in the active-context snapshot verified, not just the ones the generated code actually exercised. Known limitation of the Gap 6 skill-trust design, not fixed.

Resolved, NOT backlog (don't re-open without new evidence):
- **Tool-calling-based agent loop architecture** - empirically tested twice (small task, then realistic large-file-argument task) against 3 local models, confirmed not viable today via any backend (Ollama or vLLM), externally corroborated by Qwen's own recommended stack and by Aider's real production choice. This is a closed "no," not an open question.

## Durable lessons learned (pattern-level, not session narrative)

- **Passive reference material is never enough - the model needs explicit checklists/instructions.** Confirmed repeatedly: showing the model its own prior file content, or existing dependencies, as passive context did NOT stop dependency drops, missing files, or redundant/wrong additions. An explicit "you must preserve/must not add X" instruction did. This generalizes: never assume a model will infer a constraint from context alone if the constraint is important.
- **A retry loop needs a forcing function, not just "here's the error, try again."** Single-shot, non-reasoning completion will regenerate byte-for-byte identical broken code across many retries even with the exact error present in every prompt, because nothing requires it to engage with that error before writing code. Structured "explain the fix, then write the code" instructions work as a prompting-level substitute for genuine reasoning.
- **Scope error-specific instructions to the file(s) actually implicated, always - even in a "regenerate everything" retry.** Broadcasting an error-specific instruction to every file in a batch produces confused/wrong output for unrelated files and dilutes the one response that mattered. Whatever mechanism identifies "which file is broken" should gate every downstream per-file signal, not just decide targeted-vs-full-set routing.
- **A model that already knows the right answer in a clean prompt can still get it wrong in the real noisy retry loop.** Don't assume a wrong answer means a knowledge gap - test the same question in isolation before concluding the model needs more capability (reasoning, a bigger model, live lookup). Often the fix is making the prompt say the right thing more clearly, not giving the model more power.
- **Test capability claims at realistic scale, not on a toy task.** Tool-calling reliability that looked solid (3/3) on a tiny Stack-class task collapsed completely on a realistically-sized file. Any "is X reliable" check needs to match the real workload's shape (size, complexity), or the result doesn't transfer.
- **Verify a regression test actually fails pre-fix, every time - a passing-for-the-wrong-reason test is a real, recurring risk.** Caught more than once: a test that looked like it validated a fix instead passed on both old and new code because of an unrelated mocking gap. `git stash` + confirm the failure mode matches the bug, every time, no exceptions.
- **Environment/toolchain mismatches are easy to re-discover from scratch - check memory before re-diagnosing.** JAVA_HOME/JDK version drift has bitten multiple times; the fix each time was already recorded from a prior session.
- **Real, live validation surfaces bugs that a fully-mocked test suite structurally cannot.** Nearly every significant bug found this whole effort came from an actual end-to-end run against real local models and real tools, not from the (extensive, always-green) mocked test suite. Mocked tests verify the code does what it's supposed to do; live runs verify the code's assumptions about the outside world are correct.
- **A "durable fact injected into the prompt" is a proven, reusable pattern** (skills, toolchain facts, dependency checklists) - reach for this shape again before inventing something new when the problem is "the model doesn't reliably know/apply X."
- **Structural/deterministic grounding beats more or better prompting for some error classes.** Real research (2026-08-03) found production coding agents increasingly favor deterministic tools - LSPs, linters, the compiler's own lint flags - over bigger models or cleverer prompts for catching import-path and type mistakes specifically. Matches this session's own evidence: a reasoning model gave zero benefit over prompting for a fact-recall error, and a prose skill rule stated verbatim in every prompt still didn't stop a recurring wrong-import mistake. When a mistake is the kind a compiler/tool could verify with certainty, reach for that before reaching for a smarter/slower model.
- **Lower temperature, not higher, for a stuck retry.** Counter to intuition, cited research found code-gen success rate drops as temperature rises even within a low range - "add randomness to shake it loose" is not supported by evidence.
