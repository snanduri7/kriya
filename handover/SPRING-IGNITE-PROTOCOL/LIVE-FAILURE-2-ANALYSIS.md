## 3. First wrong decision and ownership
- **Whole-run first wrong decision: the model's** (attempt 1 `ProtocolParser.java` accesses `protocol.body` etc. although `Protocol` declares them private and offers getters). Kriya's rejection (compile gate), attribution (locator, high, correct file) and first retry target (the parser) were all correct.
- **First KRIYA-owned wrong decision: the attempt 2 -> 3 retarget (KRIYA_FAILURE_ATTRIBUTION_GAP).** Mechanism (TRACED + CONFIRMED by replay): `kriya/workflow/attribution.py::extract_self_diagnosed_files` takes the model's free-text FIX ANALYSIS and treats **any known file whose name occurs in the prose, other than the file the analysis is attached to,** as "the model names a different real cause"; the `self_diagnosis` tier then ranks above the compiler locator (`attribution.py` "most-trusted first"; gated only by failure signature + attempt number in `retry_strategy.py:951-957`, where an edit-protocol failure's signature collapses onto the authoritative failure it was repairing). The analysis attached to the parser said that the parser could not see "the private fields of the `Protocol` class"; that mention became `likely_files [Protocol.java]`. Control (replay): an analysis that only quotes the compiler message ("body has private access in Protocol") yields `[Protocol.java]`; one that names no other file yields `[]`; the real-redirect sentence also yields `[Protocol.java]`, i.e. the extractor cannot tell a mention from a diagnosis. The redirect target was also factually wrong: the staged `Protocol.java` has `getProtocolVersion/…/getBody` and setters (MEASURED, candidate blob).
- **Decisive Kriya defect: candidate atomicity (OTHER_GENERIC_KRIYA_DEFECT).** A repair attempt is a unit: when one file's response violates the single-file contract, every file's proposal in that attempt is recorded REFUSED with that reason, including a syntactically and semantically valid edit for the file the compiler actually blamed. Attempt 3 therefore threw away a correct, compiling fix; attempt 4 never evaluated one.
- **Contributing, KRIYA_GENERATION_BUDGET_POLICY_GAP:** the 900 s deadline is a single run-wide clock started at the first model call that includes planning and the owner's review wait (section 7). It ended the run before the fallback pass.
- **Contributing, context shape (model fabrication with a Kriya share):** the attempt 2 request showed `ProtocolParser.java` only as two member excerpts (`member_exact`, lines 8-45) and not the class header; the model nevertheless wrote a whole-file anchor and invented the header javadoc. Attempts 3 and 4 showed the whole 46-line file.
- **Ruled out:** KRIYA_VALIDATION_FALSE_POSITIVE (javac confirms the six errors on the attempt 1 file); KNOWLEDGE_TO_DEVELOPER_GAP (section 4); DEPENDENCY_OFFLINE_RESOLUTION_GAP / RUNTIME_ENV_GAP (section 6); KRIYA_WORK_UNIT_GRANULARITY_GAP (section 5).
- **Primary classification of the repair failure: KRIYA_FAILURE_ATTRIBUTION_GAP** (first Kriya-owned wrong decision), with the atomicity defect as the reason it became terminal. Evidence strength: the mechanism and the discarded-valid-fix are CONFIRMED by deterministic replay; that attempt 3's fix would have gone on to pass *all* later gates is INFERRED (compile only was replayed).

## 7. Why `generation_budget_exhausted`
TRACED (`attempt.py::_ensure_generation_time_budget`, `workflow.py:2825`, `run_coordinator.claim_run_generation_clock`): the budget is `autonomy.generation_time_budget_seconds` (900 here, the unchanged Demo setting); its clock is the run-wide monotonic start of the **first model call (the first planner call)** and is never reset by a unit, retry or role; all five attempts belonged to the same unit; best-of-N is off (`best_of_n_first_attempt` 1). Before a generation pass Kriya requires `remaining >= estimate + 120 s gate reserve`; the estimate is `median(observed seconds per file for the ACTIVE model) x files`, falling back to the configured 90 s per file when that model has no timings. `qwen3.6` had none, so a 2-file pass was estimated at 180 s + 120 s = 300 s against 226.8 s remaining. Where the 673.0 s went (`budget-timeline.txt`, from the log): planning 77.9 s; attempt 1 generation 129.6 s; reviewer + static checks 20.2 s; **owner source review 128.5 s**; gates 6.3 s; attempt 2 49.5 s; attempt 3 85.6 s; attempt 4 174.0 s (of which one call of about 140 s). Findings: retries consumed budget whether or not they made progress (the progress classifier ended at NO_PROGRESS x2, which triggered the fallback; it did not shorten anything); the failure family changed type each attempt (compile, anchored_edit, operation_contract, anchored_edit) so the "new failure family" budget reset logic was reached once; **the human review wait is inside the budget** (without it, 355.5 s would have remained and the fallback pass would have started); policy intentionally keeps the primary model until two consecutive no-progress attempts, then tries one fallback-targeted pass, which is what happened. Whether Kriya should have stopped earlier: under the current policy no. Whether the budget policy is right: it is a **modularization / product backlog item, not changed here** (documented intent in `config.py`: an end-to-end deadline for harnesses with an outer timeout; it has no notion of human-wait time). One more wasted call: the fallback model's only request attributed Kriya's own budget notice to a source file.
