## Gap A - declining REQUIRED runtime verification was reported as success

- **Root cause (TRACED, CONFIRMED by the reproducer):** both runtime call sites in `attempt.py` checked "required and declined" only on entry to the gate; the decline is recorded later in the same call (`run_verification_declined = True`) and execution fell through. The structured plan was saved by the pre-apply `REQUIRED VERIFICATION UNRESOLVED` catch-all, which the direct plan's empty `required_verification` does not feed.
- **Fix:** one helper `_raise_if_required_runtime_verification_declined` (existing `REQUIRED_RUNTIME_VERIFICATION_DECLINED` typed `verification_infrastructure_failure`, STOP_ENVIRONMENT, no Developer retry), used on entry and immediately after a decline is recorded, at both sites. OPTIONAL checks keep declined-and-skipped semantics (pinned).
- **Final semantics:** required + Reject -> not executed, not success, not applied, `ApplicationOutcome` NOT_APPLICABLE with `blocked_reason_code` = the refusal code; runtime failure -> not success; slow decision = waiting; wrong review kind fails closed.
- **Structured-plan change (flagged, not hidden):** its Reject now stops at the typed `REQUIRED_RUNTIME_VERIFICATION_DECLINED` at the verification unit instead of reaching the pre-apply catch-all. Terminal result unchanged (not success, nothing executed); the recorded reason is more specific and `application_outcome` already had a `blocked_reason_code` slot for exactly this code that the catch-all never filled. `test_reject_is_the_explicit_refusal_*` was updated accordingly.
- **Mutations:** M1 (no post-decline call, direct), M2 (no post-decline call, verification-only), M3 (ignore `required`), M4 (ignore `declined`): all killed.

## Gap B - runtime review/execution preceded the source review
- **Reproducer (MEASURED, failed pre-fix):** `[runtime_command, change_approval]` order; source Reject still raised the runtime review; a candidate tampered after approval was caught only by the later terminal binding, AFTER the commands ran.
- **Check 1 (TRACED):** approve-then-verify-then-apply is already how the direct path works (the change approval precedes the full regression suite; a regression failure `raise QualityGateFailure` re-enters the retry loop and the next iteration asks approval again). Moving runtime execution next to the regression suite does not change what source approval means; stop condition 2 does not fire.
- **Check 2 (TRACED):** the `change_approval` `candidate_digest` is a hash of the per-file DIFF text; `_bind_direct_candidate` / `state.verified_candidate_binding` is a hash of the worktree BYTES plus base revision (the same binding the terminal commit refuses on). They are different functions of the same candidate; no parallel identity was invented. Source continuity is carried by the existing byte binding, checked right after approval, immediately before execution and after it. The runtime review's `candidate_digest` binds commands, not source (unchanged).
- **Design:** `_approve_and_execute_runtime_verification` (extracted unchanged from `run_attempt`, mechanical: its only free locals were `state, ctx, validator, active_code_context, judgment, autonomy_cfg_rv`). When the attempt wrote source in human-in-the-loop mode with an approver (`_defer_runtime_execution_until_source_review`), it is held in `ctx.deferred_runtime_verification` and run in `workflow.py` right after the source approval. The judge, grounding and the fail-fast required checks still run first (none executes the candidate). Self-correction (edits files) is off after approval; a failing run goes to the ordinary retry loop whose new candidate is reviewed again. The required-verification check waits only for runtime-execution requirements and re-runs complete after the deferred step; the `candidate_gates_passed` checkpoint is saved after it (a resume can never skip an unrun runtime check); `run_attempt` clears any held execution on entry (Best-of-N); an unasked review fails closed. Other autonomy modes, verification-only units and no-approver runs are unchanged.
- **Final order:** candidate generated -> build/tests (isolated worktree, as before) -> requirements, static analysis -> exact multi-file source review -> approve -> runtime review -> execution of the same bytes in the isolated worktree -> terminal regression -> apply the same bytes.
- **Mutations:** B1 never-defer, B1b defer outside HITL, B2a/b/c (in-gate, pre, post byte checks), B3 self-correction after approval, B4 unasked-review fail-closed, B5a/b required-filter, B6 post-deferral required check, B7 early checkpoint, entry reset: all killed. B1c (forced Best-of-N=1) survived and was REMOVED as redundant; the real hazard (a stale held execution) is covered by the entry reset, which has its own killed mutation.
- **Interpretation to confirm (review-first rule):** the brief's Gap B invariant bans RUNTIME execution before source review. Its Phase 6 sequence lists compile/tests after source approval. Build and tests still run before the source review (both plan shapes, today; the reviewer evidence depends on them). Moving them is a larger change to a different invariant; not done.
- **Behavior note:** the pre-approval Reviewer no longer sees the runtime outcome (it does not exist yet); it still sees compile and test evidence.

A deterministic closer (for example: the quoted literal appears in the captured stdout of the exact approved commands run on the exact approved bytes) is a NEW closer with new semantics (it can over-claim: "prints X on error", multi-case requirements) - an owner design decision, not a patch. Registered as `REQ-LEDGER-RUNTIME-CLOSURE-001` (P2, target_scope set).
