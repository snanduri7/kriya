## Gap A - declining REQUIRED runtime verification was reported as success
- **Reproducer (MEASURED, failed pre-fix):** direct plan, required runtime obligation, runtime review Rejected -> nothing executed, `_succeeded` true, change applied (`test_gap_a_rejecting_the_required_runtime_review_is_not_success_and_applies_nothing`).
- **Root cause (TRACED, CONFIRMED by the reproducer):** both runtime call sites in `attempt.py` checked "required and declined" only on entry to the gate; the decline is recorded later in the same call (`run_verification_declined = True`) and execution fell through. The structured plan was saved by the pre-apply `REQUIRED VERIFICATION UNRESOLVED` catch-all, which the direct plan's empty `required_verification` does not feed.
- **Fix:** one helper `_raise_if_required_runtime_verification_declined` (existing `REQUIRED_RUNTIME_VERIFICATION_DECLINED` typed `verification_infrastructure_failure`, STOP_ENVIRONMENT, no Developer retry), used on entry and immediately after a decline is recorded, at both sites. OPTIONAL checks keep declined-and-skipped semantics (pinned).
- **Final semantics:** required + Reject -> not executed, not success, not applied, `ApplicationOutcome` NOT_APPLICABLE with `blocked_reason_code` = the refusal code; runtime failure -> not success; slow decision = waiting; wrong review kind fails closed.
- **Structured-plan change (flagged, not hidden):** its Reject now stops at the typed `REQUIRED_RUNTIME_VERIFICATION_DECLINED` at the verification unit instead of reaching the pre-apply catch-all. Terminal result unchanged (not success, nothing executed); the recorded reason is more specific and `application_outcome` already had a `blocked_reason_code` slot for exactly this code that the catch-all never filled. `test_reject_is_the_explicit_refusal_*` was updated accordingly.
- **Mutations:** M1 (no post-decline call, direct), M2 (no post-decline call, verification-only), M3 (ignore `required`), M4 (ignore `declined`): all killed.

## Gap B - runtime review/execution preceded the source review
- **Reproducer (MEASURED, failed pre-fix):** `[runtime_command, change_approval]` order; source Reject still raised the runtime review; a candidate tampered after approval was caught only by the later terminal binding, AFTER the commands ran.
- **Check 1 (TRACED):** approve-then-verify-then-apply is already how the direct path works (the change approval precedes the full regression suite; a regression failure `raise QualityGateFailure` re-enters the retry loop and the next iteration asks approval again). Moving runtime execution next to the regression suite does not change what source approval means; stop condition 2 does not fire.
- **Check 2 (TRACED):** the `change_approval` `candidate_digest` is a hash of the per-file DIFF text; `_bind_direct_candidate` / `state.verified_candidate_binding` is a hash of the worktree BYTES plus base revision (the same binding the terminal commit refuses on). They are different functions of the same candidate; no parallel identity was invented. Source continuity is carried by the existing byte binding, checked right after approval, immediately before execution and after it. The runtime review's `candidate_digest` binds commands, not source (unchanged).
- **Design:** `_approve_and_execute_runtime_verification` (extracted unchanged from `run_attempt`, mechanical: its only free locals were `state, ctx, validator, active_code_context, judgment, autonomy_cfg_rv`). When the attempt wrote source in human-in-the-loop mode with an approver (`_defer_runtime_execution_until_source_review`), it is held in `ctx.deferred_runtime_verification` and run in `workflow.py` right after the source approval. The judge, grounding and the fail-fast required checks still run first (none executes the candidate). Self-correction (edits files) is off after approval; a failing run goes to the ordinary retry loop whose new candidate is reviewed again. The required-verification check waits only for runtime-execution requirements and re-runs complete after the deferred step; the `candidate_gates_passed` checkpoint is saved after it (a resume can never skip an unrun runtime check); `run_attempt` clears any held execution on entry (Best-of-N); an unasked review fails closed. Other autonomy modes, verification-only units and no-approver runs are unchanged.
- **Final order:** candidate generated -> build/tests (isolated worktree, as before) -> requirements, static analysis -> exact multi-file source review -> approve -> runtime review -> execution of the same bytes in the isolated worktree -> terminal regression -> apply the same bytes.
- **Mutations:** B1 never-defer, B1b defer outside HITL, B2a/b/c (in-gate, pre, post byte checks), B3 self-correction after approval, B4 unasked-review fail-closed, B5a/b required-filter, B6 post-deferral required check, B7 early checkpoint, entry reset: all killed. B1c (forced Best-of-N=1) survived and was REMOVED as redundant; the real hazard (a stale held execution) is covered by the entry reset, which has its own killed mutation.
- **Superseded 2026-10-15 (owner decision 2):** the runtime-only form above was not strong enough for Desktop HITL because build and tests execute model-authored artifacts. See "Continuation" below for the stronger ordering that is now implemented.
- **Behavior note:** the pre-approval Reviewer no longer sees the runtime outcome (it does not exist yet); it still sees compile and test evidence.

### Decision 2 - stronger Gap B: nothing executes before the source review succeeds
- **Characterization (MEASURED, failed pre-change, 7 of 9 new tests):** build, POM validation, tests and the PRD-020 requirement closers (which run the candidate's tests) all ran BEFORE the source review; the same on the structured plan (`test_gap_b_structured_plan_builds_and_tests_each_unit_only_after_that_unit_s_source_was_approved` failed too). The generic owner point is `run_attempt` / `run_generation_workflow`, shared by every unit.
- **Fix:** `run_attempt` is split at the first executing gate. Non-executing checks (completeness, static rules, stack contract, then in workflow.py static analysis and the semantic-safety gate) still run before the review. Everything that executes - POM validation (`mvn validate` runs Maven on a model-authored pom), compile, tests, the runtime verification and the gates that judge after them (migration, spec compliance) - moved unchanged into `_run_executing_candidate_gates` / `_run_pom_validation_gate`; in HITL with an approver and written source they are held in `ctx.deferred_executing_gates` and run right after the approval. The PRD-020 requirement closers are a nested `_close_and_check_requirements` called at their original place otherwise, and after the deferred gates when held.
- **Order now (HITL):** candidate generated -> non-executing checks -> source review -> approve -> byte check -> POM validation -> build -> tests (byte check before them) -> requirement closers -> runtime judge -> byte check -> runtime-command review -> native confirmation -> byte check -> execution -> byte check -> terminal regression -> apply the same bytes. Source reject: nothing built, tested or reviewed for runtime, nothing applied.
- **Identity:** the existing byte binding (`state.verified_candidate_binding`, `bind_candidate`) is compared at: right after approval, before the tests, before the runtime review, immediately before execution, and after the deferred gates. The diff-text `candidate_digest` is not used as byte identity. A drift is `CANDIDATE_CHANGED_AFTER_SOURCE_REVIEW` (or the pre-existing `WORKTREE_CONTENT_MISMATCH` / `VERIFICATION_GATE_MUTATED_TRACKED_FILES`, which fire first for a changed written file); the guard before the compile was removed as redundant with `tree_binding.check("pre_compile")` (its mutant could not be killed).
- **Self-correction off after approval:** all candidate-editing micro-loops (compile, test, targeted-test repair, runtime) are gated on the approval guard; a failing gate goes to the ordinary retry loop whose new candidate is reviewed again.
- **Source-approval presentation:** the reason (policy note, before the reviewer's section) states "Pre-checks passed: expected files present, static rules, stack contract. Nothing has been built, tested or run yet. Build and tests: will run after you approve. Running the application: you will be asked separately before any command runs." No pending check is shown as a pass.
- **Required verification:** only requirements that the executing gates resolve (builtin compile/test tools, a judgment needing runtime execution) wait; any other unresolved requirement still stops the run before the review. The complete check re-runs after the deferred gates. The `candidate_gates_passed` checkpoint is saved after them, so a resume cannot skip an unrun gate. `run_attempt` clears any held execution on entry (Best-of-N).
- **Mutations (all killed; two removed as redundant):** never-defer, defer outside HITL, POM not deferred, guards before tests / runtime review / execution / after, self-correction allowed in compile / tests / repair-loop / runtime, closers not deferred / dropped after deferral, required-check dropped / filter variants, checkpoint saved early, unasked-review fail-closed, entry reset. Removed as redundant: forced Best-of-N=1 (the entry reset is the real protection), the guard before the compile (see above).
- **One existing test changed meaning:** `tests/test_workflow.py::test_workflow_terminal_regression_failure_is_not_reported_or_applied_as_success` scripted the model calls in the old order (attempt 2 failed at compile before any second review). Under the intended behavior attempt 2's source is reviewed first, so the script gained that review and the final review is attempt 2's own (still fresh, never attempt 1's). 1 test of 3126 in the wide run.
- **Behavior notes (flag to the owner):** in HITL a candidate that does not build is now shown to the person before that is known (previously they never saw it); the pre-approval Reviewer sees no build/test/runtime evidence; the requirement closers, spec compliance and migration checks follow the approval.
