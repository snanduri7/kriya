### F2 addendum: secondary finding REPAIR_FEEDBACK_SEMANTICS_GAP, and the generic fix (owner decision, 2026-10-14)
**Measured behaviour.** The validator correctly rejects an unprovided `requires_capabilities` entry. The repair feedback only said the plan "does not declare that capability in requires". For an external environment dependency that is incomplete and misleading: it never says the entry should not be a subtask capability at all, and adding it to `requires` produces `SUBTASK_REQUIREMENT_UNPROVIDED`. The plan model already had the valid representation, `environment_requirements`.
**Generic distinction (repository terminology, no new field).** INTER-SUBTASK CAPABILITY: supplied by another planned subtask -> `requires_capabilities`. EXTERNAL ENVIRONMENT DEPENDENCY: a library, package, runtime or tool supplied by the project or execution environment -> `environment_requirements`.
**Change 1, contract (one shared sentence).** `kriya/agents/contracts.py::ENVIRONMENT_DEPENDENCY_RULE`: "A library, package, runtime or tool that the project or execution environment supplies, rather than another planned subtask, is an environment dependency: declare it in planned_files[].environment_requirements, not in requires_capabilities or in subtask requires/provides." It is defined once and included by the three independently generated Planner contracts (the structured Planner system prompt and its user-message protocol in `workflow_controller.py`, and the Planner agent's system prompt in `agent.py`). No technology, language, package manager or scenario is named.
**Change 2, deterministic repair feedback.** `planner_repair.py`: `unprovided_capability_facts` (typed facts read from the previous plan: capability, consumer subtask, consumer file; skips capabilities some planned subtask provides and the validator's exempt ambient tools) and `format_unprovided_capability_feedback`, emitted for `PLANNED_ARTIFACT_PREREQUISITE_UNDECLARED` / `SUBTASK_REQUIREMENT_UNPROVIDED`. It states the boundary and the three valid repairs (reference an existing provided capability; add the missing provider; if it is an environment dependency, move it to `environment_requirements`) plus that adding it to `requires` without a provider is not a repair. It does not choose a branch.
**Validator unchanged (CONFIRMED).** `plan_validation.py` has a zero-line diff. Characterization tests that pin acceptance: the recorded bad plan is still rejected; an invented capability and seven package-like names are still rejected; a capability a planned subtask provides is accepted; external dependencies in `environment_requirements` are accepted; `python`/`pytest` stay exempt.
**Tests.** `tests/test_plan_external_package_capability_001.py`: 30 tests, written before the change (collection failed on the missing symbols); 9 mutants of the new logic all killed (feedback facts, gate by reason code, repair 3, dead-end warning, the rule missing from each of the three contracts, a technology name in the rule). 1,037 existing planner / plan-validation / repair / prompt tests pass. `ruff check .` clean.
**Replay of all six recorded bad plans, no model (MEASURED).** All six are STILL rejected (two runs x three attempts: reason codes unchanged), each now produces the typed block (`capability="tree-sitter-python"` is plan data, the template text names no technology), and applying repair 3 mechanically to each recorded plan validates it (the only exception keeps an unrelated reason code, `SUBTASK_GLOBAL_INVARIANTS_MISSING`, that the repair prompt handles separately).
