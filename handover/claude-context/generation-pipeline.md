# Generation pipeline, unified execution plans (PRD-008A), static analysis gate (PRD-031A)

_Moved verbatim from CLAUDE.md on 2026-10-07 (loaded on demand, not every session). Read before modifying any module named here. Code is ground truth; update this file when behaviour changes._

### The generation pipeline (`kriya/workflow/workflow.py`)
`WorkflowEngine.run_generation_workflow` is the core orchestration and is long/stateful by design — read it end-to-end before modifying, don't assume a stage is isolated:
1. **KnowledgeGuard stage 0** (`kriya/tools/knowledge.py`) — scans the goal text for library/version mentions that postdate the configured knowledge cutoff and can short-circuit the whole run with a `knowledge_gap` status requiring explicit confirmation (`--yes`, `--knowledge-policy`, `--ack-knowledge-gap` in the CLI).
2. **Repository analysis** via `RepositoryAnalyzer` (`kriya/analyzer/analyzer.py`) plus **skill matching** via `SkillEngine` (`kriya/skills/skill.py`) — skills activate based on repo facts (dependencies/frameworks detected in analysis) or goal-text/tag matches, not just keywords, and respect `supported_versions` ranges.
3. **Graph RAG retrieval**: hybrid vector+lexical query (`kriya/memory/vector.py::LocalVectorStore.query_hybrid`, reciprocal rank fusion over a brute-force Python/NumPy cosine-similarity scan of BLOB-serialized embeddings in a plain SQLite `vector_chunks` table — no `sqlite-vec` extension is loaded anywhere — plus FTS5 lexical search) finds seed files, then `kriya/analyzer/graph.py::DependencyGraph` expands to a bounded neighborhood, each hit scored by relation-type weight over hop distance; results are assembled into a token-budgeted context string via `build_code_context`, which degrades the lowest-scored matched/related files first through skeletonization tiers (full → skeleton → signatures) when over budget. The stage lives in `kriya/workflow/graph_retrieval.py::retrieve_graph_context` (PRD-027). It queries with the real embedding dimension, uses a term-based BM25 lexical leg, and seeds the graph walk with the seed files as well as their symbols. Seeds come from `select_expansion_seeds` (PRD027-PRECISION-001): when both legs have valid top_k hits, only hits ranked within top_k by both seed (none when they disagree: `NO_CORROBORATED_EXPANSION_SEED`, never a fallback to every hit); when only one leg has valid hits, that leg's top_k seeds. Every hit stays matched and packaged either way, and the run records a `retrieval.expansion_seeds` event. File scores are ranked in explicit evidence tiers (`evidence_scores`, PRD027-SCORE-NORMALIZATION-001): each class normalized by its own best score into (0, 1], direct query hits then in (1, 2] (`DIRECT_EVIDENCE_TIER`), graph-expanded files in (0, 1] - so a binding budget degrades/omits graph expansion before any file the query itself matched (raw RRF <=0.033 vs relation weights 0.5-1.0 used to invert that). `index_implementation_digest` covers the whole graph_retrieval module and every context-assembly step (`build_code_context_package`, `_build_file_tiers`, `_omit_over_budget`, the skeletonizers, `estimate_tokens`). The walk reports a file-sourced relation's calling file (so callers are reached), walks a reached definer's own relations (so two-hop dependencies are reached), and returns one best entry per file before the cap. `kriya/workflow/context_certification.py` measures exactly this path against fixed per-class recall targets and a precision target (`kriya context certify`; CI uses a deterministic hashing embedder for mechanics only). `doctor --production` reads the stored record.
4. **Untrusted learned-knowledge RAG (KNOWLEDGE-READPATH-001)**: anything ingested via `kriya learn` is read ONLY through `kriya/memory/learned_knowledge.py` (`web_knowledge.db`/`learned_knowledge`, rows of the configured embedding model only), once per run by the `generate` CLI from the user's own goal (a milestone plan's `original_goal` for `--from-milestones`), and handed in as `reference_context`; `run_generation_workflow` never queries a knowledge store itself. It is wrapped in explicit "Begin/End Untrusted Reference Context" fencing (`kriya/workflow/untrusted_context.py`; marker lines inside the body are neutralized) with an instruction not to treat it as commands, and reaches Planner/Architect via `convention_prompt` and the Developer via the budgeted `learned_rag_context` slot (trimmed at whole entries to what the PRD-016 graph pool leaves, `context_budget.developer_reference`, at every Developer assembly site - optional untrusted text is never the reason a Developer request is refused) — preserve this fencing if you touch that code path, it's a prompt-injection mitigation, not incidental formatting. Checks for Kriya's own prompt sections (the skill-conventions reminders) read `outside_untrusted_reference(...)`, never the raw prompt. Never join retrieved, learned, Planner or tool text to `goal`/`grounding_goal`/`original_goal`: those are the only source of requirement, mutation-scope, contract and expected-exit authority (AUTH-GOAL-CONTAMINATION-001, a structural test in `tests/test_auth_goal_contamination_001.py`).
5. **Developer + Quality Gates loop**: runs inside an isolated, reused git worktree (`.kriya/worktree`, created/reset by `create_git_worktree`) so compile caches survive across retries. A candidate workspace's worktree (the subtask engine inside the enforce plan worktree) is a sibling, `.kriya/worktrees/<name>`, rooted at the run's canonical workspace (`run_coordinator.candidate_workspace_root`), never inside another managed worktree (`NestedWorktreeError`); only `kriya/workflow/worktree.py` decides worktree locations (WORKTREE-CANONICAL-ROOT-001). The developer agent (`kriya/agents/agent.py::DeveloperAgent`) either returns full file contents or anchored search/replace `edits` (applied via `apply_anchored_edits` -> `kriya/workflow/file_integrity.py`: complete-line blocks matching **exactly once** in one raw-byte snapshot, never straddling skeletonized/elided content; see File integrity below). `PolymorphicValidator` (`kriya/tools/validate.py`) auto-detects the target stack from real markers (Java via pom.xml/build.gradle, Ruby via Gemfile/Rakefile/spec, Python via requirements.txt/pyproject.toml/setup.py/setup.cfg/Pipfile/any .py file present) and runs compile checks then targeted tests before a full regression run (the candidate gate also runs the repository's suite when the stage's `required_verification` declares a test/tests/regression verifier and no target test or written test file selected one - `attempt._declares_test_verification`). Anything matching none of those markers is `"unknown"`, not a silent Python fallback — `run_compile_check`/`run_tests` return `success: True` (so the retry loop doesn't fail forever on a gate that can never run) but say plainly that nothing was actually validated, rather than falsely claiming a Python check passed against zero matching files. On failure the loop retries (bounded by `max(4, 1 + len(llm_chain))`), escalating through `config.llm_chain` fallback models and re-running the context budget allocator against each fallback's own `context_window`.
6. **Human approval gate**: triggered by `autonomy.mode == "human-in-the-loop"` (the closed vocabulary is `guardrails` / `human-in-the-loop`; any other value is a typed configuration error, S16a), a sensitive-path match, or diff size exceeding `autonomy.risk_threshold_lines`; only after approval are worktree changes copied into the real workspace.
   **Approval outcome contract (N1/F4, Wave 1 closure; `kriya/policy/approval.py`).** The general approval callback `callback(files, reason)` answers with one closed `ApprovalOutcome`: `APPROVED`, `DECLINED` (a person, or the terminal prompt, said no) or `UNAVAILABLE` (nobody was asked or nobody decided), each with a reason code from the closed table `APPROVAL_REASON_CODES` (`APPROVAL_GRANTED`, `APPROVAL_DECLINED`, `APPROVAL_LAUNCH_CANNOT_ASK`, `APPROVAL_REVIEW_EXPIRED`, `APPROVAL_DECISION_NOT_RECORDED`, `APPROVAL_RESULT_UNRECOGNIZED`). A legacy `bool` stays accepted (True -> APPROVED, False -> DECLINED); anything else (None, a number, a mock, a still-unresolved awaitable) is UNAVAILABLE, never read through truthiness. `ApprovalOutcome` has NO truth value (`bool()` raises) so no site can write `if approved:` on it. EVERY authority site resolves the answer through the one owner (`resolve_approval` / `resolve_approval_result`, which await any awaitable - coroutine, Task, Future - and let a callback exception propagate to the caller's own fail-closed policy): the change gate (`stage_apply`), Stage 2A, contract escalation (`spec_compliance`), the policy REQUIRE_APPROVAL path and the live-lookup egress approval (`workflow.py`), the live-lookup reference review (`stage_analysis`/`stage_architecture`) and the legacy runtime-command fallback (`approval.ask`, which binds the subject fingerprint only to an APPROVED outcome). A callback that supplies CONTENT (skill gap / skill conflict) is not an approval and only uses `await_if_awaitable`. A desktop launch answers UNAVAILABLE (`cli._approval_decision`) for a decision it cannot put to a person, and its review wait (`launch_approval.await_decision`) answers DECLINED only for a durable rejection by the person; an expired or abandoned review is UNAVAILABLE. At the change gate DECLINED stays the `human_rejected` stop; UNAVAILABLE is the existing `approval_required` stop ("approval required and not available"), recorded on the `approval.decision` event with its `reason_code`. Stage 2A ends the unit the same way, as a RESULT and not an exception (Wave-1 final fix-forward 1-E): DECLINED -> `status: human_rejected`, UNAVAILABLE -> `status: approval_required` (with the reason code in `reason`), both with `quality_gates_passed: False`, `files: []` and a short trace row of the same status, before any Developer work; the enforce loop reads such a result as a failed subtask and stops. `ApprovalDecision` itself also has no truth value (`bool()` raises, 1-F), so `if outcome.decision:` cannot read a decline as approval. Contract escalation maps DECLINED -> `CONTRACT_ESCALATION_DECLINED` and UNAVAILABLE -> `CONTRACT_ESCALATION_UNAVAILABLE`. Pinned by `tests/test_n1_f4_approval_outcome.py` (resolver, every awaitable shape, runtime-command fallback, egress, structural tripwire) and the per-site tests named there.
7. **Lesson extraction**: when a fallback-model escalation resolves an error, a one-sentence rule is extracted and staged into `skills/auto-<repo-slug>/staged_rules.txt` (promoted to `rules.txt` via `kriya skills approve`).
8. **Reviewer + trace log**: final review pass (a PRD-016 refusal of it is `failure_category: final_review_refused`, never SUCCESS and never a raw exception; `final_review_refusal` reports the applied and committed state, nothing is rolled back - PROMPT-BUDGET-FIT-001C), then a run trace (plan, retries, gate outcomes, retrieved chunks, model hops) is persisted via `kriya/core/trace.py::TraceLogger` to `trace_db_path(cfg)` (`<state dir>/traces.db`) (viewable with `kriya traces`).

### Unified execution plans (`kriya/workflow/execution_plan.py`, `plan_adapters.py`, `plan_executor.py`) — PRD-008A
A direct goal and a milestone sequence both run as an immutable `ExecutionPlan` of `WorkUnit`s through ONE executor, `plan_executor.execute_plan()` (direct = exactly one unit; milestones = one unit per milestone + an INTEGRATION unit, replay as the plan-wide phase before it). `run_generation_workflow(work_unit=None)` treats the call as a new intent and wraps it in a one-unit plan; anything executing a unit of an outer plan MUST pass its typed `WorkUnitInvocation` (the milestone driver and the enforce subtask loop do) - a new intent started inside a running unit raises `NestedExecutionPlanError`. The executor owns ordering, WorkUnit lifecycle (`RunRecord.execution_plan`/`work_unit_states`), the active work-unit record (commit/checkpoint attribution), WorkUnit-aware checkpoint selection (`select_work_unit_checkpoint`), completion reuse (only PRD-008 S4b/S4c-validated units; incoherent reuse fails closed) and the terminal decision (SUCCESS only when every unit is VERIFIED; the RunCoordinator enforces the same). A `PlanDriver` supplies source-specific bookkeeping only - never a safety decision. `source_kind` is provenance, never a switch between safety implementations. Unit digests/records are byte-compatible with pre-PRD-008A checkpoints and proofs. The enforce-mode structured subtask loop is not yet executed by `execute_plan()` (STRUCTURED is provenance only). See `docs/design.md` §2.9a. **Enforce terminal (PRD-030):** `_run_structured_enforce` calls `TerminalGateService` (`kriya/workflow/terminal_gate_service.py`; typed `TerminalGateReport`, gates in fixed order, a raising gate fails, never writes the real workspace) and `commit_service.commit_verified_candidate` (only a commit-eligible report; wraps `terminal_commit`). The gate validators are passed in as `TerminalGateValidators` built from `workflow_controller`'s own names, so tests that patch `kriya.workflow.workflow_controller.<validator>` still reach them; keep that binding if you move code. The services never import the controller (`tests/test_prd030_terminal_services.py`); see `docs/design.md` §2.9b.

**Verification binding (CANDIDATE-VERIFIED-DIGEST-BINDING-001):** `commit_terminal_candidate(verified_candidate=)` is required. It recomputes `verification_binding.bind_candidate(writes)` before anything else and refuses a missing or different binding (`VERIFIED_CANDIDATE_EVIDENCE_MISSING`/`_STALE`) with nothing written, whatever static analysis says; the refusal is the deterministic `workspace_commit_failed` stop. Bindings are taken by enforce in `TerminalGateService.run` before the first gate (`TerminalGateRequest.commit_batch`) and by direct/milestone right after `run_attempt` (`state.verified_candidate_binding`). Tests that commit directly pass `bind_candidate(writes, workspace)`. **Attempt recovery/verification (PRD-031):** `retry_strategy.handle_attempt_failure` is a wrapper over `RecoveryCoordinator` (`kriya/workflow/recovery_coordinator.py`: classify the exception -> `_record_attempt_failure` (injected, unchanged recording) -> `conclude_attempt_failure`, which defers to `retry_policy.decide_for_state`); `attempt._run_verification_only_attempt` runs its declared verifiers through `VerificationCoordinator` (`verification_coordinator.py`, runtime verifier injected). Neither coordinator may import attempt/retry_strategy/workflow/workflow_controller (`tests/test_prd031_coordinators.py`); see §2.9c.

### Static analysis gate (`kriya/static_analysis/`) — PRD-031A
Provider-neutral and off by default. `StaticAnalysisService` is the ONE gate, called at BOTH commit boundaries: the enforce `TerminalGateService` (gate 4 of 7, before terminal_obligations; injected as `TerminalGateValidators.evaluate_static_analysis` from the controller's own `StaticAnalysisService` name) and the direct/milestone pre-apply boundary (`workflow._run_static_analysis_gate`, before approval).

- **Layering.** `kriya/workflow` imports only `static_analysis.service`/`model`. Only `static_analysis/adapters/` may name a provider; a tripwire rejects the word "semgrep" anywhere else in `kriya/`. Policy is Kriya's: adapters never import policy, service or waivers.
- **Commit binding.** `commit_terminal_candidate` has a REQUIRED `static_analysis=` guard, built only by `service.commit_guard(cfg, result)`. Whether evidence is required comes from config (`analysis_enabled`: exactly `enabled is True`; a missing section = disabled). It refuses evidence that is missing, not permitting, or stale in the batch, base scope, scope plan, runtime/rule packs (`port.runtime_fingerprint()`) or settings. Tests that are not about static analysis pass `tests/_fake_static_analysis.py::DISABLED_STATIC_ANALYSIS`.
- **Stops.** A blocked direct run is a deterministic stop (`static_analysis_blocked|unknown|unavailable` in retry_strategy's stop set), never a Developer retry. No scanner text reaches a prompt or a gap.
- **Waivers.** Written ONLY by `kriya static-analysis waive|revoke` (single-caller tests). The store is outside the workspace (`KRIYA_STATIC_ANALYSIS_HOME`) and read fresh. Coverage gaps and scanner failures are never waivable. ACCEPTED_RISK exits 0 and prints `ACCEPTED RISK — NOT A CLEAN PASS`, never PASS.
- **Scanner.** Semgrep is pinned to an exact version (1.178.0 for the `live_static_analysis` tier). It runs with `--disable-nosem --verbose`, explicit existing targets only, a fixed environment and Kriya-owned snapshots. Kriya enforces `max_target_bytes`. In contained mode it uses a digest-pinned `ContainmentProfile.image_reference` (`--pull never`, `--network none`).
- **Config, production, doctor.** `static_analysis.*` is SECURITY_AUTHORITY as a whole; rule-pack and waiver-store paths are anchored to `config_dir`. Production does not force it on; when enabled, requirement=required and analysis_errors/prerequisites_missing=block. Doctor has seven `static_analysis.*` rows (NOT_APPLICABLE = PASS + `evidence.status`).
- See `docs/design.md` §2.9d and `handover/PRD-031A_TASK.md`.

### Terminal commit: the candidate is released only on proof (P-2) — `kriya/workflow/enforce_loop.py`
After a started terminal commit (a durable journal entry), the isolated candidate is the only copy of possibly-partly-applied verified bytes (PRD-004). The error handler sets the UNCERTAIN marker BEFORE it reads the journal outcome (`interrupted_commit_outcome`) and clears it only on proof: journal COMMITTED agreeing with the commit's settled RunRecord cycle (the workspace holds the bytes), or nothing durable / proven rolled back. A second interrupt (a `BaseException` the lookup's `except Exception` cannot take) therefore finds the candidate retained. Pinned by `tests/test_p2_candidate_retention.py`.
