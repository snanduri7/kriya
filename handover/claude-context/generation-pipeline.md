# Generation pipeline, unified execution plans (PRD-008A), static analysis gate (PRD-031A)

_Moved verbatim from CLAUDE.md on 2026-10-07 (loaded on demand, not every session). Read before modifying any module named here. Code is ground truth; update this file when behaviour changes._

### The generation pipeline (`kriya/workflow/workflow.py`)
`WorkflowEngine.run_generation_workflow` is the core orchestration and is long/stateful by design — read it end-to-end before modifying, don't assume a stage is isolated:
1. **KnowledgeGuard stage 0** (`kriya/tools/knowledge.py`) — scans the goal text for library/version mentions that postdate the configured knowledge cutoff and can short-circuit the whole run with a `knowledge_gap` status requiring explicit confirmation (`--yes`, `--knowledge-policy`, `--ack-knowledge-gap` in the CLI).
2. **Repository analysis** via `RepositoryAnalyzer` (`kriya/analyzer/analyzer.py`) plus **skill matching** via `SkillEngine` (`kriya/skills/skill.py`) — skills activate based on repo facts (dependencies/frameworks detected in analysis) or goal-text/tag matches, not just keywords, and respect `supported_versions` ranges.
   - WAVE8 OI-120 (2026-11-06): the analyzer's auto-generated conventions skill is created ONLY through the Skills owner, `SkillEngine.create_skill` (canonical atomic writer; refuses an existing skill and the shared install skills directory for an unrelated workspace; `commit_message=None` = no repository commit, as before). No plain `open(..., "w")` may appear in `kriya/analyzer/analyzer.py` (AST tripwire in `tests/test_wave8_analyzer_skill_owner.py`).
   - WAVE8 OI-56 (2026-11-06): a runtime-verification gate outcome's `deterministic_result` is a projection of the gate's authoritative verdict: process-exit authority -> `PASS` only when the gate passed, else `FAIL`; `DISTRUSTED` for a rejected marker; `None` when no deterministic verdict exists (`runtime_verification._deterministic_result_provenance_field(authority, passed)`). A failed mandatory gate can never serialize PASS.
3. **Graph RAG retrieval**: hybrid vector+lexical query (`kriya/memory/vector.py::LocalVectorStore.query_hybrid`, reciprocal rank fusion over a brute-force Python/NumPy cosine-similarity scan of BLOB-serialized embeddings in a plain SQLite `vector_chunks` table — no `sqlite-vec` extension is loaded anywhere — plus FTS5 lexical search) finds seed files, then `kriya/analyzer/graph.py::DependencyGraph` expands to a bounded neighborhood, each hit scored by relation-type weight over hop distance; results are assembled into a token-budgeted context string via `build_code_context`, which degrades the lowest-scored matched/related files first through skeletonization tiers (full → skeleton → signatures) when over budget. The stage lives in `kriya/workflow/graph_retrieval.py::retrieve_graph_context` (PRD-027). It queries with the real embedding dimension, uses a term-based BM25 lexical leg, and seeds the graph walk with the seed files as well as their symbols. Seeds come from `select_expansion_seeds` (PRD027-PRECISION-001): when both legs have valid top_k hits, only hits ranked within top_k by both seed (none when they disagree: `NO_CORROBORATED_EXPANSION_SEED`, never a fallback to every hit); when only one leg has valid hits, that leg's top_k seeds. Every hit stays matched and packaged either way, and the run records a `retrieval.expansion_seeds` event. File scores are ranked in explicit evidence tiers (`evidence_scores`, PRD027-SCORE-NORMALIZATION-001): each class normalized by its own best score into (0, 1], direct query hits then in (1, 2] (`DIRECT_EVIDENCE_TIER`), graph-expanded files in (0, 1] - so a binding budget degrades/omits graph expansion before any file the query itself matched (raw RRF <=0.033 vs relation weights 0.5-1.0 used to invert that). `index_implementation_digest` covers the whole graph_retrieval module and every context-assembly step (`build_code_context_package`, `_build_file_tiers`, `_omit_over_budget`, the skeletonizers, `estimate_tokens`). The walk reports a file-sourced relation's calling file (so callers are reached), walks a reached definer's own relations (so two-hop dependencies are reached), and returns one best entry per file before the cap. `kriya/workflow/context_certification.py` measures exactly this path against fixed per-class recall targets and a precision target (`kriya context certify`; CI uses a deterministic hashing embedder for mechanics only). `doctor --production` reads the stored record.
4. **Untrusted learned-knowledge RAG (KNOWLEDGE-READPATH-001)**: anything ingested via `kriya learn` is read ONLY through `kriya/memory/learned_knowledge.py` (`web_knowledge.db`/`learned_knowledge`, rows of the configured embedding model only), once per run by the `generate` CLI from the user's own goal (a milestone plan's `original_goal` for `--from-milestones`), and handed in as `reference_context`; `run_generation_workflow` never queries a knowledge store itself. It is wrapped in explicit "Begin/End Untrusted Reference Context" fencing (`kriya/workflow/untrusted_context.py`; marker lines inside the body are neutralized) with an instruction not to treat it as commands, and reaches Planner/Architect via `convention_prompt` and the Developer via the budgeted `learned_rag_context` slot (trimmed at whole entries to what the PRD-016 graph pool leaves, `context_budget.developer_reference`, at every Developer assembly site - optional untrusted text is never the reason a Developer request is refused) — preserve this fencing if you touch that code path, it's a prompt-injection mitigation, not incidental formatting. Checks for Kriya's own prompt sections (the skill-conventions reminders) read `outside_untrusted_reference(...)`, never the raw prompt. Never join retrieved, learned, Planner or tool text to `goal`/`grounding_goal`/`original_goal`: those are the only source of requirement, mutation-scope, contract and expected-exit authority (AUTH-GOAL-CONTAMINATION-001, a structural test in `tests/test_auth_goal_contamination_001.py`).
5. **Developer + Quality Gates loop**: runs inside an isolated, reused git worktree (`.kriya/worktree`, created/reset by `create_git_worktree`) so compile caches survive across retries. A candidate workspace's worktree (the subtask engine inside the enforce plan worktree) is a sibling, `.kriya/worktrees/<name>`, rooted at the run's canonical workspace (`run_coordinator.candidate_workspace_root`), never inside another managed worktree (`NestedWorktreeError`); only `kriya/workflow/worktree.py` decides worktree locations (WORKTREE-CANONICAL-ROOT-001). The developer agent (`kriya/agents/agent.py::DeveloperAgent`) either returns full file contents or anchored search/replace `edits` (applied via `apply_anchored_edits` -> `kriya/workflow/file_integrity.py`: complete-line blocks matching **exactly once** in one raw-byte snapshot, never straddling skeletonized/elided content; see File integrity below). `PolymorphicValidator` (`kriya/tools/validate.py`) auto-detects the target stack from real markers (Java via pom.xml/build.gradle, Ruby via Gemfile/Rakefile/spec, Python via requirements.txt/pyproject.toml/setup.py/setup.cfg/Pipfile/any .py file present) and runs compile checks then targeted tests before a full regression run (the candidate gate also runs the repository's suite when the stage's `required_verification` declares a test/tests/regression verifier and no target test or written test file selected one - `attempt._declares_test_verification`). Anything matching none of those markers is `"unknown"`, not a silent Python fallback — `run_compile_check`/`run_tests` return `success: True` (so the retry loop doesn't fail forever on a gate that can never run) but say plainly that nothing was actually validated, rather than falsely claiming a Python check passed against zero matching files. On failure the loop retries (bounded by `max(4, 1 + len(llm_chain))`), escalating through `config.llm_chain` fallback models and re-running the context budget allocator against each fallback's own `context_window`.
6. **Human approval gate**: triggered by `autonomy.mode == "human-in-the-loop"` (the closed vocabulary is `guardrails` / `human-in-the-loop`; any other value is a typed configuration error, S16a), a sensitive-path match, or diff size exceeding `autonomy.risk_threshold_lines`; only after approval are worktree changes copied into the real workspace.
   **Approval outcome contract (N1/F4, Wave 1 closure; `kriya/policy/approval.py`).** The general approval callback `callback(files, reason)` answers with one closed `ApprovalOutcome`: `APPROVED`, `DECLINED` (a person, or the terminal prompt, said no) or `UNAVAILABLE` (nobody was asked or nobody decided), each with a reason code from the closed table `APPROVAL_REASON_CODES` (`APPROVAL_GRANTED`, `APPROVAL_DECLINED`, `APPROVAL_LAUNCH_CANNOT_ASK`, `APPROVAL_REVIEW_EXPIRED`, `APPROVAL_DECISION_NOT_RECORDED`, `APPROVAL_RESULT_UNRECOGNIZED`). A legacy `bool` stays accepted (True -> APPROVED, False -> DECLINED); anything else (None, a number, a mock, a still-unresolved awaitable) is UNAVAILABLE, never read through truthiness. `ApprovalOutcome` has NO truth value (`bool()` raises) so no site can write `if approved:` on it. EVERY authority site resolves the answer through the one owner (`resolve_approval` / `resolve_approval_result`, which await any awaitable - coroutine, Task, Future - and let a callback exception propagate to the caller's own fail-closed policy): the change gate (`stage_apply`), Stage 2A, contract escalation (`spec_compliance`), the policy REQUIRE_APPROVAL path and the live-lookup egress approval (`workflow.py`), the live-lookup reference review (`stage_analysis`/`stage_architecture`) and the legacy runtime-command fallback (`approval.ask`, which binds the subject fingerprint only to an APPROVED outcome). A callback that supplies CONTENT (skill gap / skill conflict) is not an approval and only uses `await_if_awaitable`. The terminal change-approval prompts (`generate`, `fix`, `proposal execute`) read ONE parser, `cli._terminal_answer` (RDCG-D-003): only an explicit `y`/`yes` approves and only `n`/`no` is a decline; a bare Enter, end of file / closed stdin, an intercepted Ctrl-C or any other text is UNAVAILABLE with `APPROVAL_DECISION_NOT_RECORDED` (never `APPROVAL_REVIEW_EXPIRED`, which is only for a review that really expired), and no prompt shows or takes a default answer (`tests/test_rdcg_d003_eof_approval.py`). A desktop launch answers UNAVAILABLE (`cli._approval_decision`) for a decision it cannot put to a person, and its review wait (`launch_approval.await_decision`) answers DECLINED only for a durable rejection by the person; an expired or abandoned review is UNAVAILABLE. At the change gate DECLINED stays the `human_rejected` stop; UNAVAILABLE is the existing `approval_required` stop ("approval required and not available"), recorded on the `approval.decision` event with its `reason_code`. Stage 2A ends the unit the same way, as a RESULT and not an exception (Wave-1 final fix-forward 1-E): DECLINED -> `status: human_rejected`, UNAVAILABLE -> `status: approval_required` (with the reason code in `reason`), both with `quality_gates_passed: False`, `files: []` and a short trace row of the same status, before any Developer work; the enforce loop reads such a result as a failed subtask and stops. `ApprovalDecision` itself also has no truth value (`bool()` raises, 1-F), so `if outcome.decision:` cannot read a decline as approval. Contract escalation maps DECLINED -> `CONTRACT_ESCALATION_DECLINED` and UNAVAILABLE -> `CONTRACT_ESCALATION_UNAVAILABLE`. Pinned by `tests/test_n1_f4_approval_outcome.py` (resolver, every awaitable shape, runtime-command fallback, egress, structural tripwire) and the per-site tests named there.
7. **Lesson extraction**: when a fallback-model escalation resolves an error, a one-sentence rule is extracted and staged into `skills/auto-<repo-slug>/staged_rules.txt` (promoted to `rules.txt` via `kriya skills approve`).
8. **Reviewer + trace log**: final review pass (a PRD-016 refusal of it is `failure_category: final_review_refused`, never SUCCESS and never a raw exception; `final_review_refusal` reports the applied and committed state, nothing is rolled back - PROMPT-BUDGET-FIT-001C), then a run trace (plan, retries, gate outcomes, retrieved chunks, model hops) is persisted via `kriya/core/trace.py::TraceLogger` to `trace_db_path(cfg)` (`<state dir>/traces.db`) (viewable with `kriya traces`).

### Unified execution plans (`kriya/workflow/execution_plan.py`, `plan_adapters.py`, `plan_executor.py`) — PRD-008A
A direct goal and a milestone sequence both run as an immutable `ExecutionPlan` of `WorkUnit`s through ONE executor, `plan_executor.execute_plan()` (direct = exactly one unit; milestones = one unit per milestone + an INTEGRATION unit, replay as the plan-wide phase before it). `run_generation_workflow(work_unit=None)` treats the call as a new intent and wraps it in a one-unit plan; anything executing a unit of an outer plan MUST pass its typed `WorkUnitInvocation` (the milestone driver and the enforce subtask loop do) - a new intent started inside a running unit raises `NestedExecutionPlanError`. The executor owns ordering, WorkUnit lifecycle (`RunRecord.execution_plan`/`work_unit_states`), the active work-unit record (commit/checkpoint attribution), WorkUnit-aware checkpoint selection (`select_work_unit_checkpoint`), completion reuse (only PRD-008 S4b/S4c-validated units; incoherent reuse fails closed) and the terminal decision (SUCCESS only when every unit is VERIFIED; the RunCoordinator enforces the same). A `PlanDriver` supplies source-specific bookkeeping only - never a safety decision. `source_kind` is provenance, never a switch between safety implementations. Unit digests/records are byte-compatible with pre-PRD-008A checkpoints and proofs. The enforce-mode structured subtask loop is not yet executed by `execute_plan()` (STRUCTURED is provenance only). See `docs/design.md` §2.9a. **Enforce terminal (PRD-030):** `_run_structured_enforce` calls `TerminalGateService` (`kriya/workflow/terminal_gate_service.py`; typed `TerminalGateReport`, gates in fixed order, a raising gate fails, never writes the real workspace) and `commit_service.commit_verified_candidate` (only a commit-eligible report; wraps `terminal_commit`). The gate validators are passed in as `TerminalGateValidators` built from `workflow_controller`'s own names, so tests that patch `kriya.workflow.workflow_controller.<validator>` still reach them; keep that binding if you move code. The services never import the controller (`tests/test_prd030_terminal_services.py`); see `docs/design.md` §2.9b. Milestone replay (W2-04, R-A): `milestones._authorize_replay` is one synchronous authority transaction - derive the ordered replay set, canonical typed approval (`policy/approval.ask`, replay workspace as the subject's working directory, human-in-the-loop only), re-derive and match the fingerprint AND the milestone-aware set digest, execute exactly the approved argv once; a refusal is `milestone_replay_not_executed`; nothing is persisted, so nothing can resume it. Tests: `tests/test_w204_replay_authority.py`, `tests/test_w204_replay_containment_docker.py`.

**Verification binding (CANDIDATE-VERIFIED-DIGEST-BINDING-001):** `commit_terminal_candidate(verified_candidate=)` is required. It recomputes `verification_binding.bind_candidate(writes)` before anything else and refuses a missing or different binding (`VERIFIED_CANDIDATE_EVIDENCE_MISSING`/`_STALE`) with nothing written, whatever static analysis says; the refusal is the deterministic `workspace_commit_failed` stop. Bindings are taken by enforce in `TerminalGateService.run` before the first gate (`TerminalGateRequest.commit_batch`) and by direct/milestone right after `run_attempt` (`state.verified_candidate_binding`). Tests that commit directly pass `bind_candidate(writes, workspace)`. **Attempt recovery/verification (PRD-031):** `retry_strategy.handle_attempt_failure` is a wrapper over `RecoveryCoordinator` (`kriya/workflow/recovery_coordinator.py`: classify the exception -> `_record_attempt_failure` (injected, unchanged recording) -> `conclude_attempt_failure`, which defers to `retry_policy.decide_for_state`); `attempt._run_verification_only_attempt` runs its declared verifiers through `VerificationCoordinator` (`verification_coordinator.py`, runtime verifier injected). Neither coordinator may import attempt/retry_strategy/workflow/workflow_controller (`tests/test_prd031_coordinators.py`); see §2.9c.

### Static analysis gate (`kriya/static_analysis/`) — PRD-031A
Provider-neutral and off by default. `StaticAnalysisService` is the ONE gate, called at BOTH commit boundaries: the enforce `TerminalGateService` (gate 4 of 7, before terminal_obligations; injected as `TerminalGateValidators.evaluate_static_analysis` from the controller's own `StaticAnalysisService` name) and the direct/milestone pre-apply boundary (`workflow._run_static_analysis_gate`, before approval).

- **Layering.** `kriya/workflow` imports only `static_analysis.service`/`model`. Only `static_analysis/adapters/` may name a provider; a tripwire rejects the word "semgrep" anywhere else in `kriya/`. Policy is Kriya's: adapters never import policy, service or waivers.
- **Commit binding.** `commit_terminal_candidate` has a REQUIRED `static_analysis=` guard, built only by `service.commit_guard(cfg, result)`. Whether evidence is required comes from config (`analysis_enabled`: exactly `enabled is True`; a missing section = disabled). It refuses evidence that is missing, not permitting, or stale in the batch, base scope, scope plan, runtime/rule packs (`port.runtime_fingerprint()`) or settings. Tests that are not about static analysis pass `tests/_fake_static_analysis.py::DISABLED_STATIC_ANALYSIS`.
- **Stops.** A blocked direct run is a deterministic stop (`static_analysis_blocked|unknown|unavailable` in retry_strategy's stop set), never a Developer retry. No scanner text reaches a prompt or a gap.
- **Waivers.** Written ONLY by `kriya static-analysis waive|revoke` (single-caller tests). The store is outside the workspace (`KRIYA_STATIC_ANALYSIS_HOME`) and read fresh. Coverage gaps and scanner failures are never waivable. ACCEPTED_RISK exits 0 and prints `ACCEPTED RISK — NOT A CLEAN PASS`, never PASS.
- **Scanner.** Semgrep is pinned to an exact version (1.178.0 for the `live_static_analysis` tier). It runs with `--disable-nosem --verbose`, explicit existing targets only, a fixed environment and Kriya-owned snapshots. Kriya enforces `max_target_bytes`. In contained mode it uses a digest-pinned `ContainmentProfile.image_reference` (`--pull never`, `--network none`).
- **Config, production, doctor.** `static_analysis.*` is SECURITY_AUTHORITY as a whole; rule-pack and waiver-store paths are anchored to `config_dir`. Production does not force it on; when enabled, requirement=required and analysis_errors/prerequisites_missing=block. Doctor has seven `static_analysis.*` rows (NOT_APPLICABLE = PASS + `evidence.status`).
- See `docs/design.md` §2.9d and `handover/PRD-031A_TASK.md`.

### Terminal commit: the candidate is released only on proof (P-2) — `kriya/workflow/enforce_loop.py`
After a started terminal commit (a durable journal entry), the isolated candidate is the only copy of possibly-partly-applied verified bytes (PRD-004). The error handler sets the UNCERTAIN marker BEFORE it reads the journal outcome (`interrupted_commit_outcome`) and clears it only on proof: journal COMMITTED agreeing with the commit's settled RunRecord cycle (the workspace holds the bytes), or nothing durable / proven rolled back. A second interrupt (a `BaseException` the lookup's `except Exception` cannot take) therefore finds the candidate retained. Pinned by `tests/test_p2_candidate_retention.py`. **Result truth (RDCG-B-001):** `run_coordinator.coordinated_mutation` is the ONE owner that reconciles the returned result with the run's RunRecord: an outermost result that claims success (`quality_gates_passed is True` or `status == "success"`) while the record did not end SUCCESS is returned as `needs_review` (record UNCERTAIN; `reason_codes` `UNCERTAIN_RUN_RECORD_COMMIT_STATE`, `recovery_command`) or `failed` (any other terminal state; `RESULT_CONTRADICTS_RUN_RECORD`), with `quality_gates_passed: False` (the aggregate terminal truth, `RunState.final_workflow_quality_passed`), `run_record_state`, `run_record_id`, `reported_status`, and every factual sub-result kept (`candidate_gates_passed`, `overall_attempt_passed`, `files`, `commit_evidence`, `post_commit_persistence_errors`). The direct workflow now carries `TerminalCommitOutcome.record_errors` out as `post_commit_persistence_errors`, as the enforce site always did. Pinned by `tests/test_rdcg_b001_result_truth.py` and `tests/test_prd004_commit_failure.py`.

### Skills and learning during a bound run (P-B, GIT-MIDRUN-COMMITS-S3-001) — `kriya/skills/skill.py`, `kriya/skills/run_shadow.py`
Skill writers commit into whatever git work tree holds the skills directory (the workspace repository by default, `./skills`), and S3 binds every contained gate to the workspace's HEAD (`GIT_METADATA_STALE`). So once an enforce run's plan sandbox exists, no learning write may move the workspace until the terminal verification is done. Two mechanisms, one owner (the run's shared `SkillEngine`):
- **Held verifications (P-B).** A passing Runtime Verification only HOLDS a `HeldSkillVerification` (`hold_verifications`); `is_effectively_verified` / `reclassify_held_rules` are the run-local view (durable `skill.verified` is never advanced early, nothing is inferred after a restart); `apply_held_verifications` persists them after the terminal commit. `mark_verified(False)` has three real causes (no source path, shared-write refusal, write exception); `git_commit_if_tracked` returns False when inside a work tree and not committed, and the flush reports `skill_verification_commit` distinctly.
- **The run-local shadow.** Immediately before the plan sandbox is created, `EnforceLoop.run` calls `activate_run_shadow`: every loaded skills directory that is inside the repository the run binds (under the workspace, or in the same git work tree) is copied to `<state>/run_shadow/<workspace hash>/N/` and the engine's effective root (`skills_dir`, every skill's `source_path`) points at the copy. `skills_dirs` stays CANONICAL (the resume fingerprint hashes it) and `manifest_for` reports canonical paths. Every same-run reader/writer must use the effective root (`SkillEngine.effective_skills_dir`, or the unit's `ctx.skills_dir`): `tests/architecture/test_skills_effective_root.py` inventories every `paths.skills` read. Roots outside the repository keep the old behaviour. Refusals are typed (`RunShadowRefused`: a root that is or holds the repository, a shadow location inside a work tree) and stop the run before any subtask.
- **The end of the run.** Only when `workspace_commit_completed`: `persist_run_learning` applies the held verifications into the shadow and flushes ONE transaction: refuse with `SKILLS_CANONICAL_CHANGED` if the canonical skills no longer equal the snapshot (never last-writer-wins), write exactly the delta, commit exactly those paths (`git_commit_paths`; git-ignored paths are written, not committed), and on any failure restore files, created directories and the index entries it staged (`SKILLS_FLUSH_FAILED`, operation `skill_learning_flush` in `post_commit_persistence_errors`) — a failed flush never leaves dirty learning and never claims durability. Otherwise (`discard_run_learning`, also on an error) the copy is dropped and the canonical skills were never touched. The flush runs after the candidate's identity is pinned and committed, so the bookkeeping commit is never the identity Kriya says it verified.
- A killed process leaves its copy under the state directory; it is never read back (a new engine starts from the canonical skills) and the next run for the same workspace sweeps it. A resumed enforce run does not recover earlier subtasks' run-local learning.

**Uncertain-commit candidate preservation (2026-10-28, RDCG B-006).** The batch commit (`kriya/repository/commit.py`) consumes a write's staged copy at apply, so when a commit ends UNCERTAIN the exact candidate bytes of every non-delete write are kept as digest-bound staged copies: consumed copies are re-created from the in-memory candidate bytes (`_restage_consumed_candidates`, through `_stage_content`; never from the workspace, sandbox or checkpoint) before the in-process rollback and when the COMMITTED evidence cannot be persisted, retained while the evidence is IN_PROGRESS/UNCERTAIN, removed once it is settled, and dropped immediately after a fully successful rollback. A re-staging failure is named in the `UncertainCommitError` detail and the commit stays UNCERTAIN; recovery (`kriya runs recover --complete-partial`) is unchanged and needs exactly one staged copy per not-applied write. The sandbox is not a recovery source. Tests: `tests/test_b006_uncertain_candidate_preservation.py`.

**Policy denials are terminal (B4, 2026-10-29).** Every `PolicyDeniedError` the Developer's proposed action provokes that no other classifier claimed is `unrecoverable_scope_denial` in `recovery_coordinator.classify_attempt_exception`: `retry_strategy.handle_attempt_failure` stops the unit with the typed `UNAUTHORIZED_GENERATION_TARGET: policy refused the Developer's proposed action (<code>)` (no model retry for the same authority decision, no fallback, no further effects) and `retry_policy.charge_failed_attempt(terminal_policy_denial=True)` does not charge the retry budget; fresh authority allows a later attempt. Tests: `tests/test_b4_policy_denial_terminal.py`.

**Generation timing provenance is advisory (contract, Wave-2 Step 11).** `generation_timings[].model` and `generation.completed` carry the active model with `EventAuthority.ADVISORY` (`workflow/generation_service.py`): they label timing; the authoritative model identity is the `model.request` / `model.result` / `model.response` records. Not a defect.

### Gate F (Wave 6, 2026-11-01): terminal authority map, the closer sequence, the milestone artifact registry
- **Commit authority.** The real-workspace transaction is `terminal_commit.commit_terminal_candidate`, with exactly two callers: `commit_service.commit_verified_candidate` (enforce, only for a `commit_eligible` `TerminalGateReport`) and `stage_apply.apply_terminal_candidate` (direct/milestone, only after every pre-apply gate passed). The verified-candidate binding, semantic-safety refusal and static-analysis commit guard live inside it, so both callers get them. Pinned by `tests/test_gate_f_closer_sequence.py`.
- **Terminal eligibility.** Enforce: `TerminalGateService` (eight gates, `commit_eligible`). Direct/milestone: the attempt-level gates call the same deciders (`find_migration_incomplete`, `validate_stack_contract_artifacts`, `StaticAnalysisService.evaluate_candidate`, `find_masking_in_batch`, `blocking_requirements`, `suite_attribution`). `terminal_obligations` and `preserved_references` exist only under enforce (their obligation creators are enforce-only modules; `FUTURE_OWNER_VERIFICATION` needs a structured plan) - tripwire in the same test file.
- **Original-requirement closer sequence.** `requirement_closers.run_requirement_closers` owns the 11-closer sequence, its order and the concatenation; `development_loop` (direct and enforce-unit gate) and `TerminalGateService._requirement_gap` each supply their own scope's arguments (thunks read right before each closer, so state a closer changes is seen by the next), their own closer callables (patch seams unchanged), their own `blocking_requirements` call and result contract. A site that forgets or invents a closer raises.
- **Milestone artifact registry (owner ruling).** A milestone must not mutate the real workspace when its registry derivation cannot be satisfied. `stage_apply.run_artifact_registry_gate` derives the CANDIDATE with the canonical `ArtifactRegistry.derive_from_workspace` before the terminal apply (milestone units only; a failure is a deterministic stop, nothing persisted). `milestones.settle_artifact_registry` publishes the registry only AFTER the source commit: derived from the committed workspace, bound to the committing transaction (`resolved_at_commit`), required to equal the validated candidate (`registry_digest`). A failure there is `ARTIFACT_REGISTRY_SETTLEMENT_UNCERTAIN` (`artifact_registry_settlement_uncertain`, `workspace_state: COMMITTED_REGISTRY_UNSETTLED`): the milestone is not complete, dependents do not run, and the S4c reconstruction completes it on resume. Not part of the commit transaction (unlike the ContractRegistry). Tests: `tests/test_gate_f_milestone_artifact_registry.py`. Open: `ARTIFACT-DERIVATION-INDETERMINATE-MANIFEST-001` (a present-but-malformed manifest derives nothing silently).
- **Current Project View (owner ruling 2026-11-07, Greenfield continuity).** `kriya/repository/project_view.py` is a DERIVED, bounded, read-only projection - never an authority, no second ledger, nothing persisted, rebuilt per work unit by `stage_analysis.analyze_work_unit` (`ctx.project_view`, run events `project_view.built` counts-only / `project_view.unavailable`). Inputs, each consulted afresh: bound tree (`bound_tree_declaration`: visible paths + Git's tracked/untracked split), the commit journal (`accepted_paths`: COMMITTED, ownership-stamped transactions only; a later DELETE ends it), the filesystem (type/size/digest/CURRENT bytes via `O_NOFOLLOW`), and `AuthorizedFileReader` (containment, hard links, secret-bearing names: such a path is not listed at all). - **Requirement evidence closers: runtime stdout and file creation (owner sign-off 2026-11-08, REQUIREMENT-BEHAVIOR-CLAIM-NO-DETERMINISTIC-CLOSER-001).** Two ANCHORED whole-statement grammars in `requirement_scopes.py` (`runtime_stdout_statement`: `[It|The program|...] prints|outputs|displays <literal> when executed|run`; `file_creation_statement`: `Create <literal relative path>.`), each producing a contract binding sealed from the user's words (`CLOSER_RUNTIME_STDOUT` on a BEHAVIOR claim, `CLOSER_FILE_CREATION` on the new `FILE_CREATION` claim; `CONTRACT_COMPILER_VERSION` 4, `SCOPE_RECOGNIZER_VERSION` 2). ## Shared decisions across subtasks (SHARED-DECISION-AUTHORITY-001)
The Planner is given the skills applicable to the goal (`kriya/workflow/skill_extraction.py::planning_skill_constraints`, the SAME `skill_applies_to_goal` + `render_skill_conventions` of `kriya/workflow/skill_conventions.py` the Developer-side analysis uses; lossless, never trimmed, initial and repair requests alike). `skill_conventions.py` imports nothing from `kriya` (kernel owner modules import it and must stay outside every import cycle); the composition that needs the analyzer, the engine and the skill/knowledge helpers lives in `skill_extraction.py` and reaches the enforce loop only through `EnforceDeps.planning_skill_constraints` (ARCH-TESTS-FOUR-FAIL-AT-77603DB-SKILL-CONVENTIONS-CYCLE-001). When a skill offers mutually exclusive alternatives whose choice spans subtasks, the Planner records the menu and its single choice once in an `integration_relationships` entry (`alternatives`, `selected_alternative`; the relationship id is the identity of the decision). `plan_validation.integration_decision_findings` refuses a declared menu with no or an out-of-menu selection and two selections under one id (`INTEGRATION_DECISION_SELECTION_MISSING/INVALID/CONFLICT`, repaired by the Planner, never resolved by order). `planning_request.integration_contracts_for` renders every relationship that names a subtask into that Developer's bounded semantic context with an explicit authority statement: the plan chooses, the skill shows how. **Enforce terminal requirement truth and run attribution (ENFORCE-TERMINAL-REQUIREMENT-TRUTH-001, audit root R1, 2026-11-11).** The enforce aggregate (`enforce_loop.py`, the `requirements` block of the result) computes `requirement_truth(...)` ONCE from the outcomes it reports and puts it on the result as `requirement_truth` (the direct path's field, `outcome.completed_result`). `shadow_mode.write_enforce_trace` copies that field into the `<run_id>.enforce` row as the `requirement.truth` event (never computed there: a result without the field writes no event) and always adds the `evidence.attempt_store` event from `attempt_evidence_scope.store_pointer()` (the owner every unit row uses; the store is opened at the start of the enforce run). Readers are unchanged: `launch._requirement_truth_field`, `application/history.py` (list, workspace-scoped list, detail) and the desktop's `requirementTruthWords`. The truth never changes the lifecycle status: an open requirement blocks only where requirement policy says so (`blocking_requirements` in the terminal gates; VIOLATED always blocks). Tests: `tests/test_enforce_terminal_requirement_truth_001.py`.

**Enforce unit acceptance: the unit's final review is advisory (ENFORCE-UNIT-ADVISORY-REVIEW-ACCEPTANCE-001, audit root R2, 2026-11-11).** A unit's `quality_gates_passed` is `RunState.final_workflow_quality_passed`, which folds in "the final review was performed". Inside an enforce plan nothing reads a unit's review and there is no plan-level review, so the loop no longer decides on that field. Every acceptance site (planned unit, owner recovery, MAY_CHANGE owner, consumer retry, verification-owner reopen) asks ONE predicate, `enforce_loop.enforce_unit_gates_accepted`: the unit passed outright, or (`advisory_review_refusal`) ONLY its review is missing - `final_review_refusal.candidate_applied`, `candidate_gates_passed`, `terminal_regression_passed` and `overall_attempt_passed` all True, no `plan_scope_conflict`, no `workspace_commit_failure`. Each site keeps its own further checks (declared verification, write scope, byte change, no-progress). The unperformed review is reported, never implied: the unit's `reason_codes` carry `ADVISORY_REVIEW_NOT_PERFORMED` plus the refusal's code, and the run result carries `advisory_reviews_not_performed`. `quality_gates_passed` itself and the direct path (final review authoritative, fail-closed) are unchanged. A new raw read of the field in the loop body fails `tests/test_enforce_unit_advisory_review_acceptance_001.py::test_the_loop_reads_the_raw_field_only_to_report_it`. The milestone path's use of the same field is unmeasured (`MILESTONE-UNIT-REVIEW-REFUSAL-FOLD-UNMEASURED-001`).

**Enforce recovery convergence and verification parity (ENFORCE-RECOVERY-CONVERGENCE-001, audit root R4, 2026-11-11).** A recovery that changes an upstream stage's bytes makes every COMPLETED dependent stale, and the run may end successfully only after each of them has converged again. All of it is local to `enforce_loop.py`; nothing new is persisted.
- **One invalidation, three sites.** `_invalidate_dependents(owner_id)` (the existing `transitive_subtask_dependents`) is called by the ordinary owner recovery, the MAY_CHANGE owner (which restores it exactly with `_restore_invalidation` when no byte was retained) and the verification-owner reopen (which used to invalidate nothing), and by a changed dependent reverification (the cascade). Every dependent becomes `pending` in the plan document and the ControlState; a dependent that was `completed` also loses its entry in `subtask_results` at once (the terminal decision reads the latest entry per stage, so a stale result can never satisfy it) and is queued for re-entry.
- **Only a real change counts, and an owner's own recovery run is its newest execution.** An ordinary owner recovery invalidates before the owner runs (crash safety, as before); when that recovery is refused and no byte of the owner changed (and it wrote nothing else) the invalidation is restored exactly, like an unchanged MAY_CHANGE owner; refused with changed bytes keeps the dependents invalidated (no current result, `pending`). In a recovery plan with several owners, an owner that an earlier group invalidated and that then ran its own accepted recovery (`owner_reran`) is not re-entered again and that run is its current result; a carried-forward (VERIFY) or unchanged MAY_CHANGE owner did not run again and stays queued.
- **Schedule.** The loop iterates `_stage_schedule()`: the initial pass is the traversal it always made (the canonical order as it stood when the loop started; a mid-run revision does not change it); before each initial stage and after the last, queued stages are re-entered first, earliest in the CURRENT canonical order, through the same loop body. A re-entry bypasses the resume skip for that stage only; `resumed_subtask_states` is never rewritten.
- **Dependent reverification.** A re-entered stage runs through `_invoke_bounded_subtask` with role `dependent_reverification` and `DEPENDENT_REVERIFICATION_CONTEXT`; a stage that owns files gets `reopened_owner=True` (a verification-only stage has nothing to regenerate). Changed and accepted: an ordinary acceptance, then the cascade. Unchanged: ONLY the unit's typed one-attempt stop `VERIFICATION_RETRY_NO_CHANGE_POSSIBLE` (raised after its candidate gates and regression gate passed on the current tree) with `candidate_gates_passed`, no committed file and equal bytes; the canonical `_evaluate_subtask_verification` still decides declared verification. The stage is `completed` again with reason code `DEPENDENT_REVERIFIED_UNCHANGED` and invalidates nothing. `terminal_regression_passed` is False on that stop (the flag is set after the settlement raises) and is deliberately not read. An answered no-change / no-op edit stays the separate `RECOVERY-MAY-CHANGE-ANSWERED-NO-CHANGE-REFUSED-IN-UNIT-001`.
- **Termination.** Between two recovery events re-entry is monotone (a re-entered stage invalidates only stages later in the topological order), so at most stages-1 re-entries follow one event. Recovery events are bounded where they start: the run may start at most `len(plan.subtasks) x _MAX_PLAN_SCOPE_REVISION_ATTEMPTS` owner-recovery cycles (what one canonical pass can legally start; re-entries share that total instead of renewing it), and the verification-owner reopen stays once per unit per run. In front of both, the same convergence state (plan hash, stages to re-enter, bytes of every planned file) seen twice stops the run. Both stops are `ENFORCE_CONVERGENCE_NOT_REACHED`, `needs_review`, never success.
- **Completed TOOL dependents.** No persisted state can say "completed, but its inputs changed since", and a completed TOOL is never run again (D1). So `_completed_tool_dependents(owner)` is checked BEFORE any owner of a recovery plan is invoked (one check for the MUST_CHANGE and MAY_CHANGE groups of the plan; a VERIFY group invokes nobody) and before a verification-owner reopen: the owner is not reopened, the TOOL stays `completed`, the failing stage ends `needs_review` with `TOOL_STAGE_INVALIDATED_NOT_REPLAYABLE`, and a `plan_recovery_events` entry names `blocked_owners`. R4 does NOT make a completed TOOL durable across a failed run: see `TOOL-DURABLE-COMPLETION-DISCARDED-ON-RUN-FAILURE-001` (sprint log 24).
- **Verification parity.** Ordinary owner-recovery acceptance and MAY_CHANGE changed-owner acceptance require `_evaluate_subtask_verification(owner, owner_result) == COMPLETED`, exactly what the planned path requires (nothing declared, nothing asked). The owner self-correction result carries no verification evidence, so an owner that declares verification skips it and goes straight to the governed owner recovery.
