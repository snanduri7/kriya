### Governed Developer investigation (`kriya/workflow/investigation.py`, `kriya/workflow/attempt.py`) — DEV-INV-001
Opt-in (`autonomy.developer_investigation_enabled`, default False — mirrors `self_correction_loop_enabled`'s exact risk classification in `kriya/config/authority.py`), read-only pre-pass inserted into `attempt.py`'s `_run_developer_generation` (the single choke point all real Developer-generation call sites already funnel through) — lets the Developer request bounded repository evidence mid-attempt, BEFORE proposing a mutation, moving the lifecycle from `precomputed context → generate → validate → retry` toward `UNDERSTAND → INVESTIGATE → PROPOSE → MUTATE → VERIFY → REPAIR` with only INVESTIGATE new. Four closed verbs only (`inspect_member`/`find_symbol`/`find_callers`/`search_code`), each a thin wrapper over an existing authoritative resolver (`CurrentSourceResolver`/`member_boundaries_for`, `DependencyGraph` — including the new indexed `find_symbol_locations` exact-match method — and `LocalVectorStore.query_hybrid`, the last injected as a plain async callable so the module never touches an embedding endpoint itself). Both a native tool-calling protocol (`LLMClient.complete_with_tools`, reusing `kriya/workflow/self_correction.py`'s established small-argument-tool shape) and a deterministic marker/text fallback (`INVESTIGATE: <verb> <json>`, for the majority of local models per `model_capabilities.py`'s conservative default) normalize into one `InvestigationRequest(verb, arguments)` before authorization/resolution ever runs. Every path-backed result passes through the new `kriya/policy/filesystem.py::AuthorizedFileReader` (the read-side sibling of `AuthorizedFileWriter` — same workspace-containment + sensitive-path composition, same real-enforcement posture) before being shown to the model. No new `EvidenceItem` class and no new `ContextItem.source_type` value — every verb returns ordinary `ContextItem`s reusing three EXISTING closed-vocabulary values (`inspect_member`→`"named_in_request"`, `find_symbol`/`find_callers`→`"graph_dependency"`, `search_code`→`"semantic_hit"`; `reason` free text carries the DEV-INV-001-specific detail — `CONTEXT_SOURCE_TYPES` is a deliberately pinned, tested-exact vocabulary, per `tests/test_context_package.py`'s own tripwire test); D1 (`_completeness_gated_operation`) is completely unmodified — a `tier="member_exact"` result merges into `state.known_target_context_items` via the SAME `_preserve_member_exact_precision` helper the retry-projection path already uses, and none of the four verbs ever produces `tier="full"`, so investigation can only ever help authorize a more precise patch, never a whole-file replacement. A distance-independent no-progress gate (fingerprint → last combined evidence hash) bounds the turn loop; `GenerationState.investigation_turns_used_by_attempt` shares one per-attempt turn budget across every `_run_developer_generation` call within that attempt (a coordinated-repair attempt calls it once per contract participant). See `docs/assurance/DEV_INV_001_ARCHITECTURE.md` for the full design rationale, explicit non-goals, and relationship to MA9 recovery (not integrated in this MVP).

### Edit-protocol capability (`kriya/workflow/edit_capability.py`) — CONTEXT-EDIT-PROTOCOL-001
- **Invariant.** Never offer a mutation operation the invocation's authoritative context cannot support. `attempt._decide_edit_capabilities` (Developer choke point) decides one `EditCapability` per existing target (`context.edit_capability`); the contract (`edit_operations` -> `_fill_missing_content`) and the validators (`_authorize_anchors`, `_validate_actual_mutation_authority`) read the same record, never a second predicate.
- **Operations.** Full file only with D1 authority or the restore phase (overrides a profile's full-file preference). Anchored edit only when byte-exact spans cover every locus: `full`/`member_exact`/excerpt items, the whole file verbatim in MANDATORY text (optional sections can be trimmed), or derived windows; skeleton text never counts. Neither: `CONTEXT_EDIT_PROTOCOL_UNSATISFIABLE` before inference (stop set).
- **Windows.** Loci only from goal-quoted code found verbatim, failure lines and rejected SEARCH blocks (`_remember_anchor_loci`). Member/block when it fits an equal share, else one shared radius <= `8*2^anchor_failures`; budget `exact_window_reserve` (12%), held back from the known-target/retry-member package only when a target is not shown whole (`_target_package_with_window_reserve`).
- **Anchors and retries.** `ANCHOR_OUTSIDE_AUTHORITATIVE_CONTEXT` (real text never shown; becomes a locus) vs `ANCHOR_NOT_IN_FILE`. Same capability digest + model + requested operation after an edit-protocol failure = `ANCHOR_CONTEXT_NOT_ESCALATED`, counted as no progress. That refusal changes strategy at once (`force_strategy_transition(immediate=True)`: the fallback when one can serve, else the full-set route), and the same refusal again (`GenerationState.edit_refused_capabilities`) reaches the no-progress limit at once (GR-R0 RETRY-NO-INFORMATION-GAIN; `tests/test_gr0_retry_no_information_gain.py`). Tests: `tests/test_context_edit_protocol_001.py` (synthetic harness `tests/_edit_protocol_harness.py`).
- **New-member insertion (P3-D, `kriya/workflow/insertion_locus.py`).** When the user's goal names in quoted code a member (`name(`) the owner type does not declare and there is no full-file authority, `_structural_insertion_locus` resolves a zero-width `InsertionLocus` from the Code Intelligence parse of the exact bytes read: the owner is the one grounded type, else the one the goal names, else the file's public type (more than one = refused); tier `after_grounded_member` else `owner_closing_delimiter` (the parser's body end, never a brace search); the gap is the whitespace after that anchor; the carrier is the smallest unique run of whole lines covering it (2-12 lines), rendered as `[insertion_locus]` exact source with an ADD-only instruction. It makes ANCHORED_EDIT feasible but is never an ordinary span: an anchor found only in the carrier is `INSERTION_ONLY`, accepted only if, applied alone, `verify_insertion` passes (same revision else `STALE_INSERTION_LOCUS`; owner/carrier unchanged; carrier in the request actually sent else `INSERTION_LOCUS_NOT_SENT`; pure insertion meeting the gap else `INSERTION_OUTSIDE_LOCUS`; re-parse keeps every declaration and adds only ones under the owner else `INSERTION_STRUCTURE_CHANGED`). No protocol change, never full-file authority, never imports. Java class/interface/record (adapter capability `STRUCTURAL_INSERTION` PARTIAL; enum/annotation types and Python typed unsupported). A locus is never persisted: each invocation decides its own. Tests: `tests/test_p3d_structural_insertion.py`.

### File integrity (`kriya/agents/response_protocol.py`, `kriya/workflow/file_integrity.py`) — FILE-INTEGRITY-CONTRACT-001 (KAD-063)
- **Protocol is not payload.** A Developer response is parsed by `response_protocol` (`parse_raw_payload`, `parse_legacy_repair`, `parse_structured`; `DeveloperAgent.parse_file_payload` adds the JSON-envelope unwrap) into a typed `DeveloperResponse`. Only a wrapper enclosing the WHOLE payload is removed (one outer fence, not for Markdown targets; the JSON envelope). Nothing inside a payload is ever rewritten; a mismatch is a typed refusal (`AMBIGUOUS_FILE_RESPONSE_PROTOCOL`, `INVALID_EDIT_PROTOCOL`, `CONFLICTING_DEVELOPER_RESPONSE`, `MODEL_EDIT_PROTOCOL_INVALID`) retried through the operation contract. `autonomy.developer_response_protocol` (SECURITY_AUTHORITY) picks exactly one protocol per invocation, never a fallback: `structured` (`kriya_sentinel_v1`, the production protocol: path-named `<<<KRIYA:FILE|EDIT|NO_CHANGE path=...>>>` blocks with explicit end markers, text after the last block refused, every FILE line newline-terminated unless `<<<KRIYA:END_FILE no_final_newline>>>`, `path=` normalized as a safe repo-relative POSIX path) or `legacy_strict` (`strict_legacy_v1`, compatibility-only: exact column-0 markers but no payload terminator; refused under `runtime_profile: production` (`RESPONSE_PROTOCOL_NOT_PRODUCTION`) and by doctor's `model.response_protocol`). The protocol identity is bound into qualification (`policy_digest_for`, record field `developer_response_protocol`; policy `/7`). There is no `sanitize_generated_content`; never add payload cleanup. Tests that script legacy/raw Developer answers either pin `legacy_strict` explicitly or render them through `tests/_protocol_responses.py::as_requested`.
- **One edit engine.** `load_snapshot` = raw bytes + `sha256` revision + strict UTF-8 (BOM ok) text in one line-ending convention, proven to round-trip; `apply_line_block_edits` locates every SEARCH as complete lines (split on `"\n"` only) in the same source, exact then indentation-tolerant, and refuses zero/ambiguous/overlapping/empty/inconsistent-indent anchors; `FileSnapshot.encode` writes the file's own BOM and convention. Unsupported encodings, mixed endings and symlinks are `file_integrity_unsupported` deterministic stops.
- **Raw revisions.** `read_file_revision` and every `expected_base_revision` are raw-byte digests (commit evidence schema 3). Decision reads for context freshness use `read_shown_text` (undecodable -> `raw:` revision). Never decode with `errors="replace"` on a mutation or revision path.
- **No hidden writes; three bindings.** Deterministic corrections are candidate mutations (`attempt._apply_candidate_pom_corrections`: only a candidate-written pom, authorized writer, `candidate.deterministic_transformation` event, before the gates). (1) Candidate binding: before the FIRST gate of an attempt `attempt._bind_verification_tree` proves the sandbox holds `state.candidate_digests`. (2) Verification-tree binding: it then binds the whole tree (git-tracked repository content from `worktree.repository_content_paths` + candidate; `file_integrity.VerificationTreeBinding`), and every `PolymorphicValidator` gate method (`_verification_gate`: compile, tests, runtime verification, pom validate, classpath inspection) re-checks it AFTER the gate (stat, then re-hash only what changed) - a change is the typed stop `VERIFICATION_GATE_MUTATED_TRACKED_FILES` (`failure_category: verification_tree_mutated`); repository content follows Git: an untracked file Git does not ignore IS content, so a gate that creates one (other than candidate or Kriya-authorized output, or the output of the exact toolchain command that gate runs - `validate.gate_output_roots`: Maven module `target/`, Gradle `build/` + `.gradle/`, `javac -d` dir, Python `__pycache__/` + `.pytest_cache/` - registered per gate invocation, never a global path rule) is the typed stop `VERIFICATION_GATE_CREATED_UNAUTHORIZED_FILE` (FILE-INTEGRITY-CONTRACT-001B); the one exception is the application-runtime gate (`validate.RUNTIME_VERIFICATION_GATE`, D6): files the APPLICATION creates while it runs are runtime state, recorded as `runtime_artifacts` (gate evidence, paths only) and deleted after the gate (`VerificationTreeBinding.check(ephemeral_untracked=True)`; an undeletable one fails closed), never candidate bytes or recovery targets, while a change to any tracked or candidate path is still `VERIFICATION_GATE_MUTATED_TRACKED_FILES`; ignored output is never listed or hashed; Kriya's own authorized writes re-record with `authorize`; the tree is checked once more before the terminal verified-candidate binding. (3) Commit binding: the verified candidate binding plus a post-commit re-read of the destination (`VERIFIED_COMMIT_DIGEST_MISMATCH`). Worktree sync is `git status --porcelain=v1 -z` (`worktree.git_status_entries`), byte-checked, fail closed (`WorktreeSyncError`); both direct and enforce runs report its reason code (`WORKTREE_SYNC_FAILED` / `WORKTREE_CONTENT_MISMATCH`) as a typed terminal result, never a generic sandbox error. A new filesystem write site fails `tests/test_file_integrity_contract_001.py` until classified in `handover/FILE_INTEGRITY_CONTRACT_001.md`. Planner/Architect/Reviewer text is never file content: every source of the bytes `run_attempt` commits maps to a named authority (`tests/test_file_integrity_contract_001b.py`), so a new source fails until classified.

### Agents (`kriya/agents/agent.py`)
`BaseAgent` wraps `LLMClient.complete`. `PlannerAgent`/`ArchitectAgent`/`ReviewerAgent` are single-shot prompt agents; `DeveloperAgent.run_generation` first asks the model for a file list, then either accepts a full JSON file-object array in one shot or falls back to iterative per-file generation (one completion per filepath) when the model only returns paths — there's also a raw-JSON-extraction fallback for models that wrap output in markdown or partial JSON. Any change to the developer agent's output contract needs to keep both the "batch JSON" and "iterative per-file" paths working, plus the `path`→`filepath` key normalization.
