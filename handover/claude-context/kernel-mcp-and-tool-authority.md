# Kernel, plugins, MCP (SEC-003/004, TOOL-002/003), ShellTool network authority (SEC-005), autonomous TOOL subtasks (TOOL-001)

_Moved verbatim from CLAUDE.md on 2026-10-07 (loaded on demand, not every session). Read before modifying any module named here. Code is ground truth; update this file when behaviour changes._

### Kernel / registry / plugins (`kriya/core`, `kriya/plugins`)
`Kernel` (`kriya/core/kernel.py`) is a thin async lifecycle object holding a `ComponentRegistry` (category → name → instance, e.g. `registry.get("tool", "filesystem")`) and an `EventSystem` (pub/sub, supports sync and async handlers, emits `kernel_starting`/`kernel_started`/`plugin_initialized`/etc.). `PluginManager` (`kriya/plugins/plugin.py`) discovers plugin packages under `plugins.directory`, imports each as a top-level module (so plugin folder names must be valid, unique module names), finds `BasePlugin` subclasses, and calls `initialize()`/`shutdown()` on them — plugins register `BaseTool` instances into the kernel registry (see `plugins/core_tools/__init__.py` for the filesystem/shell/git/search/ast/validate_refactor tools).

### MCP subprocess environment (`kriya/mcp/mcp.py`) — SEC-003
`MCPManager.start_all()` (called from `Kernel.start()`) is the only place `MCPClient` is constructed, and `MCPClient.start()` is the only MCP subprocess creation site in the codebase. Its environment is built by `build_mcp_subprocess_env(configured_env)`, never ambient `os.environ`: `MCP_BASELINE_ENV_ALLOWLIST` (`LANG, LC_ALL, TMPDIR, TEMP, TMP`, plus real `PATH` always via `kriya/tools/sandbox.py::build_restricted_env()`, reused as-is from SEC-001) UNION `cfg.mcp.<server>.env` (already SEC-009-authorized before this function runs). `HOME` is deliberately excluded from the baseline — it's the implicit discovery root for a wide range of third-party tooling (`.ssh`, `.gitconfig`, cloud-CLI state, SDK config), not a low-authority compatibility variable like `LANG`/`TMPDIR` — and is only present if a server's own `env` sets it explicitly. Proxy variables (`HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`/`NO_PROXY`) are never in the baseline either. `build_mcp_subprocess_env()` is pure and non-raising — there is no fallback path to ambient `os.environ` on any failure. When adding a new MCP-adjacent subprocess call, reuse `build_mcp_subprocess_env()`/`build_restricted_env()` rather than merging `os.environ` directly.

### MCP subprocess lifecycle (`kriya/mcp/mcp.py`, `kriya/mcp/lifecycle.py`) — SEC-004
Every MCP server's process is spawned via `kriya/mcp/lifecycle.py::spawn_mcp_process()` (process-group isolation via `ProcessControlPort.spawn_options()`, POSIX `start_new_session=True`, CPU/memory rlimits via SEC-001's `posix_resource_limits_preexec_fn`, a hard per-line stdout ceiling via asyncio's own `limit=` kwarg) and torn down via `terminate_mcp_process()` (bounded `RUNNING → SIGTERM → bounded wait → killpg(SIGKILL) → bounded reap → CLOSED` state machine, reusing `kriya/tools/process.py::terminate_process_tree()` for the process-group kill — promoted from a `ProcessController`-only helper this same pass). `MCPClient` tracks an explicit `_ConnState` (not a single boolean) and bounds every server-controlled await: `start()` wraps the full launch+handshake in `mcp_lifecycle.startup_timeout_seconds`, `_send_request()` wraps every request (including `initialize`) in `mcp_lifecycle.request_timeout_seconds`. An oversized stdout line (`ValueError` from the StreamReader `limit`) or stdout EOF both run the full `_close()` sequence — connection state, process, reader tasks, and pending-request Futures are torn down together, and `MCPManager._on_client_closed()` proactively unregisters that server's tools so a dead connection can never keep routing calls (stale-lifecycle-state cleanup). `MCPManager.start_all()` is atomic — any server failing to start rolls back every server already started in that same call. stderr retention is a bounded rolling buffer (`mcp_lifecycle.max_stderr_buffer_bytes`) with LOGGING separately capped (`MCPClient._STDERR_LOG_LINE_CAP`) so a flooding server can't exhaust Kriya's own logs either. All `mcp_lifecycle.*` bounds are `SECURITY_AUTHORITY` under SEC-009 — a repository can never weaken any of them. `memory_mb` (RLIMIT_AS) is deterministic on Linux, advisory-only on macOS (an accepted SEC-001 platform limitation); `cpu_seconds` (RLIMIT_CPU) is a cumulative LIFETIME budget, not a rate limit — true CPU/memory rate/ceiling enforcement needs real container/cgroup containment, which belongs to **TOOL-003** (see that section below), not attempted here. SEC-004 does not touch tool-call authorization or MCP execution containment — it only bounds the lifecycle of an already-authorized (SEC-009) connection.

### MCP invocation authority (`kriya/mcp/mcp.py`, `kriya/policy/execution.py`, `kriya/policy/model.py`) — TOOL-002 P1
Every MCP `tools/call` passes a deterministic `ExecutionPolicy` decision, bound to structured identity, immediately before `MCPClient.call_tool()` — the single production choke point (`MCPTool._run()`), covering every route that reaches an MCP tool (`kriya tools execute` via `BaseTool.execute()`, and a planned TOOL subtask via `execute_model_authored()` — S1/S18: the planned-tool governance resolution first, then the tool's `authorize_model_invocation`; both end in `_run()`). This is **real enforcement, unconditionally** — unlike every other `ExecutionPolicy` consumer (audit-only unless `execution_policy.mode == "enforce"`), MCP has no legitimate "Kriya's own trusted command" carve-out to ever fall back on, so `MCPTool._run()` never reads `mode` at all; DENY, REQUIRE_APPROVAL (P1 has no reachable approval mechanism at this call site, so it fails closed, mirroring `ShellTool`/`GitTool`'s own established precedent), and a throwing/unavailable policy engine all raise `PolicyDeniedError` before `self.client.call_tool()` is ever reached — this is Kriya's *second* deliberate, explicit exception to MA4's audit-only mandate, after `AuthorizedFileWriter`.

`ActionType.MCP_TOOL_CALL` (new) is governed by a new `ExecutionPolicy._check_mcp_invocation` stage. It decides purely on **structured identity** — `MCPToolIdentity(server_identity, tool_name, schema_digest)` (`kriya/policy/model.py`), bound once at `MCPTool.__init__` from the same `tool_meta` snapshot the actual dispatch target (`self.client`, `self._exact_tool_name`) is also derived from, so a policy decision and its own dispatch target can never diverge — never a flattened display string (`f"{server}_{tool}"`, still used for registry lookup/UI only). `schema_digest` is a SHA-256 over the tool's `inputSchema` with every `description` key stripped at any nesting depth first (`compute_mcp_schema_digest`) — a schema/tool/server change is a different identity, so an earlier approval never silently carries over. The server's own advertised `description`/annotations/result text and the call's actual arguments are never inputs to this decision at all (Invariant: MCP-provided metadata may describe an operation, never authorize it) — P1 intentionally does not infer filesystem/network/process semantics from anything; the only decision it can make is whether this exact identity is in an explicit, non-persistent, constructor-supplied approved set (`ExecutionPolicy(approved_mcp_tool_identities=...)`, empty by default) — every real call in a default deployment therefore falls through to `REQUIRE_APPROVAL` → fails closed, until a real operator-facing capability/approval mechanism (TOOL-002 P2) exists.

**This is invocation authority only.** An ALLOWed call reaches an MCP subprocess whose filesystem/network/process containment depends entirely on `autonomy.mcp_contained_execution_required` (default False, host-side/unconstrained; `True` = real OCI enforcement — see the "MCP OCI enforcement — TOOL-003 P2" section below). SEC-009 config-activation approval and this invocation approval are deliberately separate decisions, never conflated — starting a server successfully never populates the approved-identity set. Reuses existing machinery throughout: `PolicyDeniedError` (same type `ShellTool`/`GitTool` already raise), `kriya/policy/telemetry.py::build_decision_record()` (extended with three narrow, named MCP fields — never a blanket `metadata` dump). See `docs/assurance/KRIYA_PRODUCTION_RISK_REGISTER.md`'s TOOL-002 entry for the full investigation/decision record and the honest security-scope statement.

### MCP durable invocation approval (`kriya/mcp/invocation_approval.py`, `kriya/cli.py`'s `mcp` group) — TOOL-002 P2
**Restores the real, operator-facing production capability P1 disclosed as lost**, without touching P1's own static test-injection mechanism at all. `ExecutionPolicy.__init__` gained a second, independent, additive constructor parameter — `mcp_invocation_approval_resolver` — consulted by `_check_mcp_invocation` only AFTER the pre-existing `approved_mcp_tool_identities` static frozenset check (unit-test injection only, completely unchanged, still checked first). `MCPManager.__init__` — the single production `MCPManager` construction site (`Kernel.__init__` always constructs one with no explicit `execution_policy`) — wires the real resolver by default via `kriya/mcp/invocation_approval.py::resolve_mcp_invocation_approval(workspace_root=os.path.realpath(os.getcwd()))`, the exact same `workspace_root` derivation `MCPManager.start_all()` already uses for capability-profile resolution — one consistent workspace-identity source, never two independently-computed values that could drift apart.

`kriya/mcp/invocation_approval.py` is a NEW, PARALLEL module — modeled closely on SEC-009 P2's own `kriya/config/authority_approval.py` patterns (atomic tmp-file+`os.replace()` write, workspace-identity binding, digest-bound records, corrupt/unknown-format fail-closed) but a completely separate artifact/store, never conflated with it (Invariant 12: SEC-009 config approval ≠ TOOL-002 invocation approval — proven by a dedicated test using a REAL SEC-009 approval and confirming it does not authorize any MCP call). The durable approval binding is `workspace_id + MCPToolIdentity(server_identity, tool_name, schema_digest) + MCPCapabilityProfileIdentity.profile_digest` — a SHA-256 over a canonical JSON dict (`compute_invocation_approval_binding_digest()`), covering exactly the same five fields Invariant 9/10 require; ANY drift in ANY one of them (server, tool, schema, capability profile, or workspace) invalidates the whole binding, with no partial/best-effort match. The store lives OUTSIDE the workspace (`~/.kriya/mcp_approvals/<workspace_id>.json` by default, override via `KRIYA_MCP_APPROVAL_HOME`, mirroring `KRIYA_AUTHORITY_HOME`'s own precedent exactly) so a malicious repository can never ship its own self-authorizing approval alongside a hostile MCP config in the same commit. The resolver this module hands `ExecutionPolicy` reads the artifact FRESH FROM DISK on every single call — no caching layer anywhere — which is what makes both Task 7's revalidation requirement and Task 11's "revocation takes effect without restarting Kriya" requirement true by construction rather than by convention.

`_check_mcp_invocation`'s capability-profile-identity metadata (audit-only under TOOL-003 P1) is now ALSO read here, but strictly as an anti-drift BINDING KEY inside the durable-approval check — never as an independent authority source (Invariant 13 stays true: a wider capability profile alone still grants nothing; an approval merely stops validating once the profile it was granted under changes). A resolver exception is deliberately NOT caught inside `_check_mcp_invocation` or `ExecutionPolicy.evaluate()` — it propagates to `MCPTool._run()`'s own PRE-EXISTING try/except (built during TOOL-002 P1, unchanged), which already converts ANY policy-evaluation exception into a fail-closed `DENY`. This is real reuse, not incidental: it means Task 15/required-test-24 ("approval-store exception fails closed") needed zero new exception-handling code.

CLI (`kriya/cli.py`'s new `mcp` group, mirroring `authority_group`'s own `inspect`/`approve`/`revoke` shape): `kriya mcp inspect` starts the real, configured MCP servers (exactly like `tools list`/`tools execute`) and shows every discovered tool's exact identity, capability-profile summary/digest, containment required/active/backend, and current approval status — read-only, never writes. `kriya mcp approve <flattened_name>` resolves `<flattened_name>` (the exact `server_tool` string `tools list`/`mcp inspect` themselves print) via a REAL registry lookup (`kernel.registry.get("tool", name)`) — **never by parsing/splitting the string** — then binds the approval to that specific `MCPTool` object's own `.identity`/`.capability_profile_identity`, so even a flattened-name collision between two servers can never transfer approval from one structured identity to another (Invariant 14, required test 22): whichever object the registry actually holds under that name is exactly what real dispatch would also invoke, so approval and dispatch can never target different objects. `kriya mcp revoke <flattened_name>` matches on `(server_identity, tool_name)` alone — not the full binding digest — so a STALE approval (whose profile/schema has already drifted, and therefore no longer matches any current binding digest) can still be found and removed. `-y` on `tools execute` never creates or substitutes for approval — it only ever skips the ordinary shell-tool-style human-review confirmation prompt, which MCP never reaches in the first place (P1's own real-enforcement gate raises `PolicyDeniedError` before that prompt is ever shown).

Telemetry (`kriya/policy/telemetry.py`, `PolicyDecisionRecord`): a fourth narrow, explicit exception to "never blanket-dump metadata" (after the tool-identity, capability-profile-identity, and this same convention) — `metadata["mcp_containment_identity"]` (a new closed, three-field `MCPContainmentIdentity` in `kriya/policy/model.py`: `required`/`active`/`backend`) is extracted into three named `mcp_containment_*` fields, so an ALLOWed call's audit trail always shows whether TOOL-003 containment assurance genuinely applied — host-mode (`containment_required=False`) is recorded EXPLICITLY as `False`/`False`/`None`, never silently omitted, so it can never be mistaken for containment evidence. The durable-approval ALLOW path gets its own reason code (`MCP_TOOL_DURABLE_APPROVAL_VALID`), distinguishable in every log/record from P1's static-injection `MCP_TOOL_IDENTITY_APPROVED`.

**Honest security statement (state exactly, no stronger claim):** TOOL-002 P2 lets an operator explicitly, durably approve a specific MCP tool's exact identity+capability binding, and revalidates that full binding — never merely a name — before every subsequent invocation. It does not grant, widen, or substitute for TOOL-003 capability/containment authority in either direction; an approved call under `mcp_contained_execution_required=True` is still fully OCI-constrained, and an approved call under the default `False` executes host-side with NO containment assurance, which every approval/inspection surface reports explicitly rather than implying otherwise. TOOL-002 and TOOL-003 remain OPEN in the risk register pending combined adversarial closure — this package does not close either.

### MCP capability authority (`kriya/config/config.py`, `kriya/mcp/capability.py`, `kriya/mcp/mcp.py`) — TOOL-003 P1
**Defines and governs MCP capability authority; does not yet enforce it at the OS/container boundary.** For every configured `mcp.<server>`, `mcp.<server>.capabilities.*` (`MCPCapabilityConfig`, pydantic) declares the MAXIMUM filesystem/network authority that server may ever be declared to possess — `workspace_read`/`workspace_write`/`temp_read_write`/`dependency_cache_read` (booleans), `additional_read_paths`/`additional_write_paths` (explicit paths), and `network`/`network_hosts` (`"denied"` default / `"explicit_destinations"` + a host list / `"unrestricted"`). The safe default is **nothing declared** — deliberately not grandfathering today's real (unenforced) host access, so the day `TOOL-003 P2` wires this into real containment, an operator who never explicitly widened a server's profile starts genuinely restricted rather than needing to lock broad implicit trust back down. There is no configurable process field at all — SEC-004's `start_new_session=True` is lifecycle ownership only, never a capability restriction, so every resolved profile instead carries a fixed, honest constant (`kriya/mcp/capability.py::PROCESS_AUTHORITY_STATEMENT = "unconstrained_pending_oci_containment"`).

The entire `mcp.<server>` block (capabilities included) is already unconditionally `SECURITY_AUTHORITY` under SEC-009 (`kriya/config/authority.py`'s `classify_field()` — the `top_key == "mcp"` branch fires before any leaf is even inspected), so no new classification-table entries were needed: any repository-sourced widening of a server's capabilities is denied before `AppConfig`/`MCPManager` ever see it, exactly like every other `mcp.*` field, and SEC-009 P2's own digest-drift mechanism (`kriya/config/authority_approval.py`) already invalidates approval the instant a capability value changes. Filesystem path safety (a relative `additional_*_paths` entry escaping via `..`/a symlink) is rejected once, at config-load time, in `resolve_config_state()` — anchored to `config_dir`, the same anchor and the same realpath-based idiom `paths.*`/`logging.directory` already use, for the identical reason (the value SEC-009 digests and the value later bound to a real `MCPClient` must be the same single resolved value, never independently re-resolved against a possibly-different CWD). An **absolute** path is a deliberately different, supported case — an explicit host path outside the workspace, never rejected as an "escape," still gated by the same blanket SEC-009 approval requirement.

`kriya/mcp/capability.py::resolve_mcp_capability_profile()` turns an already-validated `MCPCapabilityConfig` into a frozen, canonical `MCPCapabilityProfile`, bound to `MCPClient.capability_profile` in `MCPManager.start_all()` *before* the client (and therefore the process) is ever constructed — a pure data/authority binding. `MCPTool` carries a parallel `MCPCapabilityProfileIdentity` (`kriya/policy/model.py`, strings-only, no import from `kriya/mcp/` — preserves the existing one-directional `mcp → policy` dependency) into `ActionRequest.metadata` alongside TOOL-002's own `MCPToolIdentity`, surfaced in telemetry (`build_decision_record()`) for audit context **only** — `ExecutionPolicy._check_mcp_invocation` never reads it, so capability approval (SEC-009, config-time) can never substitute for or widen invocation approval (TOOL-002, per-call), and vice versa. `NetworkAuthority` (the SEC-001/target-code-sandboxing enum) is deliberately NOT extended with a third member for this — `kriya/tools/containment_oci.py`'s `OCIContainmentBackend.prepare()` has no exhaustive-match guard on it, so a shared new member risks a silent full-UNRESTRICTED fallback in that unrelated path; MCP capability profiles use their own `MCPNetworkAuthority` enum instead, with matching value-strings for a lossless future mapping.

### MCP OCI enforcement (`kriya/mcp/containment_adapter.py`, `kriya/tools/containment.py`, `kriya/tools/containment_oci.py`, `kriya/mcp/mcp.py`) — TOOL-003 P2
**S7 supersession (2026-10-26): containment is no longer opt-in.** `autonomy.mcp_contained_execution_required` now defaults to **True**, an explicit false is refused (`ContainmentOptOutError`, `kriya.config.authority.parse_containment_mandate`), and `_containment_is_mandatory` is unconditional; the opt-in / default-False history in this section and the next is superseded. Project-controlled execution is contained by an isolating backend or refused typed before any process starts.

**Enforces the resolved `MCPCapabilityProfile` at the OCI boundary, opt-in.** `autonomy.mcp_contained_execution_required` (default **False**, SEC-009 `SECURITY_AUTHORITY`, mirroring `contained_execution_required`'s own established pattern) is a deliberate default-flip decision made explicitly with the user (2026-09-13): "always require containment for every MCP server" was considered and rejected as the *default* because every MCP server is `TrustClass.UNTRUSTED_EXECUTION` (`backend_required=True` unconditionally), so an unconditional requirement would make Docker a hard MCP dependency and break ~40 pre-existing tests that spawn real MCP subprocesses with no Docker involved. A strict-superset relationship holds instead — flipping the default to `True` later is a one-line config change, not a rearchitecture. **Once `True`, "no raw-host fallback" is absolute, and the decision is the canonical owner's (D2 S5, 2026-10-25).** `MCPManager.start_all` asks `decide_external_execution(autonomy, subject=mcp_subject(name))` (kriya/tools/containment.py; the MCP-specific pre-migration flag lives in the ONE `_containment_is_mandatory` rule, the final production contract makes it unconditional) and takes the backend from `decision.backend()`: a non-isolating (`none`), unknown or unavailable backend is the typed `ExternalExecutionRefused`/`BackendUnavailableError` BEFORE any client or process exists, for EVERY network grant (before S5 the Null backend ACCEPTED an `unrestricted` profile and ran the server on the host with Kriya's full environment while reporting `containment_active=True` — MEASURED, fixed). A client that is handed a backend checks it with the owner's `require_isolating_backend`; a prepared containment with no launch prefix is refused. `MCPClient.containment_required`/`.containment_active` are two DIFFERENT booleans, both exposed for audit: the former is what was demanded, the latter is `True` only while the server was actually launched THROUGH an isolating backend's prefix (and is cleared on close) — a host-side run must never be misread as containment evidence. Required containment does not imply network denial: an `unrestricted` grant is valid inside a real container (containment owns where it runs, the capability grant owns the network). Semantic MCP tests use the test-only stand-in (tests/_mcp_containment_standin.py, `mcp_standin` fixture; not selectable by configuration, not isolation evidence); real isolation is proven in the real-OCI tier (tests/test_tool003_p2_oci_enforcement.py, tests/test_s5_mcp_real_oci.py). The tests that characterized the legacy host state (marker `legacy_host_mcp`) were deleted in S8 and the marker is retired.

`kriya/mcp/containment_adapter.py::map_capability_profile_to_containment()` is the ONE Kriya-owned, explicit mapping from `MCPCapabilityProfile` to `ContainmentProfile` — no server-supplied input (name/description/schema/annotations/arguments/results) is ever an input. `ContainmentProfile` gained purely-additive fields (all defaulting to today's exact pre-existing shape, zero behavior change for `PolymorphicValidator`/`service_runtime`'s own compile/test/managed-service callers): `mount_workspace`/`workspace_write` (no mount at all unless `workspace_read` or `workspace_write` is granted; `ro` vs `rw` otherwise — real bind-mount modes, not just a policy note), `additional_mounts` (a `MountSpec` per resolved `additional_read_paths`/`additional_write_paths` entry, at fixed Kriya-chosen container paths `/kriya/mcp/extra/{ro,rw}/<n>`), `resolved_env` (MCP's own SEC-003 `build_mcp_subprocess_env()` output baked into `-e` flags **verbatim**, deliberately bypassing the unrelated `_HOST_ONLY_ENV_VARS` filter built for host-path-shaped compile/test env values — that filter would otherwise silently drop an operator's own explicit, SEC-009-approved `mcp.<server>.env.HOME` override), `persistent_stdio` (`-i`, never `-t` — a pseudo-TTY would corrupt MCP's JSON-RPC line framing; lets `MCPClient`'s existing stdio reader/writer work completely unchanged, since the container's OWN foreground process — `docker run -i ... image mcp_command`, not a `sleep infinity` + `docker exec` placeholder — literally IS the MCP server, and `docker run`'s own subprocess stdin/stdout is what `MCPClient` already reads/writes), `run_as_uid`/`run_as_gid` (Task 7 non-root: `resolve_mcp_container_identity()` — the fixed "nobody" UID/GID (65534) when no write authority is granted at all; the REAL host UID/GID, fail-closed on mismatch, when a write mount exists, mirroring SEC-008's own `_resolve_acquisition_identity()` reasoning without touching that CLOSED registry-scoped code path), `authority_label` (the capability-profile digest, as `--label kriya.mcp-capability-digest=<digest>` — the audit chain server→digest→container instance, and what every real-OCI test's zero-leftover-containers check filters on).

`MCPNetworkAuthority.EXPLICIT_DESTINATIONS` is an explicit **STOP**, not an approximation: `kriya/tools/containment_oci.py`'s real per-run scoped-egress mechanism (SEC-006 — a dedicated Squid proxy container + fresh Docker network + in-container iptables/privilege-drop, all torn down after ONE finite acquisition command) is the closest existing primitive, but adapting it to a session-LIFETIME MCP connection (the proxy/network would need to live for the whole connection, with their own health-monitoring and cleanup wired into `MCPClient`'s own close sequence) is real, additional infrastructure work, not a bounded reuse — a server configured with `network: explicit_destinations` fails closed with a typed `MCPContainmentUnsupportedError` (a `ContainmentSetupError` subclass) the moment containment is required, never silently downgraded to `DENIED` (looks like a working config doing less than declared) or `UNRESTRICTED` (the exact silent widening this exists to prevent).

The container's OWN process (`docker run -i`) is what `spawn_mcp_process()` (`kriya/mcp/lifecycle.py`) spawns when a `command_prefix` is supplied — host CPU/memory rlimits are skipped in that case (meaningless for the lightweight `docker` CLI wrapper; the container's own `--memory`/`--cpus` flags, already derived from the SAME `mcp_lifecycle.cpu_seconds`/`memory_mb` bounds, are the real limit — and are a REAL cgroup hard limit even on macOS Docker Desktop, unlike host-mode `memory_mb`'s existing "advisory-only on macOS" limitation). Teardown has a SECOND lifecycle layer beyond SEC-004's own process-group kill: `PreparedContainment.cleanup` (`docker rm -f`) runs via `run_in_executor` (never blocks the event loop) in `MCPClient._close()`, bounded by its own SEC-009-governed `mcp_lifecycle.container_cleanup_timeout_seconds` (default 15s) — additive to, never a replacement for, `shutdown_grace_seconds`/`force_kill_reap_seconds`. A timeout here is logged, not raised, mirroring `terminate_mcp_process()`'s own "reap timeout after the forced kill is still terminal" precedent — `docker rm -f` is itself the forceful path.

Testing note: an MCP server's own code (the script/binary named in `mcp.<server>.command`/`args`) must be something the SELECTED CONTAINER IMAGE can already resolve — a bare command name on the image's own `PATH` (`python3`, matching `_select_image_and_cache_mount()`'s own detection), or a path inside a mount the operator's OWN capability profile already grants (e.g. `additional_read_paths` naming the directory holding a homegrown script) — never an absolute HOST-specific path (a venv's `sys.executable`, say), which cannot resolve inside the container's own filesystem namespace at all. This is inherent to the containerization model, not a TOOL-003 P2 limitation: a real npm/pip-distributed MCP server's code must already be baked into the image (or otherwise present) rather than fetched at container start, since `network=DENIED` blocks any runtime install.

**Honest security statement (state exactly, no stronger claim):** TOOL-003 P2 enforces the operator-authorized MCP capability profile at the OCI boundary from server startup onward, when `autonomy.mcp_contained_execution_required` is `True`. MCP invocation authority remains separately governed by TOOL-002. `EXPLICIT_DESTINATIONS` network authority is not yet enforceable (fails closed, never approximated). When `mcp_contained_execution_required` is `False` (the default), TOOL-003 P1's own P1-era statement still applies in full: an MCP process that starts still has the host capabilities of its execution environment.

### ShellTool package-manager network authority (`kriya/policy/execution.py`, `plugins/core_tools/__init__.py`) — SEC-005
**Closes the one genuine residual found by a dedicated SEC-005 reconciliation pass (2026-09-13).** SEC-005's own historical scope ("package-installation/network-access containment," a never-built "subprocess/package/network broker," `KRP-016`) was reconciled and found superseded: registry-scoped acquisition network authority is `SEC-006`'s (CLOSED), acquisition resource/privilege authority is `SEC-007`/`SEC-008`'s (both CLOSED), the configuration-authority floor underneath all of them is `SEC-009`'s (CLOSED), and MCP-mediated invocation/capability authority is `TOOL-002`/`TOOL-003`'s (both CLOSED) — no centralized broker was ever built or required, independently re-confirming `docs/architecture/SEC001_HOSTILE_CODE_CONTAINMENT_DESIGN.md`'s own §9 conclusion that `POL-001` closed the equivalent decision-gating scope via direct, call-site-by-call-site `ExecutionPolicy` consultation instead. The one property none of those owners covered: `plugins/core_tools/__init__.py::ShellTool._run` — "Execute arbitrary shell commands on the local machine" — constructed its `ContainmentProfile` with `network=NetworkAuthority.UNRESTRICTED` unconditionally, independent of command shape or `autonomy.contained_execution_required`, so a package-manager command (`pip install`, `mvn`, `npm install`, ...) run through `kriya tools execute shell "..."` got full host network even under a deployment with containment fully enabled everywhere else.

`kriya/policy/execution.py::classify_shell_acquisition_command()` (new, exported alongside the existing `extract_install_package_target`) is a deterministic, shape-based recognizer reusing the SAME `_command_matches_prefix`/`_INSTALL_COMMAND_PREFIXES` idiom POL-001's own INSTALL_PACKAGE detector already established — a new capability, not a new parsing approach. Returns `"registry_scoped"` for `mvn`/`mvnw` (ANY subcommand — Maven's dependency resolution is implicit on nearly every real invocation, unlike `extract_install_package_target`'s own narrower INSTALL_PACKAGE detector, which deliberately excludes Maven for exactly that reason) and `pip`/`pip3 install|download` (including venv-qualified `python -m pip`) — the two ecosystems `SEC-006`'s own `AutonomyConfig.acquisition_registry_hosts` already authorizes, reused as-is, never a second independently-maintained host list. Returns `"unmapped"` for a real, recognized package-manager shape Kriya has no registry-host authority for today (`npm install/ci/i`, `bundle install`, `gem install`, `cargo add`, `gradle`/`gradlew` any subcommand). Returns `None` for anything else, INCLUDING every near-miss (`pip list`, a command merely containing the word "pip", an unrelated executable) — deliberately conservative: this function only ever NARROWS authority relative to ShellTool's pre-existing baseline, never widens it, so a false negative costs nothing beyond today's already-accepted status quo while a false positive would incorrectly restrict a legitimate command.

Splits the shlex-tokenized command on shell control operators (`&&`/`||`/`;`/`|`/`&`) first, so a compound command (`pip install x && curl evil`) is recognized by ANY segment — narrowing the WHOLE process's network authority when any segment matches, since containment is per-process, not per-segment, and over-narrowing a compound command is always the safe direction. Then does ONE bounded level of `sh -c "..."`/`bash -c "..."` unwrapping (reusing the existing `_SHELL_WRAPPER_EXECUTABLES` set already used by `_check_command_allowlist`'s `COMMAND_SHELL_WRAPPER_REQUIRES_APPROVAL` rule) — deliberately NOT a general shell-language parser: subshells (`( ... )`), command substitution (`` `...` ``/`$(...)`), and an eval/xargs-launched package manager remain undetectable, disclosed explicitly rather than silently claimed as covered. An undetected compound form is identical to ShellTool's own pre-existing baseline (`UNRESTRICTED`) both before and after this change, so this is a disclosed limitation of shape-based recognition, never a regression.

(S7: `contained_execution_required` is now always true, so the registry-scoped branch below is the only one reachable; the unconditional `UNRESTRICTED` default described here applies to no project-controlled command any more.) `ShellTool._run` now selects, in order: `network=UNRESTRICTED` (the unconditional default, unchanged) UNLESS BOTH `autonomy.contained_execution_required` is `True` (the SAME opt-in flag `PolymorphicValidator`'s own acquisition path already gates on — extending, not duplicating, its existing meaning: "these paths must be really contained") AND the command classifies as `"registry_scoped"` (→ `NetworkAuthority.DEPENDENCY_REGISTRY_ONLY` + `network_destinations=AutonomyConfig.acquisition_registry_hosts`) or `"unmapped"` (→ `NetworkAuthority.DENIED`, never an approximated `UNRESTRICTED`). A deployment running with containment intentionally disabled (the packaged default) sees **zero behavior change** — Task-level invariant "preserve current documented behavior when containment is intentionally disabled" satisfied by construction, not a special case. Under `contained_execution_required=True` with `containment_backend` still `"none"` (a misconfiguration), the pre-existing `NullContainmentBackend` gate (unmodified) now correctly refuses to run a recognized package-manager command at all (`BackendUnavailableError`) rather than silently downgrading — the exact same fail-closed mechanism `PolymorphicValidator`'s own acquisition calls already rely on, reused, not reinvented.

Human confirmation (`requires_confirmation`/`-y`, `kriya/cli.py`'s `tools_execute`) and `ExecutionPolicy` mode/decision (POL-001's own `enforce_hard_invariants`/`evaluate()` calls earlier in the SAME method) are both structurally incapable of influencing this selection: `ShellTool._run(self, args)` takes no confirmation-related parameter at all, and the network-authority code path never reads any `PolicyResult` — proven identical network-authority selection under `mode="audit"` and `mode="enforce"` for the same command.

### Autonomous TOOL-subtask execution (`kriya/workflow/workflow_controller.py`, `kriya/workflow/subtask_executor.py`) — TOOL-001
**Enables `_run_structured_enforce` (the real, mutating, authoritative enforce-mode path — not `_run_structured_shadow`, which stays a hard stop for TOOL subtasks by its own non-mutating design, unrelated to security) to execute TOOL-tagged Subtasks for real, through `kernel.registry.get("tool", ...) → kriya.tools.tool.execute_model_authored()` (S1/S18). A planned call is governed SEPARATELY from the operator's `kriya tools execute` (`BaseTool.execute()`): one governance resolution (`resolve_planned_tool_governance`; each tool declares READ_ONLY / GOVERNED_SIDE_EFFECT / OPERATOR_ONLY; undeclared and non-shipped tools are unplannable) is projected by the Planner catalogue, enforced by plan validation (`PLANNED_TOOL_NOT_PLANNABLE`) and rechecked by the executor; `shell` and `validate_refactor` are OPERATOR_ONLY (refused `TOOL_OPERATOR_ONLY`); planned filesystem writes and git commits stay refused per call.** `kriya/workflow/subtask_executor.py::_execute_tool_subtask` (unchanged — the function `SubtaskExecutor.execute()` already dispatched TOOL-tagged Subtasks to, previously reachable only from `_run_structured_shadow`'s own non-mutating, TOOL-refusing branch) is now also called from `_run_structured_enforce`'s per-subtask loop, in a dedicated branch inserted BEFORE `_invoke_bounded_subtask`/`run_generation_workflow()` — a TOOL subtask never enters the MODEL-specific Quality-Gates retry loop, scope-conflict/recovery machinery, or obligation-ledger tracking, all of which are meaningless for a single deterministic tool call. No second execution primitive, no new policy engine, no broker: `subtask.tool_arguments` passes through `execute_model_authored()`'s validation (the tool's own `arguments_schema`), and each tool's own existing security boundary is what governs the call — `ExecutionPolicy`'s hard invariants and command allowlist for `ShellTool`/`GitTool`, TOOL-002's durable MCP invocation approval + TOOL-003's OCI capability containment for `MCPTool`, SEC-005's registry-scoped network authority for ShellTool package-manager commands — none of it duplicated or reimplemented at the SubtaskExecutor layer (Invariant: one security decision, one authoritative owner).

The blanket pre-execution refusal this depended on removing (`TOOL_SUBTASK_UNSUPPORTED_IN_ENFORCE`, previously turning ANY TOOL-tagged subtask into a whole-plan PLAN_REPAIR failure) is gone; `validate_plan()`'s own `available_tool_names` check (unchanged) still rejects an unregistered `tool_name` at PLAN-VALIDATION time, before execution — an unknown/malformed/stale tool_name still fails closed (`NEEDS_REVIEW`/`FAILED`), never substituted with a "closest match" (`ComponentRegistry.get()` is an exact-name dict lookup, no fuzzy resolution anywhere). Nothing in the TOOL branch reads `subtask.description`/planner rationale/labels as an authority signal — only the structured `tool_name`/`tool_arguments` fields ever reach `execute_model_authored()`.

**Retry/recovery cannot widen authority — proven as an absence, not a classifier**: the TOOL branch has no retry loop of its own at all; a non-`COMPLETED` result `break`s the per-subtask loop immediately (mirroring the MODEL path's own `if not passed: break`), so `_execute_tool_subtask` is structurally called at most once per subtask id per run, with the exact arguments the validated plan declared — no identity swap, no argument widening, no silent MCP→shell fallback, no direct-subprocess workaround. A `PolicyDeniedError`'s `reason_code` (whether from `ExecutionPolicy`'s hard invariants or TOOL-002's own MCP denial) is now surfaced into `SubtaskResult.reason_codes` — read off the real exception chain `execute_model_authored()` preserves (`ModelInvocationRefused` carries its own reason code), never re-derived — so a security denial is structurally distinguishable, as evidence, from an ordinary tool failure, without a second classification engine.

**Checkpoint/resume cannot bypass revalidation (Invariant 18) and never duplicates or retries an external effect (D1, 2026-10-28).** A MODEL subtask's "completed" resume record is self-verifying via the caller's own git tree_hash/base_commit match - the written file content IS the artifact - and an interrupted MODEL subtask is safely re-runnable (its `in_progress` semantics are unchanged). A TOOL subtask's effect (an MCP `tools/call`, a Maven build, ...) leaves no such trace, so its persisted lifecycle is the only truth, and it is `durable STARTED -> effect -> durable COMPLETED`: the STARTED marker (`kriya.control.state.SUBTASK_STATE_TOOL_STARTED`, `tool_started`) is written with the strict durable writer (`kriya/repository/atomic_write.py::durable_atomic_write_bytes`: temp write -> file fsync -> atomic replace -> parent-directory fsync, every step required, a failure raises `DurableWriteError`) BEFORE the effect (a failure: typed `TOOL_STARTED_NOT_DURABLE`, the effect never runs); COMPLETED is written the same way AFTER it and before success is authoritative (a failure: `needs_review` `TOOL_COMPLETED_NOT_DURABLE`, the tool's output kept as evidence, the in-memory state reverted so nothing later resurrects `completed`, never retried). `kriya/workflow/resume_support.py::classify_tool_resume` is the ONE authoritative resume classification and the enforce loop only consumes it: durably COMPLETED -> the effect is NEVER run again for that execution (authority is revalidated through the effect-free seam `subtask_executor.revalidate_tool_subtask_authority` -> `tool.revalidate_model_authored`; for MCP that is the same `_decide_invocation_authority` TOOL-002 durable approval / TOOL-003 capability decision `_run` makes, so a revoked approval still refuses without dispatching); `tool_started` (or a legacy `in_progress` record of a TOOL subtask) with no durable COMPLETED -> `needs_review`, never auto-retried. The ControlState is ONE document per workspace, so the one run gate (`assess_workspace_commit_state`) reports `UNRESOLVED_TOOL_EXECUTION` for it (resume, a fresh run and a different plan are all refused with the bytes untouched; the caller's own run is excluded; `kriya runs recover` cannot settle it - a person inspects it and archives `.kriya/control/state.json`), retention never erases it, and an existing but UNREADABLE control state is never read as absent (`ControlStateUnreadableError`, `CONTROL_STATE_UNREADABLE`; the bytes are preserved and never overwritten). The direct operator path (`kriya tools execute`) follows the same lifecycle through the RunRecord's optional `tool_execution` field (`started` durable before the effect; the terminal state durable BEFORE the result is printed). Durability target: the portable fsync + atomic replace + parent-directory fsync contract; no `F_FULLFSYNC` and no claim about physical-media or power-loss persistence beyond it. Not covered (owner-visible): a core tool's per-effect ExecutionPolicy decision is not re-evaluated for an already-completed effect on resume (the default `BaseTool.revalidate_authority` adds nothing beyond the declaration; MCPTool overrides it); a TOOL subtask the tool itself reported FAILED keeps its existing retryable semantics.

**Every atomic write is crash-durable (WAVE8 OI-03/OI-04, 2026-11-06).** `kriya/repository/atomic_write.py::atomic_write_file` has ONE path, `durable_atomic_write_bytes`: temp beside the target -> write -> flush -> fsync(temp) -> `os.replace` -> fsync(parent directory) (POSIX; Windows has no directory fsync, the step is skipped there; macOS `os.fsync` is not `F_FULLFSYNC`, no drive-cache claim). A failure at any step raises `DurableWriteError` (an `OSError`, `.step` names it), removes the temp file and leaves the destination intact before the replace. `durable=` is accepted for source compatibility and is only the caller's declaration of an authoritative transition (the D1 fault harness counts those); no caller carries its own fsync code. The rollback writer also fsyncs the directory. Pinned by `tests/test_wave8_durable_writer_contract.py` (every entry point, every step, mutants). Characterization tests that pinned the old behaviour (`test_the_default_writer_is_unchanged_it_performs_no_fsync_at_all`, the leftover-temp test, the commit golden's op traces) were updated as STRICTER, never looser.

**A planned `git diff` obeys the direct-read authority (WAVE8 OI-172, 2026-11-06).** `GitTool.authorize_model_invocation` lists the changed tracked paths (`git diff --name-only -z --no-renames`, same containment profile, content filters refused first) and judges each by `_authorize_read_target` - the one function the filesystem tool's read and blame's file also use (credential stores, containment, PLAT-039 control paths). The first refused path refuses the whole call before git prints anything (`SENSITIVE_PATH_DENIED`, naming that path only); a listing git cannot give refuses (fail closed). It is an authority check, not an output filter. Reachable content surfaces of GitTool: `diff` (this) and `blame` (already authorized); status/log/branch print no file content; show, grep, `log -p` and free arguments are not exposed. Pinned by `tests/test_wave8_git_content_authority.py`; the census row `GitTool._changed_paths` is TRUSTED_NULL.

**Terminal correctness (Invariant 20).** `kriya/workflow/workflow_controller.py::all_subtasks_completed()` (also extracted as a small pure function) is a plain AND-reduction over every current-plan subtask's own structural `SubtaskStatus` — a TOOL subtask reporting `COMPLETED` (even if its own `tool_output` happens to contain text like `"PASS"`) can never make the aggregated `quality_gates_passed` true while any OTHER subtask (MODEL or TOOL) in the same plan is not itself `COMPLETED`; nothing in this reduction ever inspects `tool_output`/`files` content — normal Kriya verification (the MODEL path's own unmodified Quality-Gates/compile/test loop) still owns whether the workflow may terminate successfully. **Direct `kriya tools execute` runs (D1 slice 4, completed by W2-02, 2026-10-28, commit `b4ec155`).** RunRecord is the single lifecycle authority for a direct run: `RUNNING + tool_execution=started` is written durably BEFORE the effect, a durable terminal state before success is reported; the set of resolving states (`completed`, `failed`, `abandoned`) is CLOSED, so `started` and any unknown value is UNRESOLVED and blocks every mutating run. `kriya runs status`/`recover` read the SAME `RunRecord.unresolved_tool_execution` as the gate: `MANUAL_ACTION_REQUIRED` with the typed reason `UNRESOLVED_TOOL_EXECUTION`, `recover` never touches it and never reports CLEAN while the gate blocks.
