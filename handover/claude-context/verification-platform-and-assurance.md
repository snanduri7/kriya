### Linux execution semantics (`kriya/tools/sandbox.py`, `kriya/tools/containment_oci.py`, `kriya/core/file_stamp.py`)
macOS hides several Linux behaviours, so verify containment/resource changes on Linux too: `scripts/linux-repro/run.sh <rev> [pytest args]` (ubuntu 24.04, uid 1001, its own docker daemon; a clean clone, never the working tree's ignored state).
- **JVM resources.** A JVM-backed host process gets JVM heap/metaspace/direct bounds in `JAVA_TOOL_OPTIONS`, never RLIMIT_AS (`sandbox.resource_plan`; typed toolchain or argv[0] launcher, never shell text); everything else keeps RLIMIT_AS.
- **OCI identity.** A container writing a host mount runs as the host uid:gid (`resolve_host_writer_identity`, SEC-008's rule), never root; `--cap-drop ALL` stays. ShellTool (operator path) mounts the PROCESS folder (the owner folder); without a git-metadata export a real `.git` directory is mounted read-write (S18-PREFLIGHT.md R22/R26).
- **Nothing of Kriya's in the candidate tree; the dependency directory is EPHEMERAL (R3, Wave-2 final closure, 2026-10-28).** The Maven local repository and the Gradle user home a gate mounts live under the state root at `gate-caches/cache-<pid>-<random>/<tool>` (`kriya/tools/dependency_cache.py`, `PolymorphicValidator._dependency_cache_dir/_maven_cache_dir`) - project build tools walk the tree (Apache RAT, NoHttp checkstyle failed every build on cached artifacts), so never inside it. It is created empty by the OUTERMOST verification scope (a `_verification_gate`, a `verification_session`, or an authority-bundle run via `PolymorphicValidator.dependency_cache_scope()`), shared by that scope's offline execution and the registry-scoped acquisition that precedes it (the offline retry finds what the acquisition fetched), and removed when the scope ends; two scopes never share a layer. There is NO persistent per-workspace cache: it used to be one `dependency-cache/<tool>/<workspace key>` directory mounted read-write into every gate, and MEASURED at f3b7d39 a candidate test could rewrite a cached jar that a later gate (Maven, Gradle, the authority oracle) then trusted. Kriya has no acquisition that runs no candidate code (a POM names extensions and plugins), so there is no safe promotion seam; the accepted cost is reduced cache reuse (every gate re-acquires), and the pre-R3 `dependency-cache/` and in-tree `.kriya/m2_cache` directories are unprovenanced, never read, moved or mounted (and never deleted). A writable cache that is not a layer this module made is the typed refusal `PERSISTENT_DEPENDENCY_CACHE_WRITABLE` from `OCIContainmentBackend.prepare` (before any docker resource); a cache asked for outside a scope is `DEPENDENCY_CACHE_SCOPE_REQUIRED` (`kriya.tools.containment.DependencyCacheError`). **Runtime verification (Option A, owner decision 2026-10-28).** A runtime session (`run_app_sequence`) used to RELY on an earlier TEST gate having warmed the persistent cache with the project's test-scope dependencies (`mvn exec:java` resolves TEST scope). It now fills ITS OWN session layer: Maven acquisition is two registry-scoped phases into the SAME layer (the named plugins' `help` in an empty directory, then `mvn dependency:resolve` in the project; `PolymorphicValidator._acquire_maven_project_dependencies`, bound floored at 300 s, honours the run deadline) and the runtime command then runs offline with `DENIED` network. Acquisition runs no application and no test; the candidate POM IS loaded in the dependency phase (same trust class as the compile/test acquisition). A failed acquisition is the typed `MAVEN_ACQUISITION_INCOMPLETE:` infrastructure no-verdict (`RUNTIME_VERIFICATION_DEPENDENCY_UNAVAILABLE`), never a source defect and never Developer-repairable; candidate test-source compile errors are never an acquisition prerequisite. Plugin-less Maven runtime commands keep the "no acquisition" contract (they run offline against an empty layer). The Gradle runtime consumer has no cache consumer (the compile gate builds in its own scope; `java`/`gradle` runtime commands mount no layer). Tests: `tests/test_r3_runtime_dependency_layer.py` (Docker tier), `tests/test_runtime_maven_acquisition.py`. Tests: `tests/test_r3_dependency_cache_poisoning.py` (Docker tier: Maven gate, Gradle gate, authority bundle; each failed on f3b7d39), `tests/test_maven_cache_location.py` (host-side contract and guard). `tests/_dependency_scope.py` holds a scope open for tests that call the runners directly. A candidate worktree's `.git` FILE points at a gitdir the container does not mount; `containment_oci.dangling_gitfile_mask` masks it with `/dev/null` (ro) so the tree reads as "no repository" (git-commit-id-maven-plugin failed on the dangling pointer); the host gitdir is never mounted.
- **The Python project venv has the lifetime of the verification scope that builds it (R3 Python sibling, 2026-10-29).** `<worktree>/.kriya/venv` (`PolymorphicValidator._ensure_project_venv_impl`) used to be reused across attempts while its pip-install step runs candidate-declared install and build hooks with the venv WRITABLE (every gate mounts it read-only; MEASURED: a test cannot write it). MEASURED at ebd022a: a hook in attempt 1 planted a pytest plugin in site-packages and attempt 2 (same worktree, benign dependency, identical declaration, an honest FAILING test) passed; `VENV-ADDITIVE-REUSE-001` compares declared specifier STRINGS, never bytes, so it only caught a DROPPED dependency. Now `dependency_cache_scope()` (the same outermost scope as the dependency layers) removes the venv when it opens (`kriya.tools.dependency_cache.discard_project_venv`; one that cannot be removed is the typed refusal `PROJECT_VENV_NOT_DISCARDED`) and when it closes, and clears the scope's install memo; the venv is shared by the gates nested in one scope and by nothing else (every `compile_check` / `run_tests` / `run_app_sequence` / authority run builds its own: the accepted cost is one `pip install` per scope). A venv asked for outside a scope is the typed refusal `DEPENDENCY_CACHE_SCOPE_REQUIRED` - so the managed-service admission (which grounds the service interpreter, i.e. builds the venv) and its run are ONE `verification_session` (`runtime_verification._execute_managed_service_verification`). Tests: `tests/test_r3_python_venv_scope.py` (host lifecycle + two real-Docker cases), `tests/test_s4_1_managed_service_view.py`.
- **Did the target process start? (FINITE-LAUNCH-TARGET-START-001).** The OCI finite-command backend owns this fact; consumers receive it typed (`ProcessResult.target_started`, `False` only when the target never started) and never infer it from exit code 126/127 or English stderr (Maven/Gradle images route argv through a shell entrypoint whose own failed `exec` exits 127 after the container started, so Docker's state cannot tell it from a program that exits 127). `containment_oci._finite_launch_stage` wraps the TARGET argv as `/bin/sh -c 'trap ... EXIT; exec "$@"' kriya-launch <nonce> <argv...>`; before the `exec` the script writes ONE `KRIYA_LAUNCHER_REACHED:<nonce>` record; `exec` replaces the shell, so the EXIT trap, which writes `KRIYA_TARGET_NOT_STARTED:<nonce>` as the last stderr line, runs only if the kernel exec failed. `FiniteLaunchStage.read` reports STARTED only when the reached record is present and no not-started record follows it (exact per-run nonce, the latter as the last non-empty line; both stripped): a run with NO reached record never reached the launcher (a Docker refusal before any container exists such as a memory limit below 6 MB, rc 125; an image without `/bin/sh`) and is NOT_STARTED whatever status it answered, while a started target that exits 125 stays STARTED. `FiniteLaunchStage.wrap` refuses an empty argv (`exec` with no operands is a successful no-op); `['']` is a real target that cannot start (rc 126, NOT_STARTED). Consumers: replay (`not_executed`, blocking, S6 contract unchanged), `run_app_sequence` (a step with `exit_code None`, sequence stops), `run_pom_validate` (`MAVEN_INVOCATION_FAILED`; the offline attempt does not fall through to acquisition), `PolymorphicValidator._run_gradle_cmd` (`GRADLE_INVOCATION_FAILED`, no acquisition; carried by the Gradle compile/test gates and the authority prepare), and the authority verify (`AUTHORITY_EXECUTION_UNAVAILABLE`: a verifier that never started is never read as PASS/FAIL from its launcher status). Deliberately unwrapped: managed services, MCP persistent stdio, pinned `image_reference` profiles. Intentional contract (FINITE-LAUNCH-ENOEXEC-001; owner canonical statement 2026-10-27: contained finite-command execution uses the Kriya-owned launch-stage execution semantics, so an executable text script without a shebang may be interpreted by the launch-stage shell rather than reproducing raw `execve` ENOEXEC behavior; not to be reopened without new evidence of an existing external/direct-exec contract): dash runs an executable file that has the exec bit but no shebang through its ENOEXEC fallback (`/bin/sh file`), so such a project script RUNS and is STARTED - the fact is true (a process did start), the isolation is unchanged (same container, mounts, environment, hardening), and the native alternative (runc: a bare rc=1 `exec format error`) is the ambiguity the stage exists to remove; pinned by a real-Docker test. Tests: `tests/test_finite_launch_target_start.py` (real Docker for the contract matrix and consumers); `tests/_containment_standin.py` models the stage minimally for the Docker-free semantic tier.
- **S8 (2026-10-27): no project-controlled host execution remains reachable.** The legacy host branches left behind by the secure-default migration are deleted (the host javac/pip/Maven/Gradle pass-throughs, the host venv and interpreter, the host venv seal `venv_integrity.py`, the (None, None) host profile, the host Semgrep provider, the jdtls spawn, the host shell run, the MCP start flag, the host artifact-preparation branch); `tests/test_s7_s8_list.py` pins that only the five record/identity/report readers still read the decision, `tests/test_s8_host_branches_are_gone.py` pins the absences, and `tests/containment_s8_list.py` + `tests/containment_h_ledger.py` record each deletion with its replacement control. - **Stat caches.** A stat-validated read cache uses `file_stamp.unchanged_since` (settled-when-cached), never a bare mtime compare; tests exercising reuse settle their files with `os.utime`.
- **Image presence is two witnesses (IMAGE-INSPECT-FALSE-UNAVAILABLE-001).** `inspect_local_image` is the one owner. A healthy `docker image inspect <reference>` is the whole answer (no listing). The listing yields presence and the id only; the runtime/build-tool versions are still observed by running the image id. Evidence: `ImageInspection.second_witness`. ### Runtime verification prerequisites, acquisition, entrypoint ownership and resource grounding (`kriya/tools/validate.py`, `kriya/workflow/failure_grounding.py`) — D3 / D2B / D4 / D5
- **Prerequisites (D3).** A runtime gate (`run_app`/`run_app_sequence`) establishes its own prerequisites from the CURRENT source: `PolymorphicValidator._prepare_runtime` runs the existing compile gate (`mvn clean compile`, bounded by the run's root deadline) before any command consuming a Maven project's classes (`mvn ...`, `java` on `target/classes`), whatever the model's command says. Never rely on `target/` from an earlier work unit: each reset is `git clean -fd`, which deletes an untracked `target/` and keeps an ignored (stale) one. A failed build runs nothing: `RUNTIME_PREREQUISITE_BUILD_FAILED` (verification infrastructure). Other stacks prepare nothing (Python is interpreted; raw `javac -d` compiles in its own command).
- **Acquisition (D2B).** The runtime step's Maven acquisition is tooling-only (`_run_maven_cmd(tooling_only=True)` -> `_acquire_maven_tooling`): `mvn <coordinate>:help` for each plugin goal the command names (the POM's declared coordinate when present, read as XML), registry-only, in an empty Kriya-owned directory mounted as the container workspace (`build_containment_profile_and_backend(workspace_path=)`); the candidate's goals never run with network, and a command naming no plugin gets no acquisition. Compile/test keep the goal-derived acquisition (those goals build/test candidate code by design).
- **Entrypoint ownership (D4).** A missing main class is classified by who chose it, never "infrastructure" by default. When a runtime step fails, `PolymorphicValidator.diagnose_runtime_entrypoint` records a deterministic diagnosis on the fresh build: requested vs effective entrypoint, provenance (`KRIYA_COMMAND` / `CANDIDATE_BUILD_CONFIG` / `UNKNOWN`), source and compiled-class existence. It reads the command, the POM as XML, and the tree. Maven precedence (measured): a POM `exec-maven-plugin` `mainClass` (`default-cli` execution > plugin > pluginManagement) beats `-Dexec.mainClass`. `acceptance.classify_runtime_entrypoint` then classifies it; the JVM's reported class must equal the diagnosed one, and UNKNOWN keeps the old behaviour:
  - A: candidate config names a class that doesn't exist → `CANDIDATE_RUNTIME_ENTRYPOINT_INVALID`, a candidate failure grounded to `pom.xml` (tier `authoritative_deterministic`).
  - B: Kriya's own command names it → `RUNTIME_COMMAND_ENTRYPOINT_INVALID` (infrastructure).
  - C: class declared and built but not loaded → `RUNTIME_ENTRYPOINT_NOT_LOADABLE` (infrastructure).
  - D: class declared but not built → `RUNTIME_ENTRYPOINT_NOT_BUILT` (infrastructure).
  From a verification-only unit, case A reuses the existing grounded cross-owner recovery: `PLAN_SCOPE_DEFECT` reopens the file's owner for exactly `[pom.xml]`. The unit's own scope is never widened, and Kriya never rewrites the POM.
- **Resource grounding (D5).** For a `run_verification` failure, `attribution._attribute_from_locator` first asks `failure_grounding.ground_runtime_resource_failure`.
  - **Measured formats only.** `class path resource [p]`, `file [p]` and `classpath:p` (Spring 5.3 under `mvn -e`).
  - **Resolution.** Exact workspace path, then resource-root path (`src/{main,test}/resources/`), then a unique bare basename. All exact matches against the candidate files; an absolute path only via `workspace_root`. Ambiguous, unresolved or outside = no resource grounding, old behaviour.
  - **Ranking.** The deepest exception naming a resolvable candidate resource decides, and the resource outranks the stack frame that loads it. Exception: if the innermost exception has a candidate frame its enclosing one lacks (candidate code threw), the stack locator stands.
  - **Same tier, same recovery.** Tier stays `locator`; recovery and scope rules are unchanged.
  - **Owner evidence.** The reopened owner's `raw_evidence` is `grounded_evidence_excerpt`: the 2000-char head as before, unless the head names no grounded file and the output does later. The window then starts at that line, or, when it is a stack frame, at the header of the exception block that frame belongs to (D5b: `x.y.SomeException: msg`, `Caused by:`, `Exception in thread`, `class x.y.SomeException:`; found within 5 lines above the block's frames, else the frame line).
- **Tests.** `tests/test_d3_runtime_prerequisite.py` (real Maven), `tests/test_runtime_maven_acquisition.py` (one real-Docker case: the candidate runs exactly once, offline), `tests/test_d4_runtime_entrypoint_ownership.py`, `tests/test_d5_runtime_resource_grounding.py` (real runtime output fixtures; one real Spring/Maven case). Evidence: `evidence/demo-defects-d3-d2b/`, `evidence/demo-defect-d4/`, `evidence/demo-defect-d5/`.

### Maven POM validation result (`PolymorphicValidator.run_pom_validate`, `dependency_execution.classify_maven_validate_failure`, `gate_orchestrator._run_pom_validation_gate`) — F7 / OI-83
Invariant (owner, Wave-1 closure delta): `no trustworthy validator verdict -> no candidate conviction`. A non-zero `mvn validate` convicts the POM (`pom_semantic_validation`, the POM offered to the Developer) ONLY when Maven ran, was not timed out or signal-killed, printed NO resolution / transfer evidence and printed located POM-model diagnostics. Every other failure carries a typed `environment_reason_code` (`MAVEN_INVOCATION_FAILED`, `MAVEN_VALIDATE_TIMED_OUT`, `MAVEN_VALIDATE_TERMINATED`, `MAVEN_VALIDATE_RESOLUTION_UNVERIFIED`, `MAVEN_VALIDATE_NO_DIAGNOSTICS`), keeps the captured stdout / stderr, and the gate raises the existing `verification_infrastructure_failure` via `_stop_on_environment_gate_result` (STOP_ENVIRONMENT; nothing is offered to the Developer). Resolution evidence is checked before model messages (a cascade is not a verdict); an ambiguous parent / dependency / plugin resolution result is infrastructure. Any other exception propagates unchanged - never a pass (OI-83). Controls are REAL recorded Maven output (`tests/fixtures/maven_validate`, `tests/fixtures/oracle_preflight/env-T2-empty_maven_repo.txt`). Pinned by `tests/test_pom_validate_fail_closed.py` and `tests/test_oi83_pom_validate_propagation.py`. Separate finding F9 (NOT changed): the Maven/Gradle compile adapters (`kriya/capabilities/maven.py`, `gradle.py`) return a missing executable as a plain failure, left to the retry strategy's text classifier (`classify_environment_failure`, `[Errno 2]` only), and log-and-fall-through on any other exception.

**Candidate model text is not resolution evidence (W2-16a, Wave-2 Step 3).** Maven quotes the candidate's own POM values (packaging, module name, id, coordinate, scope, the text around a parser fault) inside its model-problem lines, so resolution-looking words in such a value must not read as a failed dependency resolution. `dependency_execution.maven_resolution_decision_view` is the ONE text view the Maven resolution/acquisition decisions read: it drops the lines whose opening is in the closed table `_MAVEN_MODEL_PROBLEM_WRAPPER_RE` (`Unknown packaging:`, `Child module `, a quoted field path `'...' with value|for `, `The project <gav> (<path>) has N error(s)`, `Malformed POM `, `Non-parseable POM `, behind repeated `[ERROR]`/`[FATAL]`/`[WARNING]` markers) and nothing else. It is applied inside `classify_maven_offline_failure_text` (so `_run_maven_cmd`'s acquisition trigger, `maven_execute_offline` and the validate classifier) and in the validate classifier's transport check and the compile classifier's resolution check; the captured output is never replaced. Genuine resolution openings (`Non-resolvable ... POM`, `Unresolveable build extension`, `Plugin ... could not be resolved`, `Failed to execute goal`) and `Internal error:` are deliberately NOT in the table: an unlisted opening stays in the view (fail closed). Known residuals: a candidate value containing a newline can forge a resolution line (a stop, never a pass or a conviction); an `Internal error:` line (an invalid `<modelVersion>`) that quotes the offline wording can still read as a missing dependency (stop -> stop). Tests: `tests/test_w216a_maven_model_echo.py` over `tests/fixtures/maven_validate/recorded_model_echo.json` (real Maven 3.9.16).

### Capability adapters (`kriya/capabilities/`) — Capability Adapters R1
- **Ports.** `LanguageAdapter` (`has_sources`, `source_files`) and `BuildAdapter` (`detects`, `output_roots`, `compile` -> result or `None` = not decided, `run_tests`); closed in-process registry (`JAVA`, `PYTHON`, `MAVEN`, `GRADLE`, `PIP`, `build_adapter_for_tool` via `BuildAdapter.invokes`), no plugin discovery.
- **Slices so far.** Maven compile/test gates, output roots and the `pom.xml` marker in `MavenBuildAdapter`; Gradle (`build.gradle` marker, `./gradlew`-else-`gradle`, `compileJava`, `test --tests`, output roots) in `GradleBuildAdapter`; Java source detection/enumeration in `JavaLanguageAdapter`; Python's marker-free source walk in `PythonLanguageAdapter`; the Python markers (requirements.txt, pyproject.toml, setup.py, setup.cfg, Pipfile), syntax compile gate (contained `py_compile`, else in-process `compile()`), pytest gate (each target its own argv entry; exit 5 passes) and `__pycache__`/`.pytest_cache` output roots in `PipBuildAdapter` (interpreter/venv resolution stays `PolymorphicValidator._resolve_python_interpreter`, shared with runtime verification). `BUILD_ADAPTERS` order is precedence (Maven, Gradle, pip; Java markers outrank Python); the validator and `toolchain._goal_or_repo_targets_java` iterate it. The raw javac fallback (`javac -proc:none -d <ws>/build` over the changed `.java` files that exist; no classpath/release flag; failure enriched by the resolver; no test runner; `javac -d X` output root) is `JavacBuildAdapter` (`JAVAC`): not in `BUILD_ADAPTERS` (no workspace declares it, `detects` is always False), reached only after every Java build adapter left the compile undecided. Ruby is still inline; Kotlin-DSL-only roots and Poetry/Pipenv dependency installation are recorded gaps.
- **Rules.** An adapter runs only through the validator handle it is given (containment, acquisition, gate binding), never a process of its own; the moved validator seams carry no Maven, Gradle or pip literal (AST tripwire in `tests/test_capability_adapters.py`). Patch points stay on `PolymorphicValidator` (`_run_maven_cmd`, `_run_cmd_with_timeout`, `_resolve_python_interpreter`).

### Platform services (`kriya/platform/`) — ARCH-PLATFORM-001
- **Mechanism behind ports.** OS-specific mechanism lives only in `kriya/platform/`, composed once by `platform_services()` (`override()` for tests). Core code asks capabilities (`ENFORCED`/`ADVISORY`/`UNAVAILABLE`); an unavailable required capability is `PLATFORM_CAPABILITY_UNAVAILABLE`, never a fallback. Adapters never grant authority.
- **Ports.** `filesystem_semantics` (path identity), `WorkspaceLockPort`, `ProcessControlPort`, `ResourceLimitPort`, `HostIdentityPort`, plus the toolchain locator and host properties. `PlatformServices.identity()` (providers + capability statuses) is bound into release certification (`kriya/core/release_identity.py`).
- **Guard.** `tests/test_platform_architecture_guard.py` forbids `fcntl`/`resource`/`pwd`/... imports, `sys.platform`/`os.name`/`os.getuid`/`os.killpg`/POSIX-only `signal.SIG*`, and any `start_new_session=` outside `kriya/platform/`. Its `TEMPORARY_ALLOWLIST` is empty and may only stay so (never workflow/policy/control/config/metrics). Core must import with those modules blocked (checked in a subprocess and on `windows-latest`).
- **Processes.** Every ProcessController and MCP subprocess spawns through `kriya/tools/process.py`'s `_spawn_popen`/`spawn_subprocess_exec_fail_closed`, which merge `ProcessControlPort.spawn_options()` and call its `attach(process)` right after creation (POSIX: a no-op; a Windows Job Object provider assigns the job there); trees are killed only by `terminate_process_tree`. No provider = typed `ContainmentSetupError` before spawn, never a direct-child kill. A failed `attach` kills and reaps the new process, then raises `ContainmentSetupError` (the `containment_setup_failed` stop). jdtls (`kriya/tools/lsp.py`) is outside the port: PLAT-LSP-TREE-KILL-001.
- **Path identity.** Security decisions about paths use `filesystem_semantics.path_relation`/`path_identity` (stat identity, fail closed on unknown, no probe files), never string prefixes.
- **Control paths.** Candidate writes (`AuthorizedFileWriter`) never reach `.git/**`/`.kriya/**` (`TRUSTED_CONTROL_PATH_DENIED`, plus a terminal-commit backstop); Kriya's own `.kriya/` state is written only through `kriya/control/control_store.write_control_file`. A PLANNED shell step cannot run (S18: OPERATOR_ONLY); the operator's own `kriya tools execute shell` runs in the process folder with the operator's authority and can write both.
- **Windows.** `PORTABILITY_ARCHITECTURE_DEFINED / RUNTIME_NOT_SUPPORTED`: core imports; there are no Windows providers yet. See `handover/PLATFORM_*.md`.

### Production metrics (`kriya/metrics/`) — PRD-033
- **Derived only.** Metrics come from persisted evidence (traces rows, RunRecords, adjudications), never a second truth. `kriya/workflow` never imports the package.
- **Content-free.** Projections never read the goal, prompts, gate output or event messages (canary test). A new metric reads only a typed field or event.
- **No fake zeros.** A missing metric is UNAVAILABLE, never 0.
- **Adjudication.** False success and regression escape come only from `kriya metrics adjudicate`, its store's only writer (structural test).
- **Thresholds.** None ship in the repo; they are the operator's, outside every workspace. - **New decisions.** Add a typed event (e.g. `approval.decision`) rather than parsing text.

### Attempt evidence recorder (`kriya/core/attempt_evidence/`) — LR-R1-M1
- **Observational only (I-2).** Never changes request bytes, workspace, result, retry/fallback or control-plane outcomes; every emit catches `Exception` (degrades the store), never `BaseException`; a store that cannot open is `RECORDER_UNAVAILABLE` and the run continues (D5). `tests/test_lr_r1_m1_equivalence.py` proves it across `full`/`digest_only`/`off`/fault modes; the `evidence` config section is excluded from the config fingerprint.
- **Producers use `scope.py` only.** Identity comes from ContextVar scopes (run > unit invocation > attempt = the whole retry-loop iteration > call > wire), never from the caller. Gate outcomes go through `GenerationState.record_gate_outcome`/`restore_gate_outcomes` (AST tripwire: no direct `gate_outcomes` mutation). New record kinds must be added to `model.KINDS`.
- **Layout is internal (I-1).** Consumers use `reader.py` / `explain.py` / `kriya evidence ... --json`; a tripwire rejects code naming the store's files; production never imports the reader (the CLI and explainer are the listed consumers).
- **D7 codes.** `GenerationState.stop_reason_evidence` (a frozen `StopReasonEvidence(code, message)`, `diagnosis_codes.py`; these stops are not environment failures, they only reuse the `environment_failure` stop channel) is read only by the recorder (structural test) - never by a decision; `Failure.diagnostics["reason_code"]` was rejected for this because it feeds the ProgressVector.
- **Retention** (`retention.py`) at run close; `kriya evidence show|explain|verify|prune`; doctor row `evidence.attempt_recorder` (never required). Docs: `docs/design.md` §2.9l.

### Live model certification (`kriya/core/model_certification.py`) — PRD-035
- **What it certifies.** An exact identity (runtime digest + inference-settings digest + environment digest + case-set version), never a model name.
