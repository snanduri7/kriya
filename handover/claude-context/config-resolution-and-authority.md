# Configuration resolution and SEC-009 configuration authority

_Moved verbatim from CLAUDE.md on 2026-10-07 (loaded on demand, not every session). Read before modifying any module named here. Code is ground truth; update this file when behaviour changes._

## Configuration resolution

`kriya/config/config.py::load_config()` layers config in this order (later wins, dicts are shallow-merged one level deep):
1. `kriya/config/default_config.yaml` (packaged defaults)
2. `kriya.yaml`/`kriya.yml` — first checked at the AUTHORITY ROOT of the CWD (D-001, 2026-10-23: the root of the Git repository that contains the CWD, found by an upward `.git` search that never crosses a Kriya-owned directory; the CWD itself when it is in no repository, a nested repository or linked work tree being its own root), then in the Kriya install directory, unless `--config` is passed explicitly. One repository, one configuration: `<repo>` and `<repo>/sub` read the same file, and the workspace SEC-009 judges (trust-path containment, an explicit `--config`'s provenance, the `paths.state` rule) is that root too. A `kriya.yaml`/`kriya.yml` in a directory BETWEEN the CWD and the root is not read, so it is refused with a typed `ShadowedConfigurationError` (`kriya/config/resolution.py`) rather than ignored (it may carry the tighter bound); `--config` is an explicit choice and is never shadow-checked
3. `AppConfig` (pydantic model in the same file) validates the merged result

Relative `paths.*` and `plugins.directory` values are resolved against the directory the config file was loaded from (or the install dir for the packaged default), using `os.path.realpath` (resolves symlinks) — `paths.state` (traces.db) resolves ANY relative value against `config_dir`, and inside the workspace must sit beneath `<workspace>/.kriya/` (typed `StateDirectoryError` otherwise; `.kriya/state` is valid, `./state`/`./logs` are not). Every filesystem-target field is canonicalized ONCE in `resolve_config_state()` before classification, so the value SEC-009 inspects and the value later opened can never diverge. **`kriya.log`/run-log locations (PRD-010 logging closure) are owned by `kriya/core/logging_setup.py` - never the process CWD:** directory = `KRIYA_LOG_DIR` > `logging.directory` (absolute; `~` expanded and realpath'd once in `resolve_config_state()`, a relative value is a typed `LogDirectoryError`; any string is `SECURITY_AUTHORITY`, `null` is `REPOSITORY_SAFE`) > `~/.kriya/logs`. Application log `<dir>/kriya.log` (`logging.file_enabled`); per-run log `<dir>/runs/<run_id>/kriya.log` (`logging.run_file_enabled`), attached around the whole run by `begin_mutating_run()`. `doctor --production` logs to the console only and checks the directory as `persistence.logs`. `tests/conftest.py` points `KRIYA_LOG_DIR` at a session temp dir so the suite never writes the real `~/.kriya/logs`. **Run history (`traces.db`) is state, owned by `kriya/core/state_paths.py`:** `KRIYA_STATE_DIR` > `paths.state` (SEC-009-classified like the other `paths.*`; null is REPOSITORY_SAFE) > `~/.kriya/state`, always `trace_db_path(cfg)` - never the log directory. `paths.logs` and `logging.file` were REMOVED: a config naming either gets `RemovedConfigFieldError` with the replacement field (`REMOVED_PATHS_LOGS_MESSAGE`/`REMOVED_LOGGING_FILE_MESSAGE`), never reinterpreted; `tests/test_state_location.py`'s repository guard fails if either, or `logs_path`, reappears in `kriya/`. A pre-move database at the historical default `<install dir>/logs/traces.db` is reported by `kriya traces` and `doctor --production` (`persistence.traces` WARN) and copied only by `kriya traces --migrate-legacy [--legacy-path <traces.db>]` (SQLite backup, refuses an existing target, never merges or deletes). Workspace `.kriya/` run control state is unaffected. `tests/conftest.py` gives every test its own `KRIYA_STATE_DIR`; tests locate traces via `trace_db_path(cfg)`. `autonomy.sensitive_paths` always has a baseline set of regexes (`.env`, secrets, `.github/workflows/`, `Jenkinsfile`, credentials, password) force-appended regardless of user config — don't remove that expectation when touching `load_config`.

**SEC-009 P1 — configuration authority (`kriya/config/authority.py`):** a config value's provenance (which source set it: packaged default, auto-discovered CWD/install-dir, explicit `--config` inside/outside the workspace, or a `runtime_profile` preset expansion) is tracked per leaf field through `load_config()`'s merge, then checked against a `REPOSITORY_SAFE`/`USER_AUTHORITY`/`SECURITY_AUTHORITY`/`PLATFORM_POLICY` classification *before* `AppConfig` is constructed. Only `PACKAGED_DEFAULT`/`PLATFORM_FLOOR` sources are unconditionally trusted; every other source may only set explicitly-allowlisted `REPOSITORY_SAFE` fields — anything else (including an unclassified/future field) is a violation, before `Kernel`/`PluginManager`/`MCPManager` ever see the config. `mcp.*`, `plugins.directory`/`enabled`, `execution_policy.*`, `runtime_profile`, and `autonomy.acquisition_registry_hosts`/`egress_policy`/`risk_threshold_lines`/`sandbox_env_allowlist` are `SECURITY_AUTHORITY`/`PLATFORM_POLICY`. `paths.{skills,memory,state}` are classified dynamically (`path_field_classification()`): `REPOSITORY_SAFE` only if the resolved real target stays inside `config_dir`, `SECURITY_AUTHORITY` (escape) otherwise — a bug that skips the override fails CLOSED (both are absent from the static `_REPOSITORY_SAFE_FIELDS` table, present in `_SECURITY_AUTHORITY_FIELDS` for accurate labeling only). `logging.directory` is `SECURITY_AUTHORITY` for any string (only `null` is `REPOSITORY_SAFE`), and `logging.file_enabled`/`run_file_enabled` are `REPOSITORY_SAFE` — removing a capability grants no authority. When adding a new `AppConfig` field, add it to `authority.py`'s explicit `_REPOSITORY_SAFE_FIELDS` allowlist only if a repository genuinely cannot use it to gain execution/network/filesystem/policy authority; otherwise leave it unlisted (fails closed by default) or add it to `_SECURITY_AUTHORITY_FIELDS` for an accurate error message.

**Closed vocabularies are checked at the resolution point (S16a, F5).** `autonomy.mode` (`parse_autonomy_mode`) and `autonomy.egress_policy` (`parse_egress_policy`, with `EGRESS_POLICIES` / `EgressPolicyError`, all in `kriya/config/authority.py`) are validated on the EFFECTIVE value in `resolve_config_state`, before classification, so `load_config`, `kriya authority inspect|approve` and the desktop's configuration operations refuse a malformed value typed; nothing is offered for approval and an approval (even a stale digest-valid one) is never consulted. `AutonomyConfig`'s validator / assignment / `model_copy` call the same functions (`config.py` keeps only lazy wrappers; resolution cannot import `config.py`). Pinned by `tests/test_s16a_autonomy_mode_vocabulary.py` and `tests/test_f5_egress_policy_authority.py`.

**Value-gated REPOSITORY_SAFE fields (S3/S3b).** A field may be repository-settable only for a RESTRICTING value: `autonomy.self_correction_loop_enabled`, the web-lookup enabling fields, and the containment resource bounds (`sandbox_cpu_seconds` 240, `sandbox_memory_mb` 4096, `acquisition_cpu_seconds` 300, `acquisition_memory_mb` 2048, `shell_command_timeout_seconds` 300, plus the sixth bound at 90 in `_VALUE_BOUNDED_FIELDS`). A repository kriya.yaml may lower a bound but never raise it: exactly a positive `int` at most the ceiling counts as REPOSITORY_SAFE (a bool, float, zero, negative or larger value is a SECURITY_AUTHORITY violation); the operator/user-level config and the durable approval path (`kriya authority`) still set any value. `autonomy.mode` is a closed vocabulary `{guardrails, human-in-the-loop}` parsed by `parse_autonomy_mode` (typed `AutonomyModeError`, closed `AUTONOMY_MODE_REASONS`); consumers use `autonomy_mode_of(config)` / `is_human_in_the_loop(mode)`, never a raw string comparison.

**One redaction owner (S2/S2b).** `kriya/foundation/redaction.py` (`redact_text`, `redact_value`, `is_secret_key`) is the only redactor: CLI inspect/approve, doctor, logs, traces, error messages, the durable approval record and the application/KUP history projection all go through it (no per-surface regex; the old three redactors are gone). Stored authoritative evidence stays RAW (digests bind exact bytes); redaction happens at the projection. By design two surfaces show raw bytes (OI-146, INTENTIONAL_CONTRACT): the change-approval review diff (reviewed bytes must equal approved bytes) and the explicit opt-in `content_visibility` evidence content (default withholds). That exemption does not extend to durable evidence, history, telemetry, logs or exports (S20 owns persisted-evidence redaction). Known open limits: see S2c/S20 in the modularization ledger.

**Attached credential flags (WAVE8 NEW-1, 2026-11-06).** The password of `--user=u:pw`, `--proxy-user=u:pw`, `-uu:pw`/`-Uu:pw` (also in a bundle `-sSuu:pw`, quoted `-u'u:pw'`) and the separate value after a bundle ending in `u` (`-sSu u:pw`) is hidden in free text and in argv list elements (so `commands_carry_secret` refuses them); `bearer` is a secret last word (`--oauth2-bearer=<token>`). Attached SHORT forms need a `user:password` value; recorded over-redaction `-u1000:1000`. Pinned by `tests/test_wave8_redaction_attached_credentials.py` (red before / green after, with mutants).


**SEC-009 P2 — durable approval (`kriya/config/authority_approval.py`, `kriya authority inspect|approve|revoke`):** a violation isn't immediately fatal — it's checked against a digest-bound approval artifact (except a malformed `autonomy.mode`, S16a: a typed `AutonomyModeError` before classification, never approvable; the closed vocabulary is `guardrails` / `human-in-the-loop`, `parse_autonomy_mode` in `kriya/config/authority.py`, read through `autonomy_mode_of`/`is_human_in_the_loop`) covering the EXACT current security-relevant field set (any addition/removal/value change invalidates the whole approval; see `build_security_field_records()`/`compute_set_digest()`). The artifact lives OUTSIDE the workspace (`~/.kriya/authority/<workspace_id>.json` by default, override via `KRIYA_AUTHORITY_HOME`) — never inside it, so repository content can never ship its own self-authorizing approval; the same rule is enforced on an explicit `--trust-file`/`KRIYA_TRUST_FILE` (CI/operator-supplied) via `validate_trust_path_outside_workspace()`. Secrets (`mcp.*.env` values) are salted-and-digested, never persisted in plaintext. `kriya authority` is reachable even when the current config is denied (but not when `autonomy.mode` is malformed: inspect and approve refuse typed) (bypasses `main()`'s eager `load_config()` — see `ctx.invoked_subcommand == 'authority'`). With no valid approval, behavior is byte-identical to P1 fail-closed. See `docs/assurance/KRIYA_PRODUCTION_RISK_REGISTER.md`'s SEC-009 entry for the full design rationale, threat-case coverage, and closure evidence (`CLOSED`, 2026-09-12, after a bypass/closure review and fix — see that entry's log-file containment addendum; the field it closed was later removed in favor of `logging.directory`). **W2-21 (one trust-file resolution):** `authority_approval.checked_trust_file(explicit, workspace_root, environment)` is the ONLY resolution of the operator's trust file (the `--trust-file` flag, else `KRIYA_TRUST_FILE`); it refuses a path whose REAL target (`realpath`, so a file symlinked into the workspace too) resolves inside the workspace, naming the path as the operator gave it (pinned by `tests/golden/config/resolution_forms.json`). `load_config` (every trust-aware command) and `kriya authority inspect` both call it; `inspect` consults an explicit trust file like `load_config` does (CURRENT / stale / absent are reported against THAT file, never replaced by the local store; an invalid or unreadable one is a typed refusal), and only without one reports the local store. Tests: `tests/test_w221_trust_file_consistency.py`.

### Containment mandate has no opt-out (S7, 2026-10-26)
`autonomy.contained_execution_required` and `autonomy.mcp_contained_execution_required` are SEC-009 `SECURITY_AUTHORITY` fields whose ONLY valid value is `true` (packaged defaults: `containment_backend: oci`, both mandates `true`). `kriya.config.authority.parse_containment_mandate` is the one check, called at every ingress: `AutonomyConfig` construction (field validators), attribute assignment, `model_copy(update=...)`, a re-validated instance, and the authority resolution (`resolve_config_state` / `load_config`, so `kriya authority inspect|approve` and the desktop configuration operations refuse it too). Anything but exactly `True` is a `ContainmentOptOutError(ValueError)`; an approval cannot make host execution valid. `kriya.tools.containment._containment_is_mandatory` reads no configuration (a forged or legacy object is still mandatory), so a mandatory decision with a backend that provides no isolation (`none`, which still parses) or an unknown name is a typed `ExternalExecutionRefused` before any process starts. Trusted Kriya infrastructure (git, the docker CLI, the neutral-cwd toolchain probe) is classified in `tests/architecture/execution_site_inventory.py` and never asks the owner. Identity-bearing: the config fingerprint, baseline environment identity, release identity and static-analysis settings digest all change, so state recorded under the old default reads STALE. Tests: `tests/test_s7_secure_default_contract.py`; the migration census is `tests/containment_census.py` (seams S/F2/N/H), the closed list S8 deletes is `tests/containment_s8_list.py` with its replacement controls in `tests/containment_h_ledger.py`.

**`kriya authority inspect` prints each pending field's value, redacted (contract, Wave-2 Step 11).** The value line is `p.redacted_value` (`cli_commands/authority.py`), produced by the one redaction owner `foundation/redaction.redact_value` (S2: URL userinfo and every secret-shaped value are masked); showing the value so the operator can judge it is the design (`tests/test_e14_cli_characterization.py`).

**A workspace skill cannot attest its own verification (B3, 2026-10-29).** A `skill.yaml` `verified: true` inside the workspace is untrusted metadata (`Skill.verified_claim`, display only), whichever directory `paths.skills` names; authoritative verification is the Kriya install library, a skill outside the workspace, or verification earned in the current run (the held verification, `SkillEngine.is_effectively_verified`). `mark_verified` still writes the flag for display/compat; a reload does not believe it. Persistent verification of workspace skills is a FUTURE FEATURE (Kriya-owned attestation bound to skill identity and content). Tests: `tests/test_skill_workspace_verified_authority.py`.

**PRD-034 — `autonomy.acquisition_registry_mirror` (D-type authority/contract correction, owner 2026-11-02):** an operator-owned, default-OFF Maven registry mirror for the contained acquisition phase (`kriya/config/config.py`, `kriya/tools/containment_oci.py`, `kriya/tools/containment.py::ContainmentProfile.registry_mirror`, classified `SECURITY_AUTHORITY` in `kriya/config/authority.py`, listed in `resume_fingerprints.CONTAINMENT_CONFIG_FIELDS`). Unset = every rendered artifact is byte-identical to before (the trusted setup script's digest is pinned in `tests/test_prd034_registry_mirror.py`). Set = the trusted setup writes ONE standard Maven `<mirror>` (`<id>central</id>`, `<mirrorOf>central</mirrorOf>`) into the container's global `settings.xml`; the id must be `central` because the offline execution phase only accepts artifacts "cached from" a repository id available in its build context (MEASURED: any other id fails `MAVEN_ACQUISITION_INCOMPLETE`). The mirror host MUST also be in `acquisition_registry_hosts` (config validator AND the OCI backend, fail closed), so the same exact-host Squid ACL admits it; `mirrorOf` is `central` only, so a pom's own `<repository>` still resolves to the host it names (SEC-006). The value reaches a ROOT shell heredoc and XML, so its grammar is closed (`http(s)://host[:port][/path]`, letters/digits/`._~-` only; refused, never escaped; re-checked by the renderer). An approved mirror HOSTNAME is NOT trusted CONTENT: certification binds the served bytes to a frozen manifest (`scripts/certification_maven_repo.py`, `tests/certification/maven_repository.manifest.json`). When the mirror host is `host.docker.internal` the proxy container (the only container that connects to it) gets `--add-host host.docker.internal:host-gateway` (Docker Desktop resolves it by itself; Docker Engine on Linux needs it).
