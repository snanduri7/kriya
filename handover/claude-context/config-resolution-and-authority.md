# Configuration resolution and SEC-009 configuration authority

_Moved verbatim from CLAUDE.md on 2026-10-07 (loaded on demand, not every session). Read before modifying any module named here. Code is ground truth; update this file when behaviour changes._

## Configuration resolution

`kriya/config/config.py::load_config()` layers config in this order (later wins, dicts are shallow-merged one level deep):
1. `kriya/config/default_config.yaml` (packaged defaults)
2. `kriya.yaml`/`kriya.yml` — first checked in CWD, then in the Kriya install directory, unless `--config` is passed explicitly
3. `AppConfig` (pydantic model in the same file) validates the merged result

Relative `paths.*` and `plugins.directory` values are resolved against the directory the config file was loaded from (or the install dir for the packaged default), using `os.path.realpath` (resolves symlinks) — `paths.state` (traces.db) resolves ANY relative value against `config_dir`, and inside the workspace must sit beneath `<workspace>/.kriya/` (typed `StateDirectoryError` otherwise; `.kriya/state` is valid, `./state`/`./logs` are not). Every filesystem-target field is canonicalized ONCE in `resolve_config_state()` before classification, so the value SEC-009 inspects and the value later opened can never diverge. **`kriya.log`/run-log locations (PRD-010 logging closure) are owned by `kriya/core/logging_setup.py` - never the process CWD:** directory = `KRIYA_LOG_DIR` > `logging.directory` (absolute; `~` expanded and realpath'd once in `resolve_config_state()`, a relative value is a typed `LogDirectoryError`; any string is `SECURITY_AUTHORITY`, `null` is `REPOSITORY_SAFE`) > `~/.kriya/logs`. Application log `<dir>/kriya.log` (`logging.file_enabled`); per-run log `<dir>/runs/<run_id>/kriya.log` (`logging.run_file_enabled`), attached around the whole run by `begin_mutating_run()`. `doctor --production` logs to the console only and checks the directory as `persistence.logs`. `tests/conftest.py` points `KRIYA_LOG_DIR` at a session temp dir so the suite never writes the real `~/.kriya/logs`. **Run history (`traces.db`) is state, owned by `kriya/core/state_paths.py`:** `KRIYA_STATE_DIR` > `paths.state` (SEC-009-classified like the other `paths.*`; null is REPOSITORY_SAFE) > `~/.kriya/state`, always `trace_db_path(cfg)` - never the log directory. `paths.logs` and `logging.file` were REMOVED: a config naming either gets `RemovedConfigFieldError` with the replacement field (`REMOVED_PATHS_LOGS_MESSAGE`/`REMOVED_LOGGING_FILE_MESSAGE`), never reinterpreted; `tests/test_state_location.py`'s repository guard fails if either, or `logs_path`, reappears in `kriya/`. A pre-move database at the historical default `<install dir>/logs/traces.db` is reported by `kriya traces` and `doctor --production` (`persistence.traces` WARN) and copied only by `kriya traces --migrate-legacy [--legacy-path <traces.db>]` (SQLite backup, refuses an existing target, never merges or deletes). Workspace `.kriya/` run control state is unaffected. `tests/conftest.py` gives every test its own `KRIYA_STATE_DIR`; tests locate traces via `trace_db_path(cfg)`. `autonomy.sensitive_paths` always has a baseline set of regexes (`.env`, secrets, `.github/workflows/`, `Jenkinsfile`, credentials, password) force-appended regardless of user config — don't remove that expectation when touching `load_config`.

**SEC-009 P1 — configuration authority (`kriya/config/authority.py`):** a config value's provenance (which source set it: packaged default, auto-discovered CWD/install-dir, explicit `--config` inside/outside the workspace, or a `runtime_profile` preset expansion) is tracked per leaf field through `load_config()`'s merge, then checked against a `REPOSITORY_SAFE`/`USER_AUTHORITY`/`SECURITY_AUTHORITY`/`PLATFORM_POLICY` classification *before* `AppConfig` is constructed. Only `PACKAGED_DEFAULT`/`PLATFORM_FLOOR` sources are unconditionally trusted; every other source may only set explicitly-allowlisted `REPOSITORY_SAFE` fields — anything else (including an unclassified/future field) is a violation, before `Kernel`/`PluginManager`/`MCPManager` ever see the config. `mcp.*`, `plugins.directory`/`enabled`, `execution_policy.*`, `runtime_profile`, and `autonomy.acquisition_registry_hosts`/`egress_policy`/`risk_threshold_lines`/`sandbox_env_allowlist` are `SECURITY_AUTHORITY`/`PLATFORM_POLICY`. `paths.{skills,memory,state}` are classified dynamically (`path_field_classification()`): `REPOSITORY_SAFE` only if the resolved real target stays inside `config_dir`, `SECURITY_AUTHORITY` (escape) otherwise — a bug that skips the override fails CLOSED (both are absent from the static `_REPOSITORY_SAFE_FIELDS` table, present in `_SECURITY_AUTHORITY_FIELDS` for accurate labeling only). `logging.directory` is `SECURITY_AUTHORITY` for any string (only `null` is `REPOSITORY_SAFE`), and `logging.file_enabled`/`run_file_enabled` are `REPOSITORY_SAFE` — removing a capability grants no authority. When adding a new `AppConfig` field, add it to `authority.py`'s explicit `_REPOSITORY_SAFE_FIELDS` allowlist only if a repository genuinely cannot use it to gain execution/network/filesystem/policy authority; otherwise leave it unlisted (fails closed by default) or add it to `_SECURITY_AUTHORITY_FIELDS` for an accurate error message.

**Value-gated REPOSITORY_SAFE fields (S3/S3b).** A field may be repository-settable only for a RESTRICTING value: `autonomy.self_correction_loop_enabled`, the web-lookup enabling fields, and the containment resource bounds (`sandbox_cpu_seconds` 240, `sandbox_memory_mb` 4096, `acquisition_cpu_seconds` 300, `acquisition_memory_mb` 2048, `shell_command_timeout_seconds` 300, plus the sixth bound at 90 in `_VALUE_BOUNDED_FIELDS`). A repository kriya.yaml may lower a bound but never raise it: exactly a positive `int` at most the ceiling counts as REPOSITORY_SAFE (a bool, float, zero, negative or larger value is a SECURITY_AUTHORITY violation); the operator/user-level config and the durable approval path (`kriya authority`) still set any value. `autonomy.mode` is a closed vocabulary `{guardrails, human-in-the-loop}` parsed by `parse_autonomy_mode` (typed `AutonomyModeError`, closed `AUTONOMY_MODE_REASONS`); consumers use `autonomy_mode_of(config)` / `is_human_in_the_loop(mode)`, never a raw string comparison.

**One redaction owner (S2/S2b).** `kriya/foundation/redaction.py` (`redact_text`, `redact_value`, `is_secret_key`) is the only redactor: CLI inspect/approve, doctor, logs, traces, error messages, the durable approval record and the application/KUP history projection all go through it (no per-surface regex; the old three redactors are gone). Stored authoritative evidence stays RAW (digests bind exact bytes); redaction happens at the projection. By design two surfaces show raw bytes (OI-146, INTENTIONAL_CONTRACT): the change-approval review diff (reviewed bytes must equal approved bytes) and the explicit opt-in `content_visibility` evidence content (default withholds). That exemption does not extend to durable evidence, history, telemetry, logs or exports (S20 owns persisted-evidence redaction). Known open limits: see S2c/S20 in the modularization ledger.


**SEC-009 P2 — durable approval (`kriya/config/authority_approval.py`, `kriya authority inspect|approve|revoke`):** a violation isn't immediately fatal — it's checked against a digest-bound approval artifact (except a malformed `autonomy.mode`, S16a: a typed `AutonomyModeError` before classification, never approvable; the closed vocabulary is `guardrails` / `human-in-the-loop`, `parse_autonomy_mode` in `kriya/config/authority.py`, read through `autonomy_mode_of`/`is_human_in_the_loop`) covering the EXACT current security-relevant field set (any addition/removal/value change invalidates the whole approval; see `build_security_field_records()`/`compute_set_digest()`). The artifact lives OUTSIDE the workspace (`~/.kriya/authority/<workspace_id>.json` by default, override via `KRIYA_AUTHORITY_HOME`) — never inside it, so repository content can never ship its own self-authorizing approval; the same rule is enforced on an explicit `--trust-file`/`KRIYA_TRUST_FILE` (CI/operator-supplied) via `validate_trust_path_outside_workspace()`. Secrets (`mcp.*.env` values) are salted-and-digested, never persisted in plaintext. `kriya authority` is reachable even when the current config is denied (but not when `autonomy.mode` is malformed: inspect and approve refuse typed) (bypasses `main()`'s eager `load_config()` — see `ctx.invoked_subcommand == 'authority'`). With no valid approval, behavior is byte-identical to P1 fail-closed. See `docs/assurance/KRIYA_PRODUCTION_RISK_REGISTER.md`'s SEC-009 entry for the full design rationale, threat-case coverage, and closure evidence (`CLOSED`, 2026-09-12, after a bypass/closure review and fix — see that entry's log-file containment addendum; the field it closed was later removed in favor of `logging.directory`).
