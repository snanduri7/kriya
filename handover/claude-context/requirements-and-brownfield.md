# Requirement lineage (PRD-020), ownership findings/recovery (PRD-021/022), contract change escalation (PRD-023), brownfield baseline auto policy (PRD-024)

_Moved verbatim from CLAUDE.md on 2026-10-07 (loaded on demand, not every session). Read before modifying any module named here. Code is ground truth; update this file when behaviour changes._

### Original requirement lineage (`kriya/workflow/requirements.py`) — PRD-020
- **Derivation.** `derive_requirements(goal)` turns the user's goal statements into REQ-n records. It is deterministic (list items, then sentences; verbatim text; `REQUIREMENT_DERIVATION_VERSION` in the digest), never a model. **Explicit contract (GR-R1A, `kriya/workflow/requirement_contract.py`):** `generate --requirements <file>` (JSON `kriya.requirements/1`, outside the workspace, read and stored content-addressed before any model call) replaces the derived set with the operator's CLOSED set - never merged; the goal stays the planning/Developer context and binds it (`goal_identity`; another goal is `REQUIREMENT_CONTRACT_GOAL_MISMATCH`). Its digest joins `RequirementSet.digest` (`contract_digest`; derived sets byte-identical), the resume goal inputs and the enforce `ControlState`, and B3 approvals bind it through `kriya.acceptance_approval/2` (`requirement_set_sha256`, required with a contract). Every derivation site goes through `requirement_set_for`.
- **Where they are verified.** The unit that verifies them is named by `WorkUnitInvocation.requirement_goal`: the direct unit, or a milestone plan's integration unit (the plan's `original_goal`). Enforce derives them in `_run_structured_enforce`.
- **Prompts and plan mapping.** The Planner and the Architect are shown them, because the Architect otherwise sees only the plan. `Subtask.requirement_ids` maps subtasks to them, and `validate_plan(known_requirement_ids=)` rejects an invented id. Citations are lineage only.
- **Verdict reasons (MODEL-EVIDENCE-HARDENING-001).** Every recorded verdict carries a normalized `reason_code` (`requirements.REQUIREMENT_REASON_CODES`: VERIFIER_CONFIRMED, VERIFIER_REPORTED_MISSING, INSUFFICIENT_CODE_EVIDENCE, MISSING_CLAIM_NOT_CONCRETE, CLAIM_CONTRADICTS_STRONGER_AUTHORITY, MODEL_RETURNED_NO_VERDICT, MALFORMED_VERIFIER_RESULT, VERIFIER_CALL_FAILED, VERIFIER_REQUEST_REFUSED; PENDING = NOT_YET_VERIFIED), its evidence text, the verifier identity (`SpecComplianceAgent.check` returns `verifier` and, when unknown, `failure_reason_code`) and the judged candidate (evidence id + revision). `verifier_result_verdicts` is the one parser both paths use; `requirement_verdict_details` feeds `requirements.verdicts` in both results and the `requirement.verdicts` events.
- **Verifier request size.** The spec-compliance files section is fitted (`context_budget.fit_spec_compliance_files`): every file whole when that fits (unchanged prompt), else each file's changed regions against its pre-change version (callers pass `baseline_contents`; unchanged files named, new files whole); no view fits -> the whole files and a typed refusal, never a verdict over files not shown.
- **Outcomes.** Only the verifier records one: the `SpecComplianceAgent.check(requirements=)` per-id verdicts, via `attempt._record_original_requirement_verdicts` and enforce's `_verify_original_requirements`. They are recorded as `ObligationKind.ORIGINAL_REQUIREMENT`, seeded PENDING at JUDGMENT so the verdict becomes authoritative.
- **Terminal decision.** A verifier verdict is MODEL_CLAIMED either way (FS-1B, GR-R0 NEGATIVE-MODEL-AUTHORITY): "satisfied" and "missing" are both recorded UNVERIFIED with the model's verdict as provenance; only deterministic or human-bound evidence makes a requirement CLOSED_BY_EVIDENCE/HUMAN_ACCEPTED (it outranks a model "missing") or VIOLATED, and an unrefuted model "missing" blocks whatever the policy (`tests/test_gr0_negative_model_authority.py`). The per-attempt Goal Spec Compliance gate is advisory the same way (GR-R1B): a model "missing" or twice-contradictory verdict on a candidate every deterministic gate passed fails no attempt and spends no retry or fallback; it is recorded (gate status `model_reported_missing`/`model_indeterminate`, run event `spec_compliance.model_advisory`, GOAL_SPEC_REQUIREMENT INDETERMINATE) and the terminal gate decides (`tests/test_gr1b_spec_gate_model_authority.py`). `blocking_requirements()` makes VIOLATED always block; `autonomy.requirement_unknown_policy`/`requirement_unverified_policy` (SECURITY_AUTHORITY; production seals both to block) decide the rest.
- **Claims (FS-1C1).** A requirement statement can claim new BEHAVIOR and REGRESSION_PRESERVATION (`requirements.requirement_claims`: BEHAVIOR whenever anything but the named tests and a closed preservation vocabulary remains - unknown phrasing fails closed). Each claim closes only by its own kind of evidence (`record_requirement_claim`: REGRESSION_PRESERVATION only from a named-test oracle, BEHAVIOR only from `BEHAVIOR_CLOSURE_METHODS` - the B2-a acceptance file below; B3 has no producer yet). The latest judgment of a claim on a candidate decides (`requirement_claim_record`: SATISFIED closes, VIOLATED is counter-evidence, INDETERMINATE revokes), and a requirement closes only when every claim it makes is closed for the same candidate (`_effective_closure`; which claims = the BEHAVIOR record's `required_claims`, else both; which also ignores a named-test whole-requirement closure of a statement that claims BEHAVIOR, e.g. a pre-FS-1C1 record read back on resume). C0 closes a pure preservation statement whole; for a compound one it records only the preservation claim (`REQUIREMENT_BEHAVIOR_UNVERIFIED`), so the requirement stays UNVERIFIED (post-P3 A1 false success).
- **Acceptance file (FS-1C2 B2-a, `kriya/workflow/acceptance_oracle.py`).** The only BEHAVIOR producer: `generate --acceptance <file>` (`cli._bind_acceptance`, before any model call) parses the operator's pytest file (every case `@pytest.mark.kriya_requirement("REQ-n")`; unknown id, mutation-scope requirement, skip/xfail/pytestmark, relative import refused), stores it content-addressed under `<state>/acceptance/` and binds the requirement-set digest; `WorkflowEngine.acceptance` carries it (`bound_acceptance`, isinstance-checked), `TerminalGateRequest.acceptance` at enforce, and `generation_resume_fingerprints(acceptance_digest=)` (verification inputs, only when present). `close_requirements_with_acceptance_tests` runs at both closure sites before the named-test closure: stages the file into the candidate's `.kriya/acceptance-runs/<uuid>/` and runs Kriya's own runner through `PolymorphicValidator.run_acceptance` (gate `acceptance`; `python -I -B`, `-c` Kriya ini, `--rootdir` stage, `--noconftest`, autoload off, project root appended to `sys.path`; `run_tests` is untouched). `judge_acceptance`: PASSED only from a complete FS-1A report cross-checked case by case with the runner's observations; VIOLATED only for a call-phase contradiction (candidate frame in the traceback, or an assertion after candidate code loaded from the root) with artifact/candidate unchanged during the run; any foreign pytest plugin, missing/inconsistent evidence, non-executed case or non-contradicting failure is INDETERMINATE. Claim typing uses every pre-existing test file (`_reference_test_files`: workspace + base; unknown = both claims), so deleting a named regression test never drops its claim. Layouts: flat package/module at the root only (`ACCEPTANCE_LAYOUT_UNSUPPORTED` for src/, namespace, test-side imports; no fallback). Tests: `tests/test_b2a_acceptance_oracle.py` (real runs; A1 on vendored freezegun, `tests/_b2a_fixtures.py`).
- **Claim strength (B2-COV).** Evidence closes a claim only at the strength it demonstrates: `requirements.behavior_strength(text, regression_covered=)` (deterministic, from the user's words) makes a BEHAVIOR statement EXACT only when it states concrete example calls and no behaviour clause carries a universal word/phrase (`any`, `every`, `only`, `of the form`, ...), a `<placeholder>` or a formula over a declared parameter (`double(x) returns 2 * x`); preservation clauses belong to the regression claim (uncovered ones make it GENERAL); anything else is GENERAL. Finite acceptance cases (`FINITE_EVIDENCE_METHODS`) close only EXACT statements: on a GENERAL one a pass is `ACCEPTANCE_GENERAL_RULE_UNPROVEN` (BEHAVIOR INDETERMINATE, supporting `BEHAVIOR_EXAMPLES` SATISFIED, never a closure claim); a counterexample still makes it VIOLATED. `_effective_closure` re-decides strength at read time (`_finite_evidence_may_close`), so a resumed pre-B2-COV record cannot close a general rule. A general rule needs another authority (B3, human approval: not implemented). Tests: `tests/test_b2cov_claim_strength.py` (A2 live candidate replay).
- **JVM acceptance (FS-1C2 B2-c, `kriya/workflow/acceptance_jvm.py`, Maven + JUnit 5/Surefire only).** `--acceptance <File>.java`: one package, one class, every `@Test` with a `// kriya_requirement: REQ-n` line above it (skip/repeat/parameterize/extend annotations, nested types and unmarked tests refused). `run_java_acceptance` (called from `close_requirements_with_acceptance_tests`, same closure and B2-COV rules as Python): C0's `OracleSurface` (build files, `.mvn`, every non-main source set, `junit-platform.properties`, `META-INF/services`, output-root writes) must equal the run base (`ACCEPTANCE_TRUST_SURFACE_CHANGED`/`_UNAVAILABLE`); the injection path `src/test/java/<pkg>/<Class>.java` must exist in neither base nor candidate (`ACCEPTANCE_PATH_COLLISION`); the candidate is copied into `<state>/acceptance-runs/<uuid>/workspace`, its main code compiled there first (`ACCEPTANCE_CANDIDATE_COMPILE_FAILED` - an ordinary candidate failure, never evidence; a compile gate with NO trustworthy verdict - a typed `environment_reason_code` or no interpretable result - is `ACCEPTANCE_ENVIRONMENT_UNAVAILABLE`, the candidate was not judged), the class injected create-exclusive and run alone through the ordinary Maven test gate (`-Dtest=<Class>`, FS-1A report). `judge_java_acceptance`: case detail re-read from the digest-verified Surefire XML; VIOLATED for an assertion-type `<failure>` in a class referencing candidate code or an `<error>` with a candidate main-class frame (linkage errors excluded); a harness that does not compile is `ACCEPTANCE_HARNESS_COMPILE_FAILED`. Gradle-only projects: `ACCEPTANCE_RUNNER_UNSUPPORTED`. Tests: `tests/test_b2c_jvm_acceptance.py` (real Maven; `tests/_b2c_fixtures.py`).
- **Human-bound acceptance (FS-1C2 B3, `kriya/workflow/acceptance_approval.py`).** Not a proof: an operator approves one exact acceptance suite as sufficient for one exact GENERAL requirement. `generate --acceptance F --acceptance-approval A.json` (`cli._bind_approval`, the only `load_approval` caller, before any model call): the file must be outside the workspace; every entry binds requirement id (no pattern/duplicate/scope-only), requirement-text sha256, goal digest, acceptance digest, the exact case list, the runner contract (`RUNNER_CONTRACT_DIGEST` / JVM `RUNNER_SOURCE_DIGEST`) and the base revision, with `accept_suite_as_sufficient: true`; stored under `<state>/acceptance-approvals/`. In `close_requirements_with_acceptance`, a GENERAL claim whose suite fully passed is recorded method `human_bound_acceptance` (`ACCEPTANCE_HUMAN_ACCEPTED`) only when `approval_problem` finds no mismatch at the closure (incl. the run's base revision); outcome `RequirementOutcome.HUMAN_ACCEPTED` (derived, never CLOSED_BY_EVIDENCE); VIOLATED and INDETERMINATE are unchanged; withdrawing/changing the approval supersedes. `_effective_closure` re-checks the requirement text at read time and never accepts a whole-requirement closure by the human method. Resume: the approval digest joins the goal-side fingerprint (planning + candidate regenerate) and `ControlState.acceptance_approval_digest` (enforce reuses no subtask recorded under another approval; unset leaves earlier hashes unchanged). Tests: `tests/test_b3_human_acceptance.py`.
- **Closure evidence.** UNVERIFIED is never SATISFIED. `record_requirement_closure` writes a separate DETERMINISTIC record (`requirement.REQ-n.closure`, never the verdict id, which it would outrank) whose `evidence_id` must equal the verdict's, and `requirement_outcomes` then reports CLOSED_BY_EVIDENCE. VIOLATED and UNKNOWN are never closed. Producers (the binding is always the user's words): `workflow.close_requirements_with_named_tests` (tests the REQ text names, judged by the FS-1C0 independent oracle `kriya/workflow/named_test_oracle.py`: the named files exist and are byte-identical at the run's base revision (`RunRecord` base, else HEAD); the runner trust surface - pytest conftests/`__init__`/ini sections on the path, declared dependencies, the test-side import closure, test resources; JVM build files, `.mvn`/`buildSrc`/`gradle`, all of `src/test/**`, `junit-platform.properties`, `META-INF/services` - equals the base before AND after the run; the exact cases come from running the named tests on a `git archive` export of the base; the candidate run's COMPLETE FS-1A report carries every one of them passed and the runner succeeded; anything else is UNVERIFIED with an `ORACLE_*` reason, runners other than pytest/Maven/Gradle refused; the closure record binds base revision, surface digest, expected cases and report digests; in-process tampering by candidate production code is the disclosed residual; direct pre-apply boundary and enforce terminal gate; D8: no validator is built unless an UNVERIFIED requirement names an existing test and the surface check passes - a changed build declaration is refused before any toolchain resolution - and the candidate validator carries the caller's toolchain authority `toolchain_declaration_mutable(...)`, never re-deciding it) and `attempt._close_requirements_by_migration_gate` (a REQ naming both migration source and target; direct attempt path and enforce terminal, since enforce subtasks carry no requirement set). Mutation-scope requirements ("do not modify any other file", whole-statement match only) are decided by `workflow.close_requirements_by_mutation_scope` at the same two sites: authorized = only paths the goal's words make change targets (`mutation_path_roles`: nearest cue verb in the clause, closed vocabularies; references/negated never authorize, undecidable roles leave it unresolved; never the plan), actual = candidate changes (git against the run base) + the run's committed history (RunRecord COMMITTED cycles' commit evidence); in scope and nothing foreign closes it (`MUTATION_SCOPE`), outside the set records DETERMINISTIC counter-evidence and the outcome is VIOLATED whatever the verifier said. Both results carry `requirements` (set + outcomes + `evidence`).
- **Milestone plans.** A failing multi-unit plan's result carries `committed_work_units`/`committed_changes_retained`, from `RunRecord.committed_work_units()` (derived from `commits[].work_unit` + settled result; no schema change). It is enforced at the pre-apply boundary (terminal `requirements_unresolved`, `REQUIREMENTS_UNRESOLVED`) and at enforce's `original_requirements` gate. `unresolved_terminal_obligations()` skips this kind on purpose.

### Grounded ownership findings (`kriya/workflow/ownership_findings.py`) — PRD-021
- **Scope.** Runs only on planned files still NEW after `prefer_existing_artifact_owners` (which keeps precedence).
- **Candidates.** `grounded_owner_candidates()` reuses planning's bounded goal-ranked candidates, `build_planning_structural_evidence` edges and an in-memory `DependencyGraph` (no second index). A candidate needs the goal to name its responsibility (the name's role word or a member verb) plus one more shared term; a domain noun alone never qualifies.
- **Findings.** `OwnershipFinding` records are GROUNDED and never deny a plan.
- **Status.** A structured `ownership_justification` (`Subtask` field / Architect file-list JSON key) only ACKNOWLEDGES. SATISFIED only via goal intent, the plan removing the owner, or human approval.
- **Where they appear.** Candidates go to the Planner (enforce; direct Planner+Architect on TASK/ENHANCEMENT) and findings to the Developer. They are recorded as non-terminal `GROUNDED_OWNERSHIP` obligations and `ownership.finding` events, and kept on `state.ownership_findings` for review.

### Ownership recovery and reviewer evidence — PRD-022
- **Retry scope.** After a deterministic `brownfield_ownership_redirect` violation, the retry targets only the grounded owner (patch authority, exact current source; proved and protected, not re-implemented).
- **Restoration.** `state.ownership_redirect_recovery` keeps the violation's evidence. In the next attempt's guarded staged batch, `attempt._stage_ownership_redirect_restoration` restores the redirected tests to baseline and removes the run-created parallel file (`RESTORE_PUBLIC_CONTRACT` precedent).
  - Anything the Developer writes again is kept, so repeats still reach `INVALIDATION_REPEAT_THRESHOLD` (2, unchanged).
  - An abandoned file leaves the expected-files set.
- **Post-generation findings.** `_record_post_generation_ownership_findings` adds findings for files a candidate actually created.
- **Advisory evidence only.** `ownership_review_evidence(ledger, files)` feeds open GROUNDED findings from the ledger to the pre-approval and final Reviewer and to the approval reason. They never gate, and the Reviewer cannot change a finding.

### Contract change classification and escalation (`kriya/workflow/contract_classification.py`) — PRD-023
- **Classification.** `find_brownfield_public_api_changes` stays the only detector. `classify_api_violations` classifies every reported change from evidence: AUTHORIZED_DIRECT/AUTHORIZED_HUMAN, UNAUTHORIZED, POTENTIALLY_DERIVED, INDETERMINATE.
  - UNAUTHORIZED: a removed symbol still called, a stale caller, or no DIRECT authorization in the run.
  - POTENTIALLY_DERIVED: co-updated callers plus a supported relationship (the owner references the authorized owner/symbol, or a co-updated caller maps both).
  - INDETERMINATE: co-updated callers but no supported relationship.
- **Escalation.** Only POTENTIALLY_DERIVED/INDETERMINATE may be escalated (`attempt._classify_and_escalate_contract_changes`, at the pre-write gate), and only with `autonomy.contract_change_escalation: human` (SECURITY_AUTHORITY, default `deny`) in a human-in-the-loop run with a callback. Otherwise the change is blocked: `CONTRACT_ESCALATION_UNAVAILABLE`, or `..._DECLINED` if refused.
- **Approval record.** An approval mints `contract_authority.human_contract_authorization` (the only other minting site; CORR-016's constructed-only-here and single-derivation-call structural tests still hold). The record is revision-bound, with provenance HUMAN, and is kept on `state.human_contract_authorizations`, which is honoured by the pre-write gate and the terminal re-check.
- **Persistence.** Classifications are `CONTRACT_CHANGE_CLASSIFICATION` obligations.

### Brownfield baseline `auto` policy (`kriya/workflow/baseline_policy.py`) — PRD-024
- **Trigger.** `decide_auto_baseline(route, planned_files, workspace, workspace_revision=)` is the deterministic `auto` trigger. Preconditions: a brownfield route, a git identity, existing tests, a planned change to existing source. Then a regression-risk signal: risk >= MEDIUM, non-LIGHT weight, refactor, a `_RISKY_IMPACT` component (incl. configuration_change) or a broad change (`BROAD_EXISTING_CHANGE_FILES`). A test naming a changed source is `signals.supporting` only, never a trigger.
- **Reuse.** The applied candidate's terminal full-suite run is kept on the engine (`full_suite_evidence_for_reuse`, keyed by the post-apply workspace content hash) and passed as `capture_brownfield_baselines(prior_full_regression=)`; reused only when content hash, command, selection and environment (which includes `verification_policy_identity`) match and the run completed. `validation_baseline.full_regression_source` records `captured`/`resume`/`prior_full_suite`. `effective_baseline_policy` turns `auto` into `required`/`disabled`, evaluated in `run_generation_workflow` before capture (`validation_baseline.policy` event). A triggered baseline is as binding as `required`, and its hard stop names the trigger reasons.
- **Environment identity.** `baseline_environment_identity` (execution mode + PRD-011 `toolchain_fingerprint`) is recorded as the invocation's `environment_fingerprint` PRE, and recomputed POST over the candidate's toolchain declarations. Both sides are computed over the same declaration overlay, so a dependency-only edit is the same environment. `classify_baseline_delta(post_environment=)` returns NOT_COMPARABLE on mismatch: no failure is excused, so any POST failure blocks, and a green suite passes (PRD-011 migrations stay possible under sealed `required`).
- **Per-test availability.** `BaselineDeltaResult.level2_available`/`level2_unavailable_reason` make an unparsed per-test comparison explicit. RESOLVED_FAILURE is FIXED.
- **Maven runs.** A Maven test run is identified by its Surefire "Results:" blocks (`surefire_results_summary` - the level-1 fingerprint; `parse_surefire_structured_outcomes` - level 2), never its log (Spring Boot timestamps, the container hostname and log interleaving differ between identical runs). The comparison rules are versioned by `BASELINE_COMPARISON_VERSION` (`validation_baseline.py`, where each bump is explained; a stored result under another version is not reused), so the number is not repeated here.
- **Pytest runs (REG-R1).** A candidate may be blamed only for a difference that is stable on the untouched baseline.
  - **Evidence.** Each pytest gate carries `pytest_evidence` (`test_execution.parse_pytest_case_evidence` over its own JUnit report): per test the outcome, exception type (pytest's crash-location line), message and body, plus integrity counts. The JUnit report is still deleted after reading.
  - **Authority.** When PRE and POST are both COMPLETE (FS-1A completeness plus integrity), `classify_pytest_per_test_delta` decides in the order id, outcome, type, message, body; the whole-output fingerprint is diagnostic only.
  - **Disputed tests.** Any blocking difference of an EXISTING test from the original baseline observation (another execution state = outcome + exception type, or the same failing state with another message/body) is `stability_required`, provisional until measured. Measured in the SAME verification context: `pytest_stability.establish_baseline_stability` re-runs the baseline's own gate call (`baseline_suite_run` in `run_generation_workflow`: same workspace, selection - a full-suite baseline is replayed as the full suite, never the disputed test alone) twice on the untouched baseline (revision checked before and after, pytest session facts must match; candidate observations are never an input).
  - **Behavior envelope (REG-R2).** The original observation and the replays together (none privileged) are the test's envelope (`validation_baseline.baseline_behavior_envelope`): the execution states the untouched baseline showed and, per state, message/body STABLE (seen 2+ times, identical), VOLATILE, or STABILITY_NOT_ESTABLISHED (seen once - never evidence against the candidate). Candidate state outside it: the provisional verdict blocks. Inside it: only a STABLE same-state field the candidate changed blocks (CHANGED_FAILURE); otherwise FLAKY_PREEXISTING (baseline showed 2+ states, non-blocking, flake-rate regression NOT_ASSESSED) or PRE_EXISTING_FAILURE. No envelope (absent from a replay, failed/incomplete replay, revision drift) keeps the provisional verdict; a same-state dispute is STABILITY_UNRESOLVED (blocking, never attributed). Never enveloped: missing tests, new failing tests, incomplete/invalid evidence. A non-blocking FAIL->PASS never triggers replays.
  - **Cache.** One measurement per `verification_context_id` (policy (3 = REG-R2), versions, session facts, revision, working directory, command, selection, environment, baseline run/report), reused for every disputed test of that context, checkpointed as `validation_baseline_pytest_stability`.
  - **Fail closed.** An incomplete or missing side blocks any failing POST. A pre-REG-R1 checkpoint (no `pytest_evidence` key) of a pytest workspace is recaptured (`OLD_CHECKPOINT_INSUFFICIENT`).
  - **Retention.** Every decision is an M1 `regression.decision`; raw stdout/stderr/JUnit ride on `gate.result`.
  - **Scope.** Non-pytest runners are byte-identical (`_whole_output_delta`).
- **Purity.** `validation_baseline.py` stays a pure comparison library (the replays live in `pytest_stability.py`).
