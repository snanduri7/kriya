When the UTF-8, byte-backed JSON parsers (those reading from an InputStream or a DataInput, and the non-blocking byte-array/ByteBuffer parsers) find an invalid character right after a root-level number, the error message may describe the first byte of the UTF-8 sequence instead of the decoded character. For example, the bytes '1', 0xC2, 0xA0 contain U+00A0 immediately after the number 1 with no whitespace separator. The error should report code 160 (the decoded Unicode code point), but the InputStream-based parser currently reports 194 (the raw first byte). Make the character reported for an invalid root-value separator be the decoded code point when the UTF-8 sequence is complete and well formed, consistently with other UTF-8 error reporting in these parsers, for every byte-backed input mode. Cases that are not a complete, valid sequence keep reporting the leading byte exactly as today: a sequence truncated by the end of input (0xC2 at EOF), a malformed continuation byte (0xC2 0x41, or 0xFF), and, for the non-blocking parsers, a sequence that is split across input chunks and not yet complete. The existing "Expected space separating root-level values" wording of the error is unchanged, and ASCII behavior must not change.
