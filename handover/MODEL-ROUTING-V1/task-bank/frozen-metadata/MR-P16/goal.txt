A `pydantic_settings` model that enables `validate_by_name=True` (or `populate_by_name=True`) and declares a field whose `validation_alias` is an `AliasChoices(...)` that does not list the field's own name does not accept the field name on the command line, although the environment-variable source already accepts it in that configuration. Example: with `cli_kebab_case=True`, `project_id: str = Field('default', validation_alias=AliasChoices('gcp_project_id', 'uno_metadata_project_id'))`, running `CliApp.run(Cfg, cli_args=['--project-id', 'x'])` fails with a parsing error unless `'project_id'` is duplicated inside the `AliasChoices`. Make the CLI source also accept the field's own name (with the usual kebab-case and case handling) when `validate_by_name` or `populate_by_name` is enabled, for the top-level model and for models used as `CliSubCommand`s; the aliases (`--gcp-project-id`, `--uno-metadata-project-id`) must keep working. Without either option the field name must still not be accepted for such a field: the same invocation (with `cli_exit_on_error=False`) must raise `SettingsError` ('error parsing CLI').
