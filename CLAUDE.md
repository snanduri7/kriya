# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Kriya is a local-first, multi-agent AI engineering platform (Python, `kriya/` package). It runs entirely against local LLM/embedding endpoints (Ollama or any OpenAI-compatible server) and coordinates Planner → Architect → Developer → Reviewer agents to plan, generate, fix, and review code inside a target repository, backed by a hybrid AST/vector/lexical index stored in SQLite.

## Commands

```bash
# Setup (Python 3.10+)
python3 -m venv .venv
source .venv/bin/activate
pip install -e .                    # installs `kriya` and `kriya-mcp` console scripts

# Run the CLI (editable install puts these on PATH inside the venv)
.venv/bin/kriya doctor               # checks dirs + LLM/embedding connectivity
.venv/bin/kriya --config kriya.yaml <command>   # -c/--config points at a project config

# Tests
.venv/bin/pytest                     # full suite (asyncio_mode = strict, see pyproject.toml) - entirely mocked, no live model calls
.venv/bin/pytest tests/test_workflow.py            # single file
.venv/bin/pytest tests/test_workflow.py::test_workflow_fallback_chain   # single test
.venv/bin/pytest -m live_model       # tests/test_live_smoke.py only - needs a real local Ollama running, excluded by default
```

There is no separate lint/format command configured in this repo — don't invent one.

## Working practices in this repo (quota discipline)

The user is quota-conscious in this repo specifically — apply these by default, without being asked each session:

- **Never run `.venv/bin/pytest` (any invocation, including a single file/test) as part of normal work.** Hand the exact command to the user and let them run it in their own terminal, reporting pass/fail back. This applies even to a quick sanity check after a small edit.
- **Don't launch long-running or live-model work (a `kriya generate`/`fix` run, `-m live_model` tests, eval batches) and then poll it from inside the session** (repeated Bash/Read check-ins, `ScheduleWakeup` loops) — every check-in costs a turn even while "just waiting." Either hand the command to the user's terminal, or start it with `run_in_background` and wait for the actual completion notification; only peek at interim output when there's a concrete reason (e.g. confirming it didn't fail fast), not out of curiosity.
- **Prefer fewer, well-scoped tool calls over several exploratory ones.** Batch independent reads/searches in parallel rather than trickling them out one at a time.
- **Be deliberate about spawning subagents (the `Agent` tool) — don't reach for one by default.** Each subagent runs its own requests against the model, on top of whatever this session has already spent. Only spawn one when the task genuinely needs isolated context (a review that shouldn't pollute the main thread) or real parallelism, and confirm with the user first for anything nontrivial (a full-package review, multiple parallel agents) rather than launching it unasked. When a subagent's task is simple/mechanical (a lookup, a narrow lint pass, not a judgment call), pass a cheaper `model` override (e.g. `haiku`) instead of defaulting to the parent session's model.
- **Watch context length in a long session — 73% of this account's usage has come from sessions sitting above 150k tokens.** Longer sessions cost more even with prompt caching. At a natural checkpoint (a chunk of work just committed, about to pivot to an unrelated task), suggest `/compact` to shrink the working context, or `/clear`/a fresh session when the next task doesn't need this thread's history at all — see `feedback_session_resume_hygiene.md` in this project's memory for the existing convention of resuming via explicit memory pointers rather than "continue where we left off."
- Ordinary work stays in-session as normal: writing/editing code, quick targeted greps, `git status`/`git diff`/`git log`, doc updates, single fast commands.

## Live-model CI tier (`tests/test_live_smoke.py`, `.github/workflows/ci.yml`'s `live-model-smoke` job)
Every other test in this repo runs against mocks - zero live LLM/embedding calls. `pyproject.toml`'s `addopts = '-m "not live_model"'` excludes this tier by default (both locally and in the `test`/`lint`/`lock-file` CI jobs); pass `-m live_model` explicitly to run it. CI runs a blocking supported-primary-model job and a scheduled three-model matrix. The bar is deliberately narrow: "did the real pipeline complete without crashing on a real API response shape," not code-generation quality. `skills.load_global` and `skills.load_cwd` control the implicit skill sources independently; set both false for a reproducible plain-Kriya run using only the explicit `paths.skills` directory.

## Configuration resolution

`kriya/config/config.py::load_config()` layers config in this order (later wins, dicts are shallow-merged one level deep):
1. `kriya/config/default_config.yaml` (packaged defaults)
2. `kriya.yaml`/`kriya.yml` — first checked in CWD, then in the Kriya install directory, unless `--config` is passed explicitly
3. `AppConfig` (pydantic model in the same file) validates the merged result

Relative `paths.*`, `plugins.directory`, and `logging.file` values are resolved against the directory the config file was loaded from (or the install dir for the packaged default), using `os.path.realpath` (resolves symlinks) — `logging.file` specifically is canonicalized to this ONE resolved absolute path before classification, so the value SEC-009 authority resolution inspects and the value `configure_logging()` actually opens can never diverge (unlike `paths.*`/`plugins.directory`, which only rewrite a `"./"`-or-`"../"`-prefixed value, `logging.file` resolves any string value uniformly — a bare-relative value with no prefix must still anchor to `config_dir`, not process CWD). `autonomy.sensitive_paths` always has a baseline set of regexes (`.env`, secrets, `.github/workflows/`, `Jenkinsfile`, credentials, password) force-appended regardless of user config — don't remove that expectation when touching `load_config`.

**SEC-009 P1 — configuration authority (`kriya/config/authority.py`):** a config value's provenance (which source set it: packaged default, auto-discovered CWD/install-dir, explicit `--config` inside/outside the workspace, or a `runtime_profile` preset expansion) is tracked per leaf field through `load_config()`'s merge, then checked against a `REPOSITORY_SAFE`/`USER_AUTHORITY`/`SECURITY_AUTHORITY`/`PLATFORM_POLICY` classification *before* `AppConfig` is constructed. Only `PACKAGED_DEFAULT`/`PLATFORM_FLOOR` sources are unconditionally trusted; every other source may only set explicitly-allowlisted `REPOSITORY_SAFE` fields — anything else (including an unclassified/future field) is a violation, before `Kernel`/`PluginManager`/`MCPManager` ever see the config. `mcp.*`, `plugins.directory`/`enabled`, `execution_policy.*`, `runtime_profile`, and `autonomy.acquisition_registry_hosts`/`egress_policy`/`risk_threshold_lines`/`sandbox_env_allowlist` are `SECURITY_AUTHORITY`/`PLATFORM_POLICY`. `paths.{skills,memory,logs}` and `logging.file` are classified dynamically (`path_field_classification()`): `REPOSITORY_SAFE` only if the resolved real target stays inside `config_dir`, `SECURITY_AUTHORITY` (escape) otherwise — a bug that skips the override fails CLOSED (both are absent from the static `_REPOSITORY_SAFE_FIELDS` table, present in `_SECURITY_AUTHORITY_FIELDS` for accurate labeling only). `logging.file: null` (disabling file logging) is `REPOSITORY_SAFE` unconditionally — removing a capability grants no authority. When adding a new `AppConfig` field, add it to `authority.py`'s explicit `_REPOSITORY_SAFE_FIELDS` allowlist only if a repository genuinely cannot use it to gain execution/network/filesystem/policy authority; otherwise leave it unlisted (fails closed by default) or add it to `_SECURITY_AUTHORITY_FIELDS` for an accurate error message.

**SEC-009 P2 — durable approval (`kriya/config/authority_approval.py`, `kriya authority inspect|approve|revoke`):** a violation isn't immediately fatal — it's checked against a digest-bound approval artifact covering the EXACT current security-relevant field set (any addition/removal/value change invalidates the whole approval; see `build_security_field_records()`/`compute_set_digest()`). The artifact lives OUTSIDE the workspace (`~/.kriya/authority/<workspace_id>.json` by default, override via `KRIYA_AUTHORITY_HOME`) — never inside it, so repository content can never ship its own self-authorizing approval; the same rule is enforced on an explicit `--trust-file`/`KRIYA_TRUST_FILE` (CI/operator-supplied) via `validate_trust_path_outside_workspace()`. Secrets (`mcp.*.env` values) are salted-and-digested, never persisted in plaintext. `kriya authority` is reachable even when the current config is denied (bypasses `main()`'s eager `load_config()` — see `ctx.invoked_subcommand == 'authority'`). With no valid approval, behavior is byte-identical to P1 fail-closed. See `docs/assurance/KRIYA_PRODUCTION_RISK_REGISTER.md`'s SEC-009 entry for the full design rationale, threat-case coverage, and closure evidence (`CLOSED`, 2026-09-12, after a bypass/closure review and fix — see that entry's `logging.file` containment addendum).

## Architecture

### Kernel / registry / plugins (`kriya/core`, `kriya/plugins`)
`Kernel` (`kriya/core/kernel.py`) is a thin async lifecycle object holding a `ComponentRegistry` (category → name → instance, e.g. `registry.get("tool", "filesystem")`) and an `EventSystem` (pub/sub, supports sync and async handlers, emits `kernel_starting`/`kernel_started`/`plugin_initialized`/etc.). `PluginManager` (`kriya/plugins/plugin.py`) discovers plugin packages under `plugins.directory`, imports each as a top-level module (so plugin folder names must be valid, unique module names), finds `BasePlugin` subclasses, and calls `initialize()`/`shutdown()` on them — plugins register `BaseTool` instances into the kernel registry (see `plugins/core_tools/__init__.py` for the filesystem/shell/git/search/ast/validate_refactor tools).

### MCP subprocess environment (`kriya/mcp/mcp.py`) — SEC-003
`MCPManager.start_all()` (called from `Kernel.start()`) is the only place `MCPClient` is constructed, and `MCPClient.start()` is the only MCP subprocess creation site in the codebase. Its environment is built by `build_mcp_subprocess_env(configured_env)`, never ambient `os.environ`: `MCP_BASELINE_ENV_ALLOWLIST` (`LANG, LC_ALL, TMPDIR, TEMP, TMP`, plus real `PATH` always via `kriya/tools/sandbox.py::build_restricted_env()`, reused as-is from SEC-001) UNION `cfg.mcp.<server>.env` (already SEC-009-authorized before this function runs). `HOME` is deliberately excluded from the baseline — it's the implicit discovery root for a wide range of third-party tooling (`.ssh`, `.gitconfig`, cloud-CLI state, SDK config), not a low-authority compatibility variable like `LANG`/`TMPDIR` — and is only present if a server's own `env` sets it explicitly. Proxy variables (`HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY`/`NO_PROXY`) are never in the baseline either. `build_mcp_subprocess_env()` is pure and non-raising — there is no fallback path to ambient `os.environ` on any failure. When adding a new MCP-adjacent subprocess call, reuse `build_mcp_subprocess_env()`/`build_restricted_env()` rather than merging `os.environ` directly.

### MCP subprocess lifecycle (`kriya/mcp/mcp.py`, `kriya/mcp/lifecycle.py`) — SEC-004
Every MCP server's process is spawned via `kriya/mcp/lifecycle.py::spawn_mcp_process()` (process-group isolation via `start_new_session=True`, CPU/memory rlimits via SEC-001's `posix_resource_limits_preexec_fn`, a hard per-line stdout ceiling via asyncio's own `limit=` kwarg) and torn down via `terminate_mcp_process()` (bounded `RUNNING → SIGTERM → bounded wait → killpg(SIGKILL) → bounded reap → CLOSED` state machine, reusing `kriya/tools/process.py::terminate_process_tree()` for the process-group kill — promoted from a `ProcessController`-only helper this same pass). `MCPClient` tracks an explicit `_ConnState` (not a single boolean) and bounds every server-controlled await: `start()` wraps the full launch+handshake in `mcp_lifecycle.startup_timeout_seconds`, `_send_request()` wraps every request (including `initialize`) in `mcp_lifecycle.request_timeout_seconds`. An oversized stdout line (`ValueError` from the StreamReader `limit`) or stdout EOF both run the full `_close()` sequence — connection state, process, reader tasks, and pending-request Futures are torn down together, and `MCPManager._on_client_closed()` proactively unregisters that server's tools so a dead connection can never keep routing calls (stale-lifecycle-state cleanup). `MCPManager.start_all()` is atomic — any server failing to start rolls back every server already started in that same call. stderr retention is a bounded rolling buffer (`mcp_lifecycle.max_stderr_buffer_bytes`) with LOGGING separately capped (`MCPClient._STDERR_LOG_LINE_CAP`) so a flooding server can't exhaust Kriya's own logs either. All `mcp_lifecycle.*` bounds are `SECURITY_AUTHORITY` under SEC-009 — a repository can never weaken any of them. `memory_mb` (RLIMIT_AS) is deterministic on Linux, advisory-only on macOS (an accepted SEC-001 platform limitation); `cpu_seconds` (RLIMIT_CPU) is a cumulative LIFETIME budget, not a rate limit — true CPU/memory rate/ceiling enforcement needs real container/cgroup containment, which belongs to **TOOL-003** (see that section below), not attempted here. SEC-004 does not touch tool-call authorization or MCP execution containment — it only bounds the lifecycle of an already-authorized (SEC-009) connection.

### MCP invocation authority (`kriya/mcp/mcp.py`, `kriya/policy/execution.py`, `kriya/policy/model.py`) — TOOL-002 P1
Every MCP `tools/call` passes a deterministic `ExecutionPolicy` decision, bound to structured identity, immediately before `MCPClient.call_tool()` — the single production choke point (`MCPTool._run()`), covering every route that reaches an MCP tool (`kriya tools execute`, and any future TOOL-tagged `SubtaskExecutor` dispatch — both call `BaseTool.execute()`, which is the only path into `_run()`). This is **real enforcement, unconditionally** — unlike every other `ExecutionPolicy` consumer (audit-only unless `execution_policy.mode == "enforce"`), MCP has no legitimate "Kriya's own trusted command" carve-out to ever fall back on, so `MCPTool._run()` never reads `mode` at all; DENY, REQUIRE_APPROVAL (P1 has no reachable approval mechanism at this call site, so it fails closed, mirroring `ShellTool`/`GitTool`'s own established precedent), and a throwing/unavailable policy engine all raise `PolicyDeniedError` before `self.client.call_tool()` is ever reached — this is Kriya's *second* deliberate, explicit exception to MA4's audit-only mandate, after `AuthorizedFileWriter`.

`ActionType.MCP_TOOL_CALL` (new) is governed by a new `ExecutionPolicy._check_mcp_invocation` stage. It decides purely on **structured identity** — `MCPToolIdentity(server_identity, tool_name, schema_digest)` (`kriya/policy/model.py`), bound once at `MCPTool.__init__` from the same `tool_meta` snapshot the actual dispatch target (`self.client`, `self._exact_tool_name`) is also derived from, so a policy decision and its own dispatch target can never diverge — never a flattened display string (`f"{server}_{tool}"`, still used for registry lookup/UI only). `schema_digest` is a SHA-256 over the tool's `inputSchema` with every `description` key stripped at any nesting depth first (`compute_mcp_schema_digest`) — a schema/tool/server change is a different identity, so an earlier approval never silently carries over. The server's own advertised `description`/annotations/result text and the call's actual arguments are never inputs to this decision at all (Invariant: MCP-provided metadata may describe an operation, never authorize it) — P1 intentionally does not infer filesystem/network/process semantics from anything; the only decision it can make is whether this exact identity is in an explicit, non-persistent, constructor-supplied approved set (`ExecutionPolicy(approved_mcp_tool_identities=...)`, empty by default) — every real call in a default deployment therefore falls through to `REQUIRE_APPROVAL` → fails closed, until a real operator-facing capability/approval mechanism (TOOL-002 P2) exists.

**This is invocation authority only.** An ALLOWed call reaches an MCP subprocess whose filesystem/network/process containment depends entirely on `autonomy.mcp_contained_execution_required` (default False, host-side/unconstrained; `True` = real OCI enforcement — see the "MCP OCI enforcement — TOOL-003 P2" section below). SEC-009 config-activation approval and this invocation approval are deliberately separate decisions, never conflated — starting a server successfully never populates the approved-identity set. Reuses existing machinery throughout: `PolicyDeniedError` (same type `ShellTool`/`GitTool` already raise), `kriya/policy/telemetry.py::build_decision_record()` (extended with three narrow, named MCP fields — never a blanket `metadata` dump). See `docs/assurance/KRIYA_PRODUCTION_RISK_REGISTER.md`'s TOOL-002 entry for the full investigation/decision record and the honest security-scope statement.

### MCP durable invocation approval (`kriya/mcp/invocation_approval.py`, `kriya/cli.py`'s `mcp` group) — TOOL-002 P2
**Restores the real, operator-facing production capability P1 disclosed as lost**, without touching P1's own static test-injection mechanism at all. `ExecutionPolicy.__init__` gained a second, independent, additive constructor parameter — `mcp_invocation_approval_resolver` — consulted by `_check_mcp_invocation` only AFTER the pre-existing `approved_mcp_tool_identities` static frozenset check (unit-test injection only, completely unchanged, still checked first). `MCPManager.__init__` — the single production `MCPManager` construction site (`Kernel.__init__` always constructs one with no explicit `execution_policy`) — wires the real resolver by default via `kriya/mcp/invocation_approval.py::resolve_mcp_invocation_approval(workspace_root=os.path.realpath(os.getcwd()))`, the exact same `workspace_root` derivation `MCPManager.start_all()` already uses for capability-profile resolution — one consistent workspace-identity source, never two independently-computed values that could drift apart.

`kriya/mcp/invocation_approval.py` is a NEW, PARALLEL module — modeled closely on SEC-009 P2's own `kriya/config/authority_approval.py` patterns (atomic tmp-file+`os.replace()` write, workspace-identity binding, digest-bound records, corrupt/unknown-format fail-closed) but a completely separate artifact/store, never conflated with it (Invariant 12: SEC-009 config approval ≠ TOOL-002 invocation approval — proven by a dedicated test using a REAL SEC-009 approval and confirming it does not authorize any MCP call). The durable approval binding is `workspace_id + MCPToolIdentity(server_identity, tool_name, schema_digest) + MCPCapabilityProfileIdentity.profile_digest` — a SHA-256 over a canonical JSON dict (`compute_invocation_approval_binding_digest()`), covering exactly the same five fields Invariant 9/10 require; ANY drift in ANY one of them (server, tool, schema, capability profile, or workspace) invalidates the whole binding, with no partial/best-effort match. The store lives OUTSIDE the workspace (`~/.kriya/mcp_approvals/<workspace_id>.json` by default, override via `KRIYA_MCP_APPROVAL_HOME`, mirroring `KRIYA_AUTHORITY_HOME`'s own precedent exactly) so a malicious repository can never ship its own self-authorizing approval alongside a hostile MCP config in the same commit. The resolver this module hands `ExecutionPolicy` reads the artifact FRESH FROM DISK on every single call — no caching layer anywhere — which is what makes both Task 7's revalidation requirement and Task 11's "revocation takes effect without restarting Kriya" requirement true by construction rather than by convention.

`_check_mcp_invocation`'s capability-profile-identity metadata (audit-only under TOOL-003 P1) is now ALSO read here, but strictly as an anti-drift BINDING KEY inside the durable-approval check — never as an independent authority source (Invariant 13 stays true: a wider capability profile alone still grants nothing; an approval merely stops validating once the profile it was granted under changes). A resolver exception is deliberately NOT caught inside `_check_mcp_invocation` or `ExecutionPolicy.evaluate()` — it propagates to `MCPTool._run()`'s own PRE-EXISTING try/except (built during TOOL-002 P1, unchanged), which already converts ANY policy-evaluation exception into a fail-closed `DENY`. This is real reuse, not incidental: it means Task 15/required-test-24 ("approval-store exception fails closed") needed zero new exception-handling code.

CLI (`kriya/cli.py`'s new `mcp` group, mirroring `authority_group`'s own `inspect`/`approve`/`revoke` shape): `kriya mcp inspect` starts the real, configured MCP servers (exactly like `tools list`/`tools execute`) and shows every discovered tool's exact identity, capability-profile summary/digest, containment required/active/backend, and current approval status — read-only, never writes. `kriya mcp approve <flattened_name>` resolves `<flattened_name>` (the exact `server_tool` string `tools list`/`mcp inspect` themselves print) via a REAL registry lookup (`kernel.registry.get("tool", name)`) — **never by parsing/splitting the string** — then binds the approval to that specific `MCPTool` object's own `.identity`/`.capability_profile_identity`, so even a flattened-name collision between two servers can never transfer approval from one structured identity to another (Invariant 14, required test 22): whichever object the registry actually holds under that name is exactly what real dispatch would also invoke, so approval and dispatch can never target different objects. `kriya mcp revoke <flattened_name>` matches on `(server_identity, tool_name)` alone — not the full binding digest — so a STALE approval (whose profile/schema has already drifted, and therefore no longer matches any current binding digest) can still be found and removed. `-y` on `tools execute` never creates or substitutes for approval — it only ever skips the ordinary shell-tool-style human-review confirmation prompt, which MCP never reaches in the first place (P1's own real-enforcement gate raises `PolicyDeniedError` before that prompt is ever shown).

Telemetry (`kriya/policy/telemetry.py`, `PolicyDecisionRecord`): a fourth narrow, explicit exception to "never blanket-dump metadata" (after the tool-identity, capability-profile-identity, and this same convention) — `metadata["mcp_containment_identity"]` (a new closed, three-field `MCPContainmentIdentity` in `kriya/policy/model.py`: `required`/`active`/`backend`) is extracted into three named `mcp_containment_*` fields, so an ALLOWed call's audit trail always shows whether TOOL-003 containment assurance genuinely applied — host-mode (`containment_required=False`) is recorded EXPLICITLY as `False`/`False`/`None`, never silently omitted, so it can never be mistaken for containment evidence. The durable-approval ALLOW path gets its own reason code (`MCP_TOOL_DURABLE_APPROVAL_VALID`), distinguishable in every log/record from P1's static-injection `MCP_TOOL_IDENTITY_APPROVED`.

**Honest security statement (state exactly, no stronger claim):** TOOL-002 P2 lets an operator explicitly, durably approve a specific MCP tool's exact identity+capability binding, and revalidates that full binding — never merely a name — before every subsequent invocation. It does not grant, widen, or substitute for TOOL-003 capability/containment authority in either direction; an approved call under `mcp_contained_execution_required=True` is still fully OCI-constrained, and an approved call under the default `False` executes host-side with NO containment assurance, which every approval/inspection surface reports explicitly rather than implying otherwise. TOOL-002 and TOOL-003 remain OPEN in the risk register pending combined adversarial closure — this package does not close either.

### MCP capability authority (`kriya/config/config.py`, `kriya/mcp/capability.py`, `kriya/mcp/mcp.py`) — TOOL-003 P1
**Defines and governs MCP capability authority; does not yet enforce it at the OS/container boundary.** For every configured `mcp.<server>`, `mcp.<server>.capabilities.*` (`MCPCapabilityConfig`, pydantic) declares the MAXIMUM filesystem/network authority that server may ever be declared to possess — `workspace_read`/`workspace_write`/`temp_read_write`/`dependency_cache_read` (booleans), `additional_read_paths`/`additional_write_paths` (explicit paths), and `network`/`network_hosts` (`"denied"` default / `"explicit_destinations"` + a host list / `"unrestricted"`). The safe default is **nothing declared** — deliberately not grandfathering today's real (unenforced) host access, so the day `TOOL-003 P2` wires this into real containment, an operator who never explicitly widened a server's profile starts genuinely restricted rather than needing to lock broad implicit trust back down. There is no configurable process field at all — SEC-004's `start_new_session=True` is lifecycle ownership only, never a capability restriction, so every resolved profile instead carries a fixed, honest constant (`kriya/mcp/capability.py::PROCESS_AUTHORITY_STATEMENT = "unconstrained_pending_oci_containment"`).

The entire `mcp.<server>` block (capabilities included) is already unconditionally `SECURITY_AUTHORITY` under SEC-009 (`kriya/config/authority.py`'s `classify_field()` — the `top_key == "mcp"` branch fires before any leaf is even inspected), so no new classification-table entries were needed: any repository-sourced widening of a server's capabilities is denied before `AppConfig`/`MCPManager` ever see it, exactly like every other `mcp.*` field, and SEC-009 P2's own digest-drift mechanism (`kriya/config/authority_approval.py`) already invalidates approval the instant a capability value changes. Filesystem path safety (a relative `additional_*_paths` entry escaping via `..`/a symlink) is rejected once, at config-load time, in `resolve_config_state()` — anchored to `config_dir`, the same anchor and the same realpath-based idiom `paths.*`/`logging.file` already use, for the identical reason (the value SEC-009 digests and the value later bound to a real `MCPClient` must be the same single resolved value, never independently re-resolved against a possibly-different CWD). An **absolute** path is a deliberately different, supported case — an explicit host path outside the workspace, never rejected as an "escape," still gated by the same blanket SEC-009 approval requirement.

`kriya/mcp/capability.py::resolve_mcp_capability_profile()` turns an already-validated `MCPCapabilityConfig` into a frozen, canonical `MCPCapabilityProfile`, bound to `MCPClient.capability_profile` in `MCPManager.start_all()` *before* the client (and therefore the process) is ever constructed — a pure data/authority binding. `MCPTool` carries a parallel `MCPCapabilityProfileIdentity` (`kriya/policy/model.py`, strings-only, no import from `kriya/mcp/` — preserves the existing one-directional `mcp → policy` dependency) into `ActionRequest.metadata` alongside TOOL-002's own `MCPToolIdentity`, surfaced in telemetry (`build_decision_record()`) for audit context **only** — `ExecutionPolicy._check_mcp_invocation` never reads it, so capability approval (SEC-009, config-time) can never substitute for or widen invocation approval (TOOL-002, per-call), and vice versa. `NetworkAuthority` (the SEC-001/target-code-sandboxing enum) is deliberately NOT extended with a third member for this — `kriya/tools/containment_oci.py`'s `OCIContainmentBackend.prepare()` has no exhaustive-match guard on it, so a shared new member risks a silent full-UNRESTRICTED fallback in that unrelated path; MCP capability profiles use their own `MCPNetworkAuthority` enum instead, with matching value-strings for a lossless future mapping.

### MCP OCI enforcement (`kriya/mcp/containment_adapter.py`, `kriya/tools/containment.py`, `kriya/tools/containment_oci.py`, `kriya/mcp/mcp.py`) — TOOL-003 P2
**Enforces the resolved `MCPCapabilityProfile` at the OCI boundary, opt-in.** `autonomy.mcp_contained_execution_required` (default **False**, SEC-009 `SECURITY_AUTHORITY`, mirroring `contained_execution_required`'s own established pattern) is a deliberate default-flip decision made explicitly with the user (2026-09-13): "always require containment for every MCP server" was considered and rejected as the *default* because every MCP server is `TrustClass.UNTRUSTED_EXECUTION` (`backend_required=True` unconditionally), so an unconditional requirement would make Docker a hard MCP dependency and break ~40 pre-existing tests that spawn real MCP subprocesses with no Docker involved. A strict-superset relationship holds instead — flipping the default to `True` later is a one-line config change, not a rearchitecture. **Once `True`, "no raw-host fallback" is absolute**: `containment_backend` still `"none"` (the packaged default) means `NullContainmentBackend` refuses any non-`UNRESTRICTED` profile outright (`BackendUnavailableError`) — the server does not start, period, never silently downgrading to host-side execution. `MCPClient.containment_required`/`.containment_active` are two DIFFERENT booleans, both exposed for audit: the former is what was demanded, the latter is only `True` once a real container was actually prepared — a host-side run must never be misread as containment evidence.

`kriya/mcp/containment_adapter.py::map_capability_profile_to_containment()` is the ONE Kriya-owned, explicit mapping from `MCPCapabilityProfile` to `ContainmentProfile` — no server-supplied input (name/description/schema/annotations/arguments/results) is ever an input. `ContainmentProfile` gained purely-additive fields (all defaulting to today's exact pre-existing shape, zero behavior change for `PolymorphicValidator`/`service_runtime`'s own compile/test/managed-service callers): `mount_workspace`/`workspace_write` (no mount at all unless `workspace_read` or `workspace_write` is granted; `ro` vs `rw` otherwise — real bind-mount modes, not just a policy note), `additional_mounts` (a `MountSpec` per resolved `additional_read_paths`/`additional_write_paths` entry, at fixed Kriya-chosen container paths `/kriya/mcp/extra/{ro,rw}/<n>`), `resolved_env` (MCP's own SEC-003 `build_mcp_subprocess_env()` output baked into `-e` flags **verbatim**, deliberately bypassing the unrelated `_HOST_ONLY_ENV_VARS` filter built for host-path-shaped compile/test env values — that filter would otherwise silently drop an operator's own explicit, SEC-009-approved `mcp.<server>.env.HOME` override), `persistent_stdio` (`-i`, never `-t` — a pseudo-TTY would corrupt MCP's JSON-RPC line framing; lets `MCPClient`'s existing stdio reader/writer work completely unchanged, since the container's OWN foreground process — `docker run -i ... image mcp_command`, not a `sleep infinity` + `docker exec` placeholder — literally IS the MCP server, and `docker run`'s own subprocess stdin/stdout is what `MCPClient` already reads/writes), `run_as_uid`/`run_as_gid` (Task 7 non-root: `resolve_mcp_container_identity()` — the fixed "nobody" UID/GID (65534) when no write authority is granted at all; the REAL host UID/GID, fail-closed on mismatch, when a write mount exists, mirroring SEC-008's own `_resolve_acquisition_identity()` reasoning without touching that CLOSED registry-scoped code path), `authority_label` (the capability-profile digest, as `--label kriya.mcp-capability-digest=<digest>` — the audit chain server→digest→container instance, and what every real-OCI test's zero-leftover-containers check filters on).

`MCPNetworkAuthority.EXPLICIT_DESTINATIONS` is an explicit **STOP**, not an approximation: `kriya/tools/containment_oci.py`'s real per-run scoped-egress mechanism (SEC-006 — a dedicated Squid proxy container + fresh Docker network + in-container iptables/privilege-drop, all torn down after ONE finite acquisition command) is the closest existing primitive, but adapting it to a session-LIFETIME MCP connection (the proxy/network would need to live for the whole connection, with their own health-monitoring and cleanup wired into `MCPClient`'s own close sequence) is real, additional infrastructure work, not a bounded reuse — a server configured with `network: explicit_destinations` fails closed with a typed `MCPContainmentUnsupportedError` (a `ContainmentSetupError` subclass) the moment containment is required, never silently downgraded to `DENIED` (looks like a working config doing less than declared) or `UNRESTRICTED` (the exact silent widening this exists to prevent).

The container's OWN process (`docker run -i`) is what `spawn_mcp_process()` (`kriya/mcp/lifecycle.py`) spawns when a `command_prefix` is supplied — host CPU/memory rlimits are skipped in that case (meaningless for the lightweight `docker` CLI wrapper; the container's own `--memory`/`--cpus` flags, already derived from the SAME `mcp_lifecycle.cpu_seconds`/`memory_mb` bounds, are the real limit — and are a REAL cgroup hard limit even on macOS Docker Desktop, unlike host-mode `memory_mb`'s existing "advisory-only on macOS" limitation). Teardown has a SECOND lifecycle layer beyond SEC-004's own process-group kill: `PreparedContainment.cleanup` (`docker rm -f`) runs via `run_in_executor` (never blocks the event loop) in `MCPClient._close()`, bounded by its own SEC-009-governed `mcp_lifecycle.container_cleanup_timeout_seconds` (default 15s) — additive to, never a replacement for, `shutdown_grace_seconds`/`force_kill_reap_seconds`. A timeout here is logged, not raised, mirroring `terminate_mcp_process()`'s own "reap timeout after the forced kill is still terminal" precedent — `docker rm -f` is itself the forceful path.

Testing note: an MCP server's own code (the script/binary named in `mcp.<server>.command`/`args`) must be something the SELECTED CONTAINER IMAGE can already resolve — a bare command name on the image's own `PATH` (`python3`, matching `_select_image_and_cache_mount()`'s own detection), or a path inside a mount the operator's OWN capability profile already grants (e.g. `additional_read_paths` naming the directory holding a homegrown script) — never an absolute HOST-specific path (a venv's `sys.executable`, say), which cannot resolve inside the container's own filesystem namespace at all. This is inherent to the containerization model, not a TOOL-003 P2 limitation: a real npm/pip-distributed MCP server's code must already be baked into the image (or otherwise present) rather than fetched at container start, since `network=DENIED` blocks any runtime install.

**Honest security statement (state exactly, no stronger claim):** TOOL-003 P2 enforces the operator-authorized MCP capability profile at the OCI boundary from server startup onward, when `autonomy.mcp_contained_execution_required` is `True`. MCP invocation authority remains separately governed by TOOL-002. `EXPLICIT_DESTINATIONS` network authority is not yet enforceable (fails closed, never approximated). When `mcp_contained_execution_required` is `False` (the default), TOOL-003 P1's own P1-era statement still applies in full: an MCP process that starts still has the host capabilities of its execution environment.

### The generation pipeline (`kriya/workflow/workflow.py`)
`WorkflowEngine.run_generation_workflow` is the core orchestration and is long/stateful by design — read it end-to-end before modifying, don't assume a stage is isolated:
1. **KnowledgeGuard stage 0** (`kriya/tools/knowledge.py`) — scans the goal text for library/version mentions that postdate the configured knowledge cutoff and can short-circuit the whole run with a `knowledge_gap` status requiring explicit confirmation (`--yes`, `--knowledge-policy`, `--ack-knowledge-gap` in the CLI).
2. **Repository analysis** via `RepositoryAnalyzer` (`kriya/analyzer/analyzer.py`) plus **skill matching** via `SkillEngine` (`kriya/skills/skill.py`) — skills activate based on repo facts (dependencies/frameworks detected in analysis) or goal-text/tag matches, not just keywords, and respect `supported_versions` ranges.
3. **Graph RAG retrieval**: hybrid vector+lexical query (`kriya/memory/vector.py::LocalVectorStore.query_hybrid`, reciprocal rank fusion over a brute-force Python/NumPy cosine-similarity scan of BLOB-serialized embeddings in a plain SQLite `vector_chunks` table — no `sqlite-vec` extension is loaded anywhere — plus FTS5 lexical search) finds seed files, then `kriya/analyzer/graph.py::DependencyGraph` expands to a bounded neighborhood, each hit scored by relation-type weight over hop distance; results are assembled into a token-budgeted context string via `build_code_context`, which degrades the lowest-scored matched/related files first through skeletonization tiers (full → skeleton → signatures) when over budget.
4. **Untrusted learned-knowledge RAG**: anything ingested via `kriya learn` is queried separately and wrapped in explicit "Begin/End Untrusted Reference Context" fencing with an instruction not to treat it as commands — preserve this fencing if you touch that code path, it's a prompt-injection mitigation, not incidental formatting.
5. **Developer + Quality Gates loop**: runs inside an isolated, reused git worktree (`.kriya/worktree`, created/reset by `create_git_worktree`) so compile caches survive across retries. The developer agent (`kriya/agents/agent.py::DeveloperAgent`) either returns full file contents or anchored search/replace `edits` (applied via `apply_anchored_edits`, which requires the search block to match **exactly once**, normalized-whitespace, and to not straddle skeletonized/elided content). `PolymorphicValidator` (`kriya/tools/validate.py`) auto-detects the target stack from real markers (Java via pom.xml/build.gradle, Ruby via Gemfile/Rakefile/spec, Python via requirements.txt/pyproject.toml/setup.py/setup.cfg/Pipfile/any .py file present) and runs compile checks then targeted tests before a full regression run. Anything matching none of those markers is `"unknown"`, not a silent Python fallback — `run_compile_check`/`run_tests` return `success: True` (so the retry loop doesn't fail forever on a gate that can never run) but say plainly that nothing was actually validated, rather than falsely claiming a Python check passed against zero matching files. On failure the loop retries (bounded by `max(4, 1 + len(llm_chain))`), escalating through `config.llm_chain` fallback models and re-running the context budget allocator against each fallback's own `context_window`.
6. **Human approval gate**: triggered by `autonomy.mode == "human-in-the-loop"`, a sensitive-path match, or diff size exceeding `autonomy.risk_threshold_lines`; only after approval are worktree changes copied into the real workspace.
7. **Lesson extraction**: when a fallback-model escalation resolves an error, a one-sentence rule is extracted and staged into `skills/auto-<repo-slug>/staged_rules.txt` (promoted to `rules.txt` via `kriya skills approve`).
8. **Reviewer + trace log**: final review pass, then a run trace (plan, retries, gate outcomes, retrieved chunks, model hops) is persisted via `kriya/core/trace.py::TraceLogger` to `<paths.logs>/traces.db` (viewable with `kriya traces`).

### Agents (`kriya/agents/agent.py`)
`BaseAgent` wraps `LLMClient.complete`. `PlannerAgent`/`ArchitectAgent`/`ReviewerAgent` are single-shot prompt agents; `DeveloperAgent.run_generation` first asks the model for a file list, then either accepts a full JSON file-object array in one shot or falls back to iterative per-file generation (one completion per filepath) when the model only returns paths — there's also a raw-JSON-extraction fallback for models that wrap output in markdown or partial JSON. Any change to the developer agent's output contract needs to keep both the "batch JSON" and "iterative per-file" paths working, plus the `path`→`filepath` key normalization.

### Egress control (`kriya/core/llm.py`)
`LLMClient.complete` enforces `autonomy.egress_policy == "local_only"` by resolving the target base URL's hostname and rejecting anything not loopback/private/`.local` (`is_local_url`), raising `EgressViolationError`. This is a safety boundary, not a convenience check — don't bypass it silently when adding new LLM call sites.

### Storage (`kriya/core/db.py`, `kriya/memory/`)
All persistent state lives in SQLite databases under `paths.memory` (`vector_index.db`, `web_knowledge.db`, `dependency_graph.db`, `knowledge_cache.db`) and `paths.logs` (`traces.db`), opened with WAL journal mode and a busy timeout for concurrent-safe access. `vector_index.db` mixes code-index vectors and a separate `learned_knowledge` table (from `kriya learn`) — keep those namespaces distinct, the workflow relies on querying them separately with different trust levels.

### CLI (`kriya/cli.py`)
Click-based command group (`kriya` entry point defined in `pyproject.toml`). Key subcommands: `doctor`, `config`, `plugins`, `repl` (interactive session, see below), `prompt render|generate`, `tools list|execute`, `analyze <path>` (indexes + prints repo model), `skills list|show|create|approve`, `generate <goal>` (the full workflow), `review <path>` (LLM code review, git-status-aware for directories), `ask <question>` (repo Q&A with RAG), `learn` (ingest URL/file/text into the RAG store), `fix` (diagnostic repair workflow from an error log/stdin), `traces`. Most commands build their own `Kernel`/`AppConfig`/`LLMClient` per-invocation rather than sharing global state — follow that pattern for new subcommands.

### Interactive session (`kriya/repl.py`)
`kriya repl` loops reading a line and dispatches it straight into the same `main` Click group via `main.main(args=tokens, standalone_mode=False)` — deliberately no separate command parser; `generate "goal" -y` inside the session is the exact same code path as `kriya generate "goal" -y` from a shell, so there's nothing REPL-specific to keep in sync when a subcommand's options change. `--config` is captured once at session start and auto-prepended to every dispatched line unless the line supplies its own. Uses `prompt_toolkit` for the boxed prompt and a `Completer` (`_SlashCommandCompleter`) that lists every non-hidden top-level command live when the line starts with `/` — commands enumerated straight from `cli_main.commands`, not a hardcoded list. `main` is `@click.group(invoke_without_command=True)`; bare invocation (`ctx.invoked_subcommand is None`) starts the session too, but only when `sys.stdin.isatty()` — non-TTY bare invocation (piped/CI) falls through to Click's own help text instead, matching the TTY-safety pattern already used for `generate`/`fix`'s approval gates.

### Natural-language routing (`kriya/routing.py`, off by default — `routing.enabled`)
Lets a `kriya repl` line be plain English instead of an explicit command. `Router.route()` runs two independent checks concurrently: an embeddings centroid classifier (`routing.embed_model`, default `embeddinggemma:latest` — deliberately separate from `embedding.model`, which stays tuned for the RAG index, a different task) ranks the six routable commands by cosine similarity against curated exemplars; a narrow LLM gate (reuses `llm.model`) answers only "is this in scope at all," fails closed on any error. Below `routing.reject_threshold` or gate=no → `UNROUTABLE`. Top-2 candidates within `routing.ask_margin` of each other → `CLARIFY` (ask the user, don't guess — `kriya/repl.py::_resolve_clarify`). `build_dispatch_tokens()` maps the resolved command to real CLI argv — not uniform passthrough: `fix` needs `--error` not a positional arg, `review`/`analyze` need an *existing path* (`click.Path(exists=True)`) so natural language routes to `.` (repo root) rather than the raw text, `skills` defaults to `list`. Production port of `spikes/version_b_routing/` (not packaged/shipped — verify before trusting any specific number quoted from it, re-run against current local models if it matters) — see that spike's README.md for the full feasibility investigation and why this specific architecture (embeddings + gate + ask-when-uncertain) was chosen over pure-embeddings or pure-LLM routing.
